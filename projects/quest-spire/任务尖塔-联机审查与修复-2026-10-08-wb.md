# 任务尖塔 · 多人联机代码审查与修复（2026-10-08）

> 结论：**有值得修的地方，而且有一处是 P0。**  
> 任务尖塔的联机代码把「奖励流程」整条判成了「只有本人那台跑」，  
> 但游戏的校验和会把「奖励集编号 / 选择编号 / 遗物 `[SavedProperty]` / PlayerRng」全算进去  
> —— 只要有一项主客机对不上，客机就会被**踢回主菜单**（`State divergence detected!`）。  
> 本次已按本体自己的写法（`HealRestSiteOption`）把它改成「**各端都算、各端都建奖励集、各端都记账，  
> 只有真正改玩家状态的那几行才限定本人那台**」，编译 0 错 0 警告并已部署。

## 一、为什么任务尖塔老是「多人数据不同步」

先把证据摆出来（全部来自反编译 `data_sts2_windows_x86_64/sts2.dll`）。

### 1.1 校验和到底算了什么

`ChecksumTracker.GenerateChecksum(NetFullCombatState)` = `XxHash32(序列化后的 NetFullCombatState)`；  
而 `NetFullCombatState.FromRun(runState, action)` 里塞进去的是：

| 内容                                                          | 出处                                                         |
| ----------------------------------------------------------- | ---------------------------------------------------------- |
| `nextChoiceIds`                                             | `PlayerChoiceSynchronizer.ChoiceIds`（**每位玩家**一个计数器）        |
| `nextRewardIds`                                             | `RewardsSetSynchronizer.GetNextRewardIds()`（**每位玩家**一个计数器） |
| `Players[].gold / piles / potions / relics / orbs / rngSet` | 每位玩家的金币、牌堆、药水、**遗物（含 `[SavedProperty]`）**、充能球、PlayerRng    |
| `Rng`                                                       | 全局 run RNG                                                 |
| `Creatures`                                                 | 敌人血量/能力                                                    |

其中遗物那一项是 `relic.ToSerializable()` → `SerializableRelic { Id, Props, FloorAddedToDeck }`，  
`Props` 就是 `SavedProperties.From(this)` 反射出来的所有 `[SavedProperty]`。

**所以：任务尖塔挂在任务册上的每一个 `[SavedProperty]`（`QuestData`、`PendingRewardKinds`、  
`PaidRewardKinds`、`RewardedKinds`、`QuestSetupDone`）都是校验和的一部分。**

### 1.2 对不上会怎样

`ChecksumTracker.CompareChecksums`（只在主机侧跑）：

```csharp
if (localChecksum.data.checksum != remoteChecksum.checksum) {
    Log.Error($"State divergence detected! ...");
    ... SendMessage(stateDivergenceMessage, remoteId);
}
```

客机收到后 → `StateDiverged` → 主机 `DisconnectClient(senderId, NetError.StateDivergence)` → **踢回主菜单**。

### 1.3 本体的奖励是怎么做到各端一致的

`HealRestSiteOption.ExecuteRestSiteHeal`：

```csharp
await CreatureCmd.Heal(player.Creature, GetHealAmount(player));
await Hook.AfterRestSiteHeal(player.RunState, player, isMimicked);
List<Reward> rewards = new List<Reward>();
Hook.ModifyRestSiteHealRewards(player.RunState, player, rewards, isMimicked);
await RewardsCmd.OfferCustom(player, rewards);      // ← 注意：不是「只给本人那台」
```

而 `RestSiteSynchronizer.HandleRestSiteOptionChosenMessage` 是把「选了哪个篝火选项」**广播给所有端**、  
各端都 `ChooseOption(player, idx)` → 各端都跑一遍 `OnSelect()`。  
→ **所以 `RewardsCmd.OfferCustom` 在各端都会为同一位玩家执行一次。**

`RewardsSet.Offer()` 本身也是这么设计的：

```csharp
await GenerateWithoutOffering();                  // 各端都 populate（会消耗 PlayerRng）
Task task = _synchronizer.BeginRewardsSet(this);  // ← 各端都分配奖励集编号（nextId）
...
if (LocalContext.IsMe(Player)) { ...弹界面... }    // ← 只有本人那台弹 UI
await task;                                       // ← 别人那台只是等同一个奖励集走完
```

奖励的「选择」也是按 **(奖励集编号, 下标)** 复现的：  
`RewardsSetSynchronizer.SelectLocalReward` 只发 `RewardSelectedMessage { setId, rewardIndex }`，  
接收端 `set.Rewards[rewardIndex]` 去应用。

**推论：奖励列表必须在各端逐项一致，奖励集编号必须在各端同步递增。**

## 二、发现清单

| #       | 严重度    | 位置                                                                                                | 问题                                                                                                                                                                                                                              |
| ------- | ------ | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **F1**  | **P0** | `QuestBookRelic.Reward()` 里的 `if (!IsLocalOwner) return;`                                         | 整条奖励流程只跑本人那台 → ① `nextRewardIds` 分叉 → 校验和不匹配 → **客机被踢**；② 别人那台收到 `RewardSelectedMessage` 时 `nextId <= setId` → 当「奖励集还没建」**永久缓冲** → 奖励在别人机器上根本不生效（金币/卡牌/遗物不同步）；③ `RelicReward.Populate()` 消耗共享 PlayerRng，只有一台消耗 → Rng 也分叉        |
| **F2**  | **P0** | 同上，连带的 `PendingRewardKinds` / `PaidRewardKinds` / `RewardedKinds`                                 | 这三个 `[SavedProperty]` 只在本人那台写 → 各端 `SerializableRelic.Props` 不同 → 校验和不匹配 → **踢**                                                                                                                                                |
| **F3**  | **P0** | `AfterCombatVictory` / `BeforeCombatRewardOffered` 里的 `if (IsLocalOwner) PushBatchIntoRoom(...)`  | 房间的额外奖励是**按玩家**存的（`CombatRoom.ExtraRewards[player]`），战斗结束时并进**那位玩家**的奖励集。只有本人那台塞 → 各端那位玩家的奖励集**内容不同、编号相同** → 本人点「第 3 项」，别人那台发的是自己的第 3 项，甚至下标越界抛异常                                                                               |
| **F4**  | **P1** | `QuestBookRelic.IsLocalOwner` 的 `catch { local = true; }`                                         | `RunManager.Instance.NetService?.NetId` 在**没连上/断线时会抛异常**（`NetClientGameService.NetId => (NetClient ?? throw ...).NetId`），老代码把异常吞成「是本人」→ 每台机器都以为别人的册子也是自己的 → 同一份奖励各端各发一遍。而且 `_isLocalOwner` 是个**跨局复用**的 `bool?` 缓存，Owner 换了也不会重算 |
| **F5**  | **P1** | `QuestPickSync.StartMultiplayer` 用 `Entry.LocalPlayer(state)`                                     | 那个函数认不出本地玩家时会**静默退回 `state.Players[0]`**。多人局里退回之后：`NotifyLocalPick` 会拿**别人的编号**去广播（替别人挑任务），自己那个编号永远没人填，面板/账本也挂到了别人的册子上                                                                                                          |
| **F6**  | **P1** | `QuestSelection.OpenPicker` 没有战斗中判断                                                               | 「接取任务」按钮从开局一直亮到点为止，玩家完全可能在战斗里点。接取会当场做「接取时改动」（诅咒交易塞 5 张诅咒 / 大改造换牌）——那是**改牌组**，战斗中途改牌组既容易和结算打架，也会让各端牌组对不上                                                                                                                         |
| **F7**  | **P1** | `EnsureQuestSetups` 的「本地即时」路径                                                                     | `QuestRunner.ApplyAcceptSetups()` 只对**本机这本**做接取改动 → 只有一台的牌组被改（另一台要等到下次进房间才跑）→ 中间这段窗口牌组不一致                                                                                                                                       |
| **F8**  | **P2** | `CardGift` 的 `OrderBy(_ => Random.Shared.Next())`                                                 | 奖励内容各端各抽各的。**在 F1 修好之后这条会变成硬伤**（奖励列表必须各端一致），所以一并修了                                                                                                                                                                              |
| **F9**  | **P2** | `Entry` 的 `RunEndedEvent` 处理                                                                      | 只清了 `QuestRunner`，没清 `QuestPickSync` 的编号/本地玩家，也没把 `PlayerCount` 复位 → 下一局开局前，面板的「队友分册」、候选个数（单人 5 / 联机 10）、随身物闸都会按上一局的人数算                                                                                                         |
| **F10** | **P2** | 预留 choiceId 发生在若干 `await` 之后（fire-and-forget）                                                     | `GrantThenArmAsync` 是 `_ = ` 起来的，中间 `await GiveQuestBookToEveryone`；万一抛异常就没预留 → 那台的 `ChoiceIds` 和别人对不上。概率低，但代价是掉线，属于「值得加一层保险」                                                                                                   |
| **F11** | **P2** | `GrantOwnRelic<T>` 的四个 `fallback`（`HasDeadBranch` / `HasTorii` / `HasDripper` / `HasOrnithopter`） | 这四个「兜底随身物」标志**只在遗物发放抛异常时**才点亮，而那段只有本人那台会跑（别人那台 `OfferRelic` 直接返回 true）→ 一旦走到这条路，各端 `Props` 又不一样。**属于错误路径，概率低**；彻底解决要给它加一条网络消息，见 §五.5                                                                                            |

## 三、本次已修

### 3.1 `QuestBookRelic.Reward()` —— 去掉 `IsLocalOwner` 早退（F1 + F2）

整条流程现在**各端都跑**（记 `_dueKinds` / `_paidKinds` / `_rewardedKinds` 也各端都记），  
只有「真正改玩家状态」的那几行限定本人那台：

```csharp
public async Task Reward(QuestState q)
{
    await ApplySharedEffect(q.Def.Kind);   // 各端一致（本来就是这样）
    MarkRewardDue(q.Def.Kind);             // ← 账本各端一起记（进存档、也进校验和）
    try
    {
        bool queued = await GrantRewardNow(q);
        if (queued) ScheduleFlush();
        else { ClearDue(q.Def.Kind); _paidKinds.Add(q.Def.Kind); }   // ← 各端一起销账
    }
    catch (System.Exception e) { ... }
}
```

### 3.2 改状态的那几处加 `IsLocalOwner` 闸

| 方法                                                                            | 现在怎么处理                                                                                                                          |
| ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `GainGoldSynced`（战斗外直接到手那条）                                                   | `if (!IsLocalOwner) return;` 之后才 `PlayerCmd.GainGold` + `SyncLocalObtainedGold`；**战斗中的 `_batch.Add(new GoldReward(...))` 各端都走** |
| `OfferRelic`                                                                  | 战斗中排队各端都排；真正 `RelicCmd.Obtain` + `SyncLocalObtainedRelic` 只有本人那台；非本人那台**返回同样的 `true`**（否则调用方会在不同端走不同分支）                         |
| `FlushPendingRewards` 的 `_pendingRelics` 补发                                   | 队列各端都清，只有本人那台真发                                                                                                                 |
| `StrikeDeckHellraiser` / `SameCardManyTimes` 两个 `CardPileCmd.Add(…, Deck)` 分支 | 整块包进 `if (IsLocalOwner)`                                                                                                        |
| `ShopXDeal` 的 `RelicCmd.Obtain<ChemicalX>` 兜底                                 | 同上，并发 `SyncRelic`                                                                                                               |

### 3.3 `PushBatchIntoRoom` 不再判 `IsLocalOwner`（F3）

两处调用（`AfterCombatVictory` / `BeforeCombatRewardOffered`）都改成**各端都塞**。  
`CombatRoom.AddExtraReward` 就是个 `Dictionary<Player, List<Reward>>` 的 Add，没有本地玩家限制，  
而 `AfterCombatVictory` 这个钩子各端都会跑 —— 各端塞同一批，奖励集内容才对得上。

### 3.4 `IsLocalOwner` 加固（F4）

```csharp
var localId = MegaCrit.Sts2.Core.Context.LocalContext.NetId;   // 游戏自己的口径，永不抛异常
local = !localId.HasValue || owner.NetId == localId.Value;
// 缓存改成跟着 Owner 走：
if (ReferenceEquals(_isLocalOwnerFor, owner)) return _isLocalOwnerCached;
```

- 判据从 `NetService.NetId` 换成 `LocalContext.NetId`（`RunManager.Launch()` 里写的就是它）；
- `catch` 从「吞成 true」改成「**当非本人**」—— 宁可不发，也不要各端重复发；
- 缓存加了 Owner 判据，遗物实例跨局复用也不会读到上一局的结论。

### 3.5 `QuestPickSync` 重写（F5 + F7 + F10）

- 本地玩家**精确认**：用 `LocalContext.NetId` 在 `state.Players` 里找；**找不到就整个放弃**  
  （`return false` → 退回「同种子自动分配」），不再依赖 `Entry.LocalPlayer` 的「退回第一位玩家」；
- 接取时改动（`EnsureQuestSetups`）**各端一起做**：本机在 `NotifyLocalPick` 里调  
  `QuestRunner.LocalBook.EnsureQuestSetups()`，别端在 `WaitForRemoteAsync` 收到选择后调  
  `relic.EnsureQuestSetups()`（它自带 `QuestSetupDone` 幂等闸，多调无害）；
- 新增 `QuestPickSync.Reset()`。

### 3.6 `Entry` / `QuestRunner` / `QuestSelection`

- `Entry.LocalPlayer`：优先用 `LocalContext.NetId`，`NetService.NetId` 降为第二手（它会抛异常）；
- `Entry` 的 `RunEndedEvent`：加 `QuestPickSync.Reset(); QuestRunner.PlayerCount = 1;`（F9）；
- `QuestRunner.OtherBooks`：同样优先 `LocalContext.NetId`；
- `QuestSelection.OpenPicker`：战斗中拒绝打开（F6，弹提示「战斗结束后再接任务」）。

### 3.7 `CardGift` 确定性（F8）

新增 `SeedFor(owner, seq)`（种子 = `NetId ^ TotalFloor ^ 序号`）与 `ShuffleDeterministic`（Fisher–Yates + 固定种子），  
替换掉 `OrderBy(_ => Random.Shared.Next())`；`QuestBookRelic` 加了 `_giftSeq` 计数器，  
`BuildXCardReward` / `BuildCardReward` / `OfferXCardReward` 都收种子。

**编译结果：0 错误 / 0 警告**，已部署到 `mods/QuestSpire/QuestSpire.dll`（245,760 字节）。

## 四、为什么这次改动是对的（一条交叉验证）

修完之后我回头验了一下 `CardSelectCmd`，发现**本体早就是这么要求的**：

```csharp
uint choiceId = RunManager.Instance.PlayerChoiceSynchronizer.ReserveChoiceId(player);
await context.SignalPlayerChoiceBegun(player, PlayerChoiceOptions.None);
if (ShouldSelectLocalCard(player)) { ...弹 UI...; SyncLocalChoice(player, choiceId, result); }
else { int num = (await ...WaitForRemoteChoice(player, choiceId)).AsIndex(); ... }
```

`CardRemovalReward.OnSelect` → `DoUnsyncedCardRemoval(player)` → `CardSelectCmd.FromDeckForRemoval`。  
也就是说：**本体的奖励 `OnSelect` 在各端都会跑，而它内部的「选牌」会在各端各预留一次 choiceId  
（保证计数器同步）+ 非本人那台 `WaitForRemoteChoice` 等结果。**  
BaseLib 的 `CardTransformReward.OnSelect` → `DoUnsyncedCardTransform` 也是同一套。

所以「各端都跑 `OnSelect`」不是我们发明的，是游戏既定的契约；任务尖塔原来的 `IsLocalOwner` 早退才是异类。

## 五、没做 / 需要你决定

1. **`_offering` / `_lootPending` 是每本册子各自的实例状态**（`FlushBatchAsync` 的串行闸）。  
   各端理论上会在同一逻辑点置位，但如果哪一台的 `CombatManager.Instance.IsInProgress` 恰好差一拍，  
   奖励可能在不同端被交出去两次。**没实测之前我不动它**，先观察日志里有没有  
   `一次发了 N 项` 在不同端条数对不上的情况。
2. **`BaseLib` 的 `CardTransformReward` / `CardUpgradeReward` 在非本人那台的行为**：  
   按上面 3.4 的分析它应该能正常工作（内部走 `CardSelectCmd` 的 remote 分支），但这是**别人 mod 的实现**，  
   我没法保证。建议实机时专门试一次「宝可梦：进化」这条任务。
3. **`QuestSpire` 还没有自己的网络消息层**。如果以后还要做「非奖励类」的跨端状态  
   （比如商店里也能挑任务），建议照《篝火交易 / Campfire Trading》那样加一条 `INetMessage`  
   （`_netService.SendMessage<T>` + `RegisterMessageHandler<T>`），别再靠「各端各算」硬撑。
4. **`UpgradeRandomCards` 在联机里直接折现 150 金币**（原作者的取舍：「升级牌没有对应的同步接口」）。  
   其实现在可以改成走 `CardUpgradeReward`（BaseLib）或 `CardCmd.Upgrade` + 确定性选牌，  
   让它真正生效。**属于功能增强，没动。**
5. **F11 的四个兜底随身物**（`HasDeadBranch` / `HasTorii` / `HasDripper` / `HasOrnithopter`）：  
   现在「要不要点亮」取决于「遗物发放有没有抛异常」，那是个**只有本人那台知道**的事实。  
   正确的改法是把它换成**各端都算得出来的条件**（例如「本册里没有对应的自研遗物」），  
   并搬进 `ApplySharedEffect`；但要注意**不能和真遗物的效果叠加**（真遗物发成功时不该再点亮），  
   而别人那台是**异步**收到遗物的（`SyncLocalObtainedRelic` 走网络），  
   在 `ApplySharedEffect` 那一刻它还看不到 → 直接照搬会变成「各端算出来还是不一样」。  
   所以这条要连带设计一条「发放结果」的网络消息才干净，**这次没动**。

## 六、实机验收清单（双人局，主机 + 客机）

> 每一步都同时看**两台**的日志。重点看客机有没有被踢回主菜单。

1. **开局**：两台都拿到任务册（每人一本），面板「队友分册」里能看到对方。
   - 日志应有：两台各一条 `QuestPickSync: 多人局接管选任务，已为 2 位玩家预留编号`。
   - 两台都点「接取任务」→ 挑几个 → 确认。两台的任务列表应该完全一样。


1. **战斗中完成一条会直接改卡组的任务**（`StrikeDeckHellraiser`「地狱狂徒」最好认）。
   - 本人那台卡组 +1；对方那台看本人的卡组也应该 +1。
   - **不应该**出现「State divergence detected!」。
2. **战斗中完成一条进 `_batch` 的任务**（比如「精英加餐」→ 随机遗物 + 150 金币）。  
   打完架在官方「搜刮」界面里领 → 两台看到的遗物/金币应该一致。
3. **战斗外完成一条金币任务**（比如「展望未来」折现）→ 两台金币数一致。
4. **战斗中点「接取任务」按钮** → 应该被挡下（提示「战斗结束后再接任务」）。
5. **SL / 读档**：中途存档退出再进 → 任务进度和随身物都还在，奖励不重发也不丢。
6. **放弃一局重开**（单人 → 再联机，或反过来）→ 面板人数、候选个数应该跟着变。

如果还有 `State divergence detected!`，请把两台日志里  
`LOCAL STATE DUMP` / `REMOTE STATE DUMP` 那两段发我 —— 里面会直接指出是哪一项对不上  
（`Choice IDs` / `Reward IDs` / 每位玩家的 relics / gold / piles / rng）。

## 七、反编译 API 速查（本次用到的）

| 类型 / 成员                                                           | 作用                                                                            |
| ----------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| `ChecksumTracker.GenerateChecksum(string, GameAction?)`           | 生成并（客机）上报校验和                                                                  |
| `NetFullCombatState.FromRun(IRunState, GameAction?)`              | 校验和的**内容清单**（见 §1.1）                                                          |
| `ChecksumTracker.CompareChecksums`                                | 主机侧比对；不等就发 `StateDivergenceMessage`                                           |
| `NetHostGameService.DisconnectClient(ulong, NetError)`            | 踢人                                                                            |
| `RewardsSet.Offer()`                                              | `GenerateWithoutOffering` → `BeginRewardsSet`（**各端**）→ 仅本人弹 UI → `await task` |
| `RewardsSetSynchronizer.BeginRewardsSet(RewardsSet)`              | 给「这位玩家」的奖励集分配 `nextId`（**必须各端同序**）                                            |
| `RewardsSetSynchronizer.SelectLocalReward(Reward)`                | 只发 `{ setId, rewardIndex }`                                                   |
| `RewardsSetSynchronizer.HandleRewardSelectedMessage`              | `nextId <= setId` → 缓冲；否则按下标应用                                                |
| `Reward.SelectUnsynchronized()`                                   | 各端都会跑 `OnSelect()`                                                            |
| `CardRemovalReward.OnSelect` / `CardSelectCmd.FromDeckForRemoval` | **本体示范**：奖励在各端跑，内部再各端预留 choiceId                                              |
| `HealRestSiteOption.ExecuteRestSiteHeal`                          | **本体示范**：篝火选项里的 `RewardsCmd.OfferCustom` 各端都执行                                |
