### ⚠️ 顺带查出一个真 bug（**✅ 已修，2026-10-08 01:18**）

`DouSpireTable.cs` 的 `PopMultiplier` 里，粒子特效位置**把缩放比当像素用了**：

```csharp
var sw = DouSpireUi.Screen;              // 是倍率（≈1.0），不是屏幕宽 1920
var sh = sw * 0.5625f;                   // ≈0.5625
SpawnGameVfx(..., new Vector2(sw * 0.5f, sh * 0.44f), 2.2f);   // → (0.5, 0.247) 像素
```

`node.Position` 是**父级局部像素坐标**，所以特效实际落在**牌桌左上角 0.5px 处** ——
这大概就是"粒子特效不知道能不能显示"的答案：播了，但在角落里。

**修法**（一行）：位置改走 `DouSpireUi.Px()`：

```csharp
new Vector2(DouSpireUi.Px(960f), DouSpireUi.Px(475f))   // 1920×1080 设计稿口径
```

同时建议把 `SpawnGameVfx` 补三处：`Instantiate<Node2D>(PackedScene.GenEditState.Disabled)`、
`AddChildSafely`、走 `VFXUtil.ModSceneCache` 预加载。详见手册第七节。

#### ✅ 修复记录（2026-10-08 01:18，国际版 WorkBuddy 接手 dou-spire 代码线）

**结论：这个问题比"坐标算错"严重 —— 那个特效场景本身在非战斗环境里就是坏的。**

位置确实算错了（已改成按 `Size` 取视口像素），但**光修坐标没用**：反编译 `NBounceSparkVfx` 后发现
它的 `_Ready()` 里 `base.GlobalPosition = _startPosition;` 会把我们设的位置**直接覆盖**，
`base.Scale = ... * Rng.Chaotic.NextFloat(0.1f, 0.8f)` 也把缩放覆盖；
`_Process` 还按重力跑抛物线 + 在 `_floorY` 弹跳，而起点/地面是从
`NCombatRoom.Instance.GetCreatureNode(target).GetBottomOfHitbox()` 推的 ——
**牌桌上 `NCombatRoom.Instance` 是 null**。

所以做了两件事：

1. **换场景** → `vfx/vfx_coin_explosion_jumbo`（筹码爆炸，语义也配斗地主）。
   它是纯 `GPUParticles2D`，脚本 `NVfxParticleSystem._Ready()` 只把子粒子 `Emitting` 置 true
   并在 `_lifetime`(3s) 后自毁，**不碰位置、不碰缩放、不依赖战斗房间**。
2. **`SpawnGameVfx` 整个改写** → 直接调**本体现成的非战斗入口**
   `VfxCmd.PlayNonCombatVfx(container, position, "vfx/xxx")`。
   它内部已经做了 `PreloadManager.Cache.GetScene` + `GenEditState.Disabled` +
   `AddChildSafely` + `GlobalPosition = position`，所以**上面那三条建议一条都不用自己写**。
   （另：`AssetCache.GetAsset` 是懒加载的，命中不了会自己 Load 并只打一条警告 —— 不需要自建缓存。）
   顺带把 2.6s 的兜底 `QueueFree` 改成 5s（原来会把 lifetime=3.0 的筹码拦腰砍掉）。

**同时落地**：`尖塔牌面-问题报告.md` 里那两个卡面问题（费用宝珠斜杠 / 手牌被按钮压住）

## 六、🔴 推送失败的真正原因查明：Steam 自动内容检查锁了物品（2026-10-08 01:55）

第三节那个"判断是短时间高频写操作触发临时冷却"的猜测，**方向对了一半，但真正原因不是冷却**。

### 证据

用户从工坊页面截图，Steam 在条目页顶部挂了黄色横幅：

> **此项目正在等待我们的自动内容检查系统分析。在我们证实其内容无害之前
> （例如试图窃取信息的钓鱼站点链接），项目将暂时隐藏。**

**因果链**：

1. 21:04:51 物品 3815233309 发布成功（`Upload finished : OK`）。
2. 约 2 分钟后 Steam **自动内容检查**介入 → 物品**临时隐藏 + 锁定**。
3. 锁定期间任何提交都被拒 → `k_EResultAccessDenied`：
   - 21:07:17 → 3815232473 → Access Denied（该条目现已被删，API 返回 `result=9` 不存在）
   - 21:26:45 / 21:29:03 / 21:41:54 → 3815233309 → 三次全被拒
4. **每次重试都是一次新的内容修订，会重新触发扫描** —— 所以越硬重试越不会解锁。

### ⚠️ 三条必须记住的排查教训

1. **`GetPublishedFileDetails` 看不到"待自动检查"状态。**
   01:52 查官方接口得到 `result=1 / visibility=0(public) / banned=0 / ban_reason=空`，
   据此错误地下了"物品健康"的结论。**判断物品状态必须看工坊网页，不能只信 API。**
2. **ModUploader 的输出写进 `mod-uploader.log` 并独占锁住它**（`--help` 会因此崩
   `IOException: ... being used by another process`）。用 `> xxx.log 2>&1` 重定向时
   .NET 侧是**块缓冲**，进程不退出就看不到任何内容 —— 极易误判"上传器秒退"。
   权威实时信号在 **Steam 侧**：`D:/software/steam/logs/workshop_log.txt` 的
   `Upload starting for workshop item <id> by AppID 2868840`（有这条才算真的开始传）。
3. **`tasklist /FI "PID eq <pid>"` 在本机会静默失败**（无输出、exit 1），会误判进程已退出。
   用 `tasklist | grep -i ModUploader`。
