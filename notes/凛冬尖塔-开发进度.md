## ★ M1 真人实测反馈（2026-10-06 15:40，用户亲测）

**结果：成功——「OK、我已经验证。简要来说就是出怪是吧。」**

✅ **M1 核心链路验证通过**：`[ModInitializer]` 注册 → 设置页开关 → 凛冬契约遗物发放 →
`BeforeSideTurnStart` 第 2 回合 `CreatureCmd.Add` 加怪 → 场上真的多了怪。
→ 说明「战斗中动态加怪」这条路是通的，设计案 §七 风险② 的最核心疑问已被实测排除。

⚠️ **发现的问题**：
1. **出怪叠在一起了**——多个 `CreatureCmd.Add` 加进来的怪位置重叠，视觉上糊成一团。
   而后面还要加更多怪，会越来越挤。
2. **只有单人角色**——玩家确认了当前是传统的单人打牌类型。

**问题 1 的定位（M1.5 待解）**：
- 敌人的摆放位置在 STS2 里是**由 `ICombatState` 的槽位/索引体系管的**
  （`Creature.SlotName` / `ICombatState.SetEnemyIndex()` / `SortEnemiesBySlotName()`）。
- 单纯 `CreatureCmd.Add<T>()` 不给位置 → 叠在一起。
- **解法分三层**（详见单房间设计案 §四 Q1）：
  1. **怪数控制**（最有效）：一波 2~5 个，从设计上绕开拥挤，别一次摆一堆。
  2. **排布**：抄 `NCombatRoom.PositionPlayersAndPets` 的"偏移网格"思路
     （官方文档原话：行列数由数量的平方根决定，偏移摆放，中间留出牌位）
     + 抄宝可梦 mod 的 `PokemonShoulderConfig` 归一化坐标表。
  3. **缩尺寸**：只有一波超 5~6 个才动，**不要全局缩放 UI**。

**问题 2 的结论**：**保持传统打牌类型**（用户设计案早就定了"卡牌还是卡牌"）。
一人 / 一双手牌 / 一个房间 / 一波波来的怪。

```csharp
// AbstractModel.ShouldStopCombatFromEnding()
// 文档原文逐字：
//   If all enemies are dead, should we stop combat from ending?
//   This should be set to true when all enemies are dead but new enemies are about to spawn.
//   <returns>Whether combat should be marked as about to end</returns>
```

- **这就是官方的原话在描述敌潮战**。怪清完了但波次表还没走完 → 返回 `true` → 战斗不结束。

- 文档特别注明：这个谓词**不走** `IterateCombatHookListeners` 守卫，是直接派发的，

### ★★★ 后续：wb 已把整条链反编译核实完毕（15:55）

**新文档：`notes/凛冬尖塔-波次系统API备忘.md`** —— 全部内容反编译实测，ZCode 可直接照抄。

**三条硬结论（其中一条是修正 ZCode 的方案）**：

1. **"一波怪" = 一个自定义 `EncounterModel` 子类**，重写 `GenerateMonsters()`
   返回 `IReadOnlyList<(MonsterModel, string?)>`，**第二个元素就是槽位名**。
   `Slots` 属性（`IReadOnlyList<string>`）定义这个遭遇有哪些站位。
   → **不需要自研坐标、不需要缩 UI。**

2. **⚠️ 修正：`SetEnemyIndex` 在自定义遭遇里不能用！**
   实测源码：`if (Encounter.Slots.Any()) throw new InvalidOperationException(
   "Cannot modify turn order of a combat with pre-set slots");`
   → **凡是有槽位的遭遇，调 `SetEnemyIndex` 直接抛异常。改用 `Slots` + `SlotName`。**

3. **⚠️ 坑：`SortEnemiesBySlotName` 里 `Slots.IndexOf(null)` 返回 -1**，
   所以 `SlotName == null` 的敌人会被排到**最前面**，且多个 null 之间顺序不定。
   → 想控站位就必须**给槽位起名 + 给每个怪传对应名**。

**另一条待确认**：反编译 `InkletsNormal`（官方 3 只小怪遭遇）发现**它槽位全传 `null` 也不叠**。
所以"M1 叠怪 = 没传 slotName"这个结论**可能有别的解释**。
→ **建议直接改用本体正规路**：`CreateCreature(monster, CombatSide.Enemy, "l1")` + `combatState.AddCreature(c)`，
   跳过 `CreatureCmd.Add`。`AddCreature` 的文档明确写「**目前只有 Doormaker 战斗这么用**」，
   是官方支持的动态加怪入口。
→ **验证不用真人操作**：在加怪前后打日志，看 `combatState.Enemies.Select(c => c.SlotName)` 即可。

# wb 对 M1.5 的代码审查回执（2026-10-06 15:58）

> 全文：`notes/凛冬尖塔-M1.5代码审查.md`。**这里只放结论。**

## 一、确认无误（ZCode 这版写得好）

- 锁1 `ShouldProceedToNextMapPoint() => FrostSpireConfig.LockRoom` ✅
  （**钩子只在遗物在场时收票 → 没发契约的局完全不干预**，设计干净）
- 锁2 `ShouldStopCombatFromEnding() => _nextSubWavePending` ✅
- `BeforeCombatStart()` 里提前 `_nextSubWavePending = true` ✅ —— **考虑到位**，
  防住"本体怪在 A 波上场前被打空就提前结算"
- `SpawnOnFreeSlot<T>` 从 `Encounter.Slots` 挑空槽，挑不到退回 `null`（**宁可叠也不崩**）✅
- 应急口子 `LockRoom` 可运行时关闭 ✅

## 二、⚠️ 发现一个真问题：读档后「锁2」会失效

`_nextSubWavePending` 是 `private bool`，**没有 `[SavedProperty]`**（注释写明"不进存档"）。
但 `WavesSpawned` **有** `[SavedProperty]`。这个组合有坑：

**场景：A 波刷完（第 2 回合）后存档退出 → 读档**
1. 读档时 `BeforeCombatStart()` 可能**不重跑** → `_nextSubWavePending` 保持默认 `false`
2. 清掉本体怪 + A 波 → `ShouldStopCombatFromEnding()` 返回 false → **战斗直接结算**
3. **B 波永远不来，验证流程断掉**

**为什么风险真实**：本体读档路径确实与正常开局分叉
（API 里有 `CombatRoomMode.FinishedCombat` = "loading a save after combat ended" 专用模式）。
**验证清单第 2/3/4 条恰好会被它影响——测的时候中途存档会得到假阴性。**

**推荐修法（方案 1，约 3 行）**：不存布尔，**从状态推导**：
```csharp
public override bool ShouldStopCombatFromEnding()
    => WavesSpawned < 本场总波数;   // M1.5 硬编码 2；M2 从波次表算
```
→ **天然抗读档**（`WavesSpawned` 已进存档），且 M2 更自然：波次表本来就该有"总共几波"。
（备选：给布尔加 `[SavedProperty]`；或在 `BeforeSideTurnStart` 里兜一层校正。方案 1 最优。）

## 三、两个小建议

1. **`SpawnOnFreeSlot` 的 `taken` 只统计"当前在场"的敌人**——怪死后槽位释放，B 波会复用。
   M1.5 无所谓（A 波死了 B 波才来）；**M2 若同波内有多只怪且中途死亡，会出现位置跳变**，

2. **`Encounter?.Slots` 基类默认是空数组** → `slot` 恒为 `null` → 退回叠怪。
   **M2 做自定义遭遇时务必把 5 个槽位名写全**（模板见 `凛冬尖塔-波次系统API备忘.md` §四）。

# wb 为 M2 扫障：波次机制全链反编译（2026-10-06 16:10）

## 挖到的核心机制：战斗结束判定的完整逻辑链

反编译 `CombatManager.IsCombatEnding`：
```csharp
if (turnState.PendingLoss != null) return true;
// ① 场上还有活的 primary enemy → 不结束
if (State.Enemies.Any(e => e != null && e.IsAlive && e.IsPrimaryEnemy)) return false;
// ② ★ 官方口子
if (Hook.ShouldStopCombatFromEnding(turnState.State)) return false;
return true;
```
→ 由 `CheckWinCondition` 在多个安全点调用 → **这就是"事件驱动波次"的正确挂钩点**。

## ★ 三条最重要的官方原话（ZCode 直接照这个写）

1. **`ShouldStopCombatFromEnding`**：
   > "If all enemies are dead, should we stop combat from ending?
   > This should be set to true when all enemies are dead but new enemies are about to spawn."
2. **`IterateCombatHookListeners`**（★ 最容易踩的坑）：
   > "yields nothing if combat is over or ending when the dispatch begins ...
   > so a hook dispatched after combat has started ending **fires for no one**"
   → **战斗进入"结束中"后，之后派发的战斗钩子没人收。**
   → `ShouldStopCombatFromEnding` 是**唯一例外**（直接派发、不走该守卫）。
3. **`IsOverOrEnding`**：
   > "use this instead of `IsEnding` or `!IsInProgress`, because they can return
   > unexpected results at certain boundary points."

## ✅ 清掉一个悬念：波次怪天生就是 primary enemy

`IsPrimaryEnemy` 是**只读推导属性**（`=> !IsSecondaryEnemy`，
而 secondary 只取决于"是否挂了 `MinionPower`/`IllusionPower` 类 power"）。
→ **`CreatureCmd.Add<T>` 加的普通怪天生 primary，不需要额外设置** ✅
→ **⚠️ 但波次怪不能挂仆从类 power**，否则会变 secondary **自动暴毙**
→ 顺带修正认知：M1.5"本体怪 + A 波全灭才不结算"能生效，**可能是"本体怪"在撑着**，
   不一定测到了锁2。验证清单写的"本体怪+A波全灭"是对的 ✅

## M2 的正解（回答代码审查里的问题 A / B）

```csharp

[SavedProperty] public int CurrentWaveIndex { get; set; }
// 场级（开战即写入，读档随存档回来）
[SavedProperty] public int WavesDoneThisCombat { get; set; }
[SavedProperty] public int WavesTotalThisCombat { get; set; }

public override bool ShouldStopCombatFromEnding()
    => WavesDoneThisCombat < WavesTotalThisCombat;   // 与 TurnNumber 完全解耦

// 惰性兜底（解决 A）：每回合都跑的钩子里补初始化
BeforeSideTurnStart: if (WavesTotalThisCombat == 0) { WavesTotalThisCombat = Plan(); WavesDone = 0; }

// 波次推进（解决 B）：事件驱动，不用回合号
AfterSideTurnEnd / BeforeSideTurnStart:
    if (清场 && WavesDone < WavesTotal) { WavesDone++; SpawnWave(WavesDone); }
```

**为什么抗读档**：判定只看两个**已持久化的数字**，不依赖"现在是第几回合"。
