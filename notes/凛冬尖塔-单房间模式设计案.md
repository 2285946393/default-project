# 凛冬尖塔 · 「单房间」模式设计案（前身方案）

> 2026-10-06 15:45。起因：用户 M1 实测后提出问题——
> **「让玩家进入一个房间就足以完成这局游戏？打这个房间的怪、抓牌、来怪、问事件、精英 Boss 啥的，
> 按原来的路线去出现各种东西，只是你只需要点这一个房间，而你一直在这个房间进行活动？」**
> 并自我怀疑：**「往这方面做是不是有些无聊、自主选择权少了很多？」**

---

## 零、先回答那句自我怀疑

**不无聊，而且这不是「退而求其次的前身」——它本身就是凛冬前线的原生形态。**

凛冬前线（FrostBound）的玩法就是**布防 → 敌潮一波波来 → 撑住**，它没有"地图路线选择"这个环节。
所以在 STS2 里做单房间，**不是阉割了尖塔，而是把尖塔的路线选择换成了凛冬的波次决策**。

用户担心的"自主选择权少了"其实是个**误判**：选择权没有消失，是**换了位置**。

| 传统尖塔的选择权 | 单房间模式的选择权 |
|---|---|
| 走哪条路线（左/右、精英/商店） | 这一波怎么活（布什么单位、留哪张牌） |
| 什么时候打精英 | 什么时候开下一波（自己按按钮，还是等它来） |
| 赌不赌未知房 | 赌不赌"提前开波换额外奖励" |

**关键**：只要"开下一波"的**时机**握在玩家手里，选择权就保住了。这是这个设计的命门。

## 一、★ 最重要发现：官方为这个模式留了专用 API

我在 `sts2.xml`（官方 API 文档）里挖到几个钩子，**几乎是为"单房间波次战"量身定做的**。这不是我猜的，是文档原文。

### 发现 1 · `ShouldStopCombatFromEnding` —— 官方原话就在说这个场景

```csharp
// AbstractModel.ShouldStopCombatFromEnding()
/// <summary>
/// If all enemies are dead, should we stop combat from ending?
/// This should be set to true when all enemies are dead but new enemies are about to spawn.
/// </summary>
/// <returns>Whether combat should be marked as about to end</returns>
```

**逐字翻译**：「如果所有敌人都死了，**要不要阻止战斗结束**？当所有敌人都死了、但**马上要刷出新敌人**时，这里应该返回 true。」

→ **官方的原话就是"敌潮还没完，别结束战斗"。**
→ 这直接解决了设计案 §七 风险②（"加怪是否影响本体清场判胜"）——**不用绕，官方给的就是这个口子。**
→ 而且文档特别注明：这个谓词**不走** `IterateCombatHookListeners` 的守卫直接派发，因为它在战斗结束判定过程中收集投票，**不能被抑制**。说明它是被认真设计过的扩展点。

### 发现 2 · `ShouldProceedToNextMapPoint` —— 锁死"不许出房间"

```csharp
// AbstractModel.ShouldProceedToNextMapPoint()
/// <summary>
/// If the player is attempting to proceed to the next point on the map, should they be allowed to?
/// </summary>
/// <returns>Whether to allow it.</returns>
```

**一句话**：玩家想点地图下一个点的时候，**这个钩子说了算**。
→ 单房间模式的实现方式变得极其干净：**本局永远返回 `false`**，玩家就出不了这个房间。
→ 不需要改地图、不需要删节点、不需要动存档结构。**一个布尔值解决"永远待在一个房间"。**

### 发现 3 · `ModifyGeneratedMap` —— 真要改地图也有干净入口

```csharp
// AbstractModel.ModifyGeneratedMap(IRunState runState, ActMap map, int actIndex)
/// <summary>
/// Modify the dungeon map before it is set up.
/// </summary>
```

**注意**：`ModifyGeneratedMapLate` 的文档明确写了「**必须不能替换地图**（不能返回另一个 `ActMap` 实例），因为联机重连时这个钩子也会跑在已保存的地图上，拓扑必须保持」。而**不带 Late 的那个版本就是用来替换地图的**（文档原话："To replace the map, use ModifyGeneratedMap"）。

→ 如果以后想要"地图上只有一个节点"这种视觉化做法，走这里；v1 用不着。

### 发现 4 · `RoomType` 可以运行时变（官方明文举例）

`RoomType` 的文档原文举例：

> 1. 玩家点了一个 `?` 点（`MapPointType.Unknown`）
> 2. 房间类型解析为 `RoomType.Event`
> 3. **在那个事件里，玩家选了「Start a Fight!」选项**
> 4. **房间类型变成了 `RoomType.Monster`**

→ **官方自己就在做"事件房原地变战斗房"。**
→ 这正是用户想要的「在一个房间里既问事件又打架」的官方先例，**不是我们要发明的东西。**

### 发现 5 · `CombatRoomMode.VisualOnly` —— 敌人先亮出来不能打

```csharp
/// Visual only - shows all creatures (allies and enemies) but no combat UI,
/// no interactivity, no hooks.
/// Used for combat-style events where enemies are visible but not yet fightable.
```

→ 官方原话"用于**战斗风格的事件**：敌人可见但还不能打"。
→ **这正是"波次预告"的最佳实现**——下一波怪可以先站在场上给你看，你准备好了再开打。比纯文字面板强得多。

### 发现 6 · `CombatRoomMode.FinishedCombat` / `SetUpBackground` —— 战斗结束后房间还在

已有注释说明：战斗结束后如果还在房间里，用 `FinishedCombat` 模式（只显示玩家、无战斗 UI）。
`SetUpBackground` 的文档也提到「**pre-finished rooms**」这个概念，即"已经打完但没离开的房间"。

→ 说明**"待在房间里"是官方支持的常态**，不是怪异状态。

### 发现 7 · `AfterCombatVictory` 之后还有房间层钩子

钩子清单里有一整套房间/流程钩子，全部可挂：

| 钩子 | 用途（在单房间模式里） |
|---|---|
| `BeforeRoomEntered` / `AfterRoomEntered` | 进入房间时初始化"这一局的波次表" |
| `BeforeCombatStart` / `BeforeCombatStartLate` | 开波前铺场（提前摆好敌人 = VisualOnly 预告） |
| `AfterCombatVictory(Early)` | 一波打完 → 不让它走结算，直接进"波次间准备" |
| `AfterCombatEnd` | 全部波次打完 → 这里才放行真正的结算 |
| `AfterActEntered` | 换幕（第一幕→第二幕）时刷新波次表 |
| `ModifyRewards` / `TryModifyRewards` | 波次奖励自定义（打一波给什么） |
| `ModifyNextEvent` | 控制"事件"出现在哪个波次之间 |

**结论**：这个模式在 API 层面**是完全正向支持的**，几乎所有需要的行为都有对应的官方钩子。

## 二、单房间模式的完整循环设计

### 核心循环

```
进入房间（这辈子就这一个房间）
   │
   ├─ 第 1 波：普通怪（教学：告诉你这是敌潮战）
   │     ↓ 打完
   ├─ 波次间：【布防窗口】← 玩家在这里有主动权
   │     · 抓牌（三选一，正常尖塔奖励）
   │     · 布置工事/单位（凛冬的核心乐趣）
   │     · 看下一波预告（VisualOnly，怪已经站那儿了）
   │     · 【准备好了 → 点「开下一波」】← ★ 选择权就在这个按钮上
   │
   ├─ 第 2 波 ... 第 N 波：普通怪（越来越难）
   │
   ├─ 波次间：【事件】← 不走地图也能碰到事件
   │
   ├─ 精英波：精英怪（本体精英改造成单只强化怪）
   │
   ├─ 【Boss 波】：幕 Boss
   │     ↓ 打完
   └─ 换幕：第 2 幕开始，波次表刷新、难度提升，房间背景换掉
```

### 「按原来的路线去出现各种东西」怎么落地

用户原话是"按原来的路线去出现各种东西"——这句话很准。落地方式：

**把"地图路线"折叠成"波次表"**。

原来玩家在地图上走：战斗 → 事件 → 战斗 → 商店 → 精英 → 休息 → Boss。
现在这条**路线变成了一张确定的波次清单**，写在面板上：

```
第 1 幕 · 共 11 波
[1] 普通  ×2      ✅ 已过
[2] 普通  ×3      ⬅ 当前
[3] 事件：遇到拾荒者
[4] 普通  ×4
[5] 精英：寒霜哨兵
[6] 事件：暴风雪
[7] 普通  ×5
[8] 商店（波间开启）
[9] 普通  ×6
[10] 精英：冰封巨兽
[11] BOSS：凛冬之主
```

**这张表就是"新地图"**。玩家来之前不知道内容，走到才揭晓（保留探索感），
但**节奏完全由自己掌控**——这是关键。

## 三、三个必须做对的细节（否则真的会无聊）

用户担心的"无聊"是真实存在的风险，但**可以精确规避**。风险点只有三个：

### 风险 1 · 节奏太慢 → 对策：主动权给玩家

**错误做法**：一波打完自动进下一波，玩家只能等。
**正确做法**：波次间是**玩家自己按「开下一波」**，想拖多久拖多久，布防布到满意为止。
→ 这就完全消灭了"被动等待"的无聊感。

### 风险 2 · 一直打同样的怪 → 对策：波次表要有"变化"

不要只有"普通怪 ×N"。波次表里必须混入：

- **事件波**（不打架，纯选择）
- **精英波**（单只、强、给好奖励）
- **Boss 波**（幕末）
- **环境波**（特殊规则：这波敌人免疫物理 / 这波每回合全场掉血…）

→ 每 2~3 波插一个"调料"，就不会腻。

### 风险 3 · 没有路线选择 → 对策：给"波次内决策"

尖塔的路线选择本质是**风险管理**（走精英还是回避）。
单房间模式里，风险管理可以这样保留：

- **「提前开波」奖励**：不等预告就开打 → 额外金币/额外卡牌。
- **「跳过波次」代价**：某些波次可以跳过，但要付出 HP 或金币。
- **事件里二选一**：拿资源 or 拿血量。

→ **选择权从"走哪条路"变成"这一波怎么赌"**。本质没变。

## 四、用户的两个直接问题的答案

### Q1：出怪叠在一起，UI 怎么办？要缩小全部 UI 吗？

**不用缩小整个 UI（那是下策，会让所有字都变模糊）。分三层解决：**

**第 1 层 · 怪数控制（最有效，优先级最高）**
- 尖塔原版单场敌人一般 1~4 个。**单房间模式不是"一次摆 10 个怪"**，
  而是"一波 3~5 个，打完再一波"。
- 换句话说：**"怪很多"是时间上的多，不是空间上的多。**这是最省事的解法。

**第 2 层 · 排布（有官方先例可抄）**
- 官方 `NCombatRoom.PositionPlayersAndPets` 文档写明：玩家按**"偏移网格"**摆放，
  行列数由玩家数的平方根决定，**"并尝试把所有玩家塞进可用空间，中间留够出牌的位置"**。
- 敌人这边同理可用网格/错位两排。**参考宝可梦 mod 的 `PokemonShoulderConfig`**：
  它用归一化坐标（0~1）把单位"贴"到指定位置，**根本没改 STS2 坐标系**。
  → 我们的波次敌人也可以走这张"坐标配置表"。

**第 3 层 · 只有实在挤不下才缩**
- 如果一波真的超过 5~6 个，再压缩敌人绘制尺寸 + 缩小血条 + 允许重叠错位。
- **不要先动全局 UI 缩放。**全局缩放是最后手段，会牵动所有界面。

**具体动作**：M2 做波次表时，直接**给每波限定 2~5 个怪**，从设计上绕开拥挤问题。

### Q2：我们这边只有单独的一个角色？还是传统的打牌类型？

**保持传统打牌类型。**用户在设计案里早就定了："**卡牌还是卡牌**"。

- 玩家还是原来那个角色（战士/猎手…），还是那套能量/抽牌/打牌。
- 凛冬的"单位/建筑"作为**卡牌形态的工事牌**混进卡组（打出后变召唤物或持久能力）。
- 所以：**一个人，一双手牌，一个房间，一波波来的怪。**

这和凛冬前线其实是**更贴近**的——凛冬前线也是"一个驻地 + 一队单位 + 一波波敌人"，
它也不是 RTS 式的多线操作。

## 五、里程碑怎么调整（新增 M1.5）

原设计案里程碑：M1 骨架 → M2 波次 → M3 工事 → M4 平衡。

**建议插入 M1.5（单房间模式验证）**，理由：
- M1 已验证"能加怪"，但**没验证"能不能留住玩家不让他走"**。
- M1.5 只做两件事：`ShouldProceedToNextMapPoint → false` + `ShouldStopCombatFromEnding → true`。
- **这两个加起来可能不超过 30 行代码**，但它是整个凛冬模式的**地基**。
- 地基验证完，M2 的波次表才有意义。

| 里程碑 | 内容 | 验收 |
|---|---|---|
| M1 ✅ | 工程 + 模式开关 + 加怪 | 已实测：出怪成功（但叠了） |
| **M1.5（新）** | **锁房间（不许出）+ 一波不死不停战** | 新开一局：打不完不许走；打完一波战斗不结算、继续打第二波 |
| M2 | 波次表 + 预告面板 + 波次间布防窗口 | 连打三场：波数/阵容/奖励正确 |
| M3 | 8 张工事牌 | 每张真人试一遍 |
| M4 | 平衡 + 本地化 + 工坊材料 | 用户过数值 |

## 六、这个"前身"到底值不值

用户问"这么做是不是比较符合前身"。**答案是：这就是目的本身。**

- 凛冬前线的乐趣 = 布防 + 抗潮。**没有地图路线这一环。**
- 所以"单房间"不是通向凛冬的**过渡方案**，它**就是**凛冬在尖塔里的样子。
- 反而如果做了完整的尖塔地图，那才是**没搬到凛冬**——那是尖塔自己。

**一句话**：把地图折叠掉，凛冬才会浮出来。
