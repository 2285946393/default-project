## 0. 一句话

**它给游戏自带的模组界面补了一个"加载顺序编辑器"** —— 游戏本体只有启用/禁用勾选框，
**没有排序功能**。它补上排序，并把结果写进 `settings.save`。

对我们最大的价值**不是"怎么排序"**，而是它顺带暴露的两件事：

1. ★★★ **手动顺序在游戏里的真实地位**（见 §2）—— 这是"排序失稳"问题域的最后一块拼图。
2. ★★★ **怎么正规地读写 `settings.save`**（反射路径 + 账户隔离守卫，见 §4）——
   我们任何一个 mod 想给玩家一个"开关"，都该走这条路，别自己另起配置文件。

## 2. ★★★ 核心发现：手动顺序到底算不算数？

这是本次拆解最值钱的一条。**结论：手动顺序只是"平局决胜"，而且游戏下次启动会把它覆盖掉。**

### 证据（游戏本体 `ModManager.cs`，0.111.0 反编译）

```csharp
// :275  先排序
SortModList(_settings?.ModList ?? new List<SettingsSaveMod>());
foreach (Mod mod2 in _mods) { TryLoadMod(mod2); }   // 按排好的顺序加载

// :287-299  ★ 排完之后，游戏把 settings 里的 mod_list 用「排好的顺序」重写一遍
if (_settings != null && _settings.PlayerAgreedToModLoading)
{
    List<SettingsSaveMod> list = new List<SettingsSaveMod>();
    foreach (Mod mod in _mods)                                  // _mods 已经是排好的
    {
        SettingsSaveMod s = new SettingsSaveMod(mod);
        bool isEnabled = _settings.ModList
            .FirstOrDefault(m => m.Id == mod.manifest?.id)?.IsEnabled ?? true;   // 只保住开关
        s.IsEnabled = isEnabled;
        list.Add(s);
    }
    _settings.ModList = list;                                   // ← 手动顺序被覆盖
}
```

### 排序算法（`SortModList`，Kahn 拓扑排序 + 手动顺序当优先级）

```csharp
// :384-397  入度为 0 的先进队列，优先级 = 手动顺序里的下标
PriorityQueue<Mod, int> priorityQueue = new PriorityQueue<Mod, int>();
Dictionary<string,int> manualIndex = new();     // mod_id -> 手动顺序下标
for (int j = 0; j < manualOrdering.Count; j++)
    manualIndex[manualOrdering[j].Id] = j;

int priority = manualIndex.TryGetValue(list[k].manifest.id, out var v) ? v : 999999999;
priorityQueue.Enqueue(list[k], priority);        // 不在手动表里的 → 999999999（排最后）
```

### 由此推出的四条结论

1. **手动顺序不是"绝对顺序"，是"同层内的相对顺序"。** 有依赖关系的 mod 一定被拉到前面，
   你手动把它往后拖也没用。
2. **游戏会用它自己的（排好的）顺序覆盖 `settings.save` 的 `mod_list`。**
   → 所以你写进去的顺序，下一次启动后**不再等于**你写的那份。这是**设计如此**，不是 bug。
3. **唯一被"保住"的是每个 mod 的 `IsEnabled`**（按 id 查回来）。
   → 想"关掉某个 mod"，写 `is_enabled = false` 是**可靠**的；想"固定绝对顺序"是**做不到**的。
4. **`RemoveDisabledMods()`（`:274`）在排序之前就执行** —— 被禁用的 mod 根本不进 `_mods`，
   也就不参与排序。所以"禁用"是真的不加载，不是加载后隐藏。

> **对我们的意义**：以后排查"为什么顺序和我想的不一样"，先问"这两个 mod 之间有没有依赖关系"。
> 没有依赖 → 顺序由 `settings.save` 决定；有依赖 → 依赖赢。

## 3. ★★★ 壳 + 版本化实现（`VersionLoader`，354 行）

这是**这个生态里「壳 + 版本化实现」的第 4 个样本**（前三个：RitsuLib / 尖塔：琐事 / 意图图），
而且**它是写得最干净的一个**，可以直接当模板抄。

### 目录约定

```
LoadOrderManager.dll                     ← 壳（16 KB，只有 VersionLoader + GameVersion）
bin/
  g0.107.1/
    LoadOrderManager.Impl.dll            ← 实现（94 KB，真正的功能）
```

### 入口

```csharp
using MegaCrit.Sts2.Core.Modding;

[ModInitializer("Initialize")]           // ★ 游戏自带的 mod 入口标记
public static class VersionLoader
{
    public static void Initialize()
    {
        if (Interlocked.Exchange(ref _started, 1) != 0) return;   // 幂等
        string modDir = ResolveModDirectory();                    // 自己 dll 所在目录
        List<VersionDir> list = Discover(modDir);                 // 扫 bin/g*/*.Impl.dll
        VersionDir picked = Pick(list);                           // 按游戏版本挑
        Environment.SetEnvironmentVariable("AMS_LOADER_SELECTED_VERSION", picked.Name);
        Load(picked, tag);
    }
}
```

### 版本探测（`GameVersion.Detect()`，两级回退）

```csharp
// 1) 读游戏 exe 旁边的 release_info.json 的 "version" 字段
// 2) 反射 MegaCrit.Sts2.Core.Nodes.NGame.GetGameVersion()   （Type.GetType(..., "sts2")）
// 3) 都失败 → 返回 null，日志警告，退到"最新实现"
```

`Parse()` 的清洗规则值得抄：去掉 `-` 后缀（预发布）、去掉 `+` 后缀（构建元数据）、
去掉 `v` 前缀、`Version.TryParse`，缺的段补 0。

### 挑实现（`Pick`，四段回退）

```csharp
1. 文件夹名精确等于 $"g{Major}.{Minor}.{Build}"          ← 命中就用
2. 版本号 <= 游戏版本 里最大的那个（降级兼容）
3. 文件夹名叫 "latest" 的
4. （游戏版本探测失败时）版本号最大的
```

### 加载实现（★ 注意用的是**自己的 ALC**，不是 Default）

```csharp
// VersionLoader.cs:204
AssemblyLoadContext ctx =
    AssemblyLoadContext.GetLoadContext(typeof(VersionLoader).Assembly) ?? AssemblyLoadContext.Default;
Assembly asm = ctx.LoadFromAssemblyPath(assemblyPath);   // ★ 与壳同一个 ALC
MethodInfo init = FindEntryPoint(asm);                   // 扫 public static void Initialize()
init.Invoke(null, null);
```

> ★ **这是对之前"默认 ALC 不探兄弟 dll"那条记忆的重要修正/补充**：
> 正确做法是**用 `GetLoadContext(自己的程序集)` 拿到当前 ALC，再 `LoadFromAssemblyPath`**，
> 这样兄弟 dll 和壳在同一个 ALC 里，类型能互相看见。

`FindEntryPoint` 的健壮性也值得抄：先 `GetExportedTypes()`，失败再 `GetTypes()`，
再失败兜 `ReflectionTypeLoadException.Types.Where(t => t != null)`（**和弹幕尖塔同一招**）。

### 调试开关（环境变量）

| 变量 | 作用 |
|---|---|
| `AMS_LOADER_DRYRUN=1` | 只探测、不执行入口（用来验版本选择逻辑） |
| `AMS_LOADER_SELECTED_VERSION` | 壳写、实现读（实现可以知道自己是被哪个包加载的） |

### 智能排序（`LoadOrderPanel.SmartSort`，UI 侧，不是游戏侧）

也是 Kahn，但**排序键不同**：库类 mod 优先（`lib/base/core/framework/common/api/helper/toolkit`），
其余按名字。**循环依赖的追加到末尾**并提示数量。
（对比：游戏侧 `SortModList` 的平局键是"手动顺序下标"。）

## 4. ★★★ 怎么正规地读写 `settings.save`

### 读

```csharp
// 顺序：SaveManager.Instance → .SettingsSave → .ModSettings → .ModList（IEnumerable）
// 每条：Id(string) / Source(ModSource 枚举) / IsEnabled(bool)
```

### 写（`LoadOrderRuntime.TrySaveOrderedEntries`，全部反射，零编译期引用）

```csharp
object sm = SaveManager.Instance;
object settingsSave = GetMemberValue(sm, "SettingsSave");

// 1. 拿到/创建 ModSettings
object modSettings = GetMemberValue(settingsSave, "ModSettings")
                  ?? Activator.CreateInstance(AccessTools.TypeByName("…Modding.ModSettings"));

// 2. 造一个 List<SettingsSaveMod>
IList list = (IList)Activator.CreateInstance(
    typeof(List<>).MakeGenericType(AccessTools.TypeByName("…Modding.SettingsSaveMod")));
foreach (var e in entries)
{
    object item = Activator.CreateInstance(settingsSaveModType);
    SetMemberValue(item, "Id", e.Id);
    SetMemberValue(item, "Source", Enum.ToObject(modSourceType, e.Source));  // ★ 枚举要转
    SetMemberValue(item, "IsEnabled", e.IsEnabled);
    list.Add(item);
}
SetMemberValue(modSettings, "ModList", list);

// 3. 存盘
AccessTools.Method(ResolveCoreType("…Saves.SaveManager"), "SaveSettings", Type.EmptyTypes, null)
    .Invoke(sm, null);
```

游戏本体的模型（`MegaCrit.Sts2.Core.Modding`）：

```csharp
public class ModSettings {
    [JsonPropertyName("mods_enabled")] public bool PlayerAgreedToModLoading { get; set; }
    [JsonPropertyName("mod_list")]     public List<SettingsSaveMod> ModList { get; set; }
    public bool IsModDisabled(string id, ModSource source)
        => ModList.Any(m => m.Id == id && m.Source == source && !m.IsEnabled);  // ★ 同时比 id 和 source
}
public class SettingsSaveMod {
    [JsonPropertyName("id")]         public string Id { get; set; }
    [JsonPropertyName("source")]     public ModSource Source { get; set; }
    [JsonPropertyName("is_enabled")] public bool IsEnabled { get; set; } = true;
}
public enum ModSource { None, ModsDirectory, SteamWorkshop }   // 1 = 本地, 2 = 工坊
```

> ★ **`Id` 单独不唯一，必须配 `Source`。** 本地 mod 和工坊 mod 可以同 id。
> LoadOrderManager 自己的 key 就是 `"{id}::{source}"`（`LoadOrderEntry.BuildKey`）。

### ★★ 账户隔离守卫（`ValidateCurrentUserScope`）—— 最该抄的一段

**它拒绝在"当前账号"和"settings.save 路径里的账号"对不上时写盘。**

```csharp
// 运行时账号：MegaCrit.Sts2.Core.Platform.PlatformUtil
//   .PrimaryPlatform → GetLocalPlayerId(platform) → ulong
// 路径里的账号：正则从 settings.save 全路径里抠
Regex UserIdPathRegex = new(@"[/](?:steam|gog|epic|xbox|none)[/](?<id>\d{1,20})(?:[/]|$)", IgnoreCase);

if (!runtimeUserId.HasValue)  → 拒绝（"无法确认当前用户，拒绝写入以免覆盖别的账号"）
if (路径里的 id != 运行时 id) → 拒绝
```

> **为什么值得抄**：多账号 / 家庭共享 / 切 Steam 号的时候，
> 一个 mod 天真地写 `settings.save` 会**把另一个账号的模组配置覆盖掉**。
> 我们任何写玩家配置的功能，都该做这个校验。

## 5. ★★ 漂移检测快照（为什么需要它）

因为 §2 那条：**游戏会覆盖你写的顺序**。所以"我写的"和"现在文件里的"必然会对不上。
LoadOrderManager 的做法：

```csharp
// 写盘成功后，额外存一份快照到自己的目录：
//   <OS.GetUserDataDir()>/LoadOrderManager/state/last_apply_<userId>.json
//   { SavedAtUtc, RuntimeUserId, PathUserId, SettingsPath, Entries:[{Key, IsEnabled}] }
```

启动时 / 打开面板时比对，不一致就在界面顶部显示黄字警告：

> `warning_overwritten` = 「警告：当前模组顺序与上次应用快照（{0}）不一致，可能被依赖排序或其他模组覆盖。」

### 关键：比对用的是**子序列**检查，不是全等

```csharp
// IsOrderMonotonic(expected, persisted)
//   把 persisted 的每个 key 记下标；遍历 expected，
//   只要下标单调不减 → 通过。
//   → 允许"中间插入了别的东西"，只要我设的那些相对顺序没变。
```

> **这是个很聪明的设计**：既容忍了游戏的覆盖（会插入/移动条目），
> 又能在"我设的顺序真的被破坏了"时报出来。
> **可抄的姿态：写外部系统之后，留一份自己的快照 + 用宽松（子序列）规则校验。**

## 6. 预设系统（`ModPresetStore`）

存 `<OS.GetUserDataDir()>/LoadOrderManager/presets.json`：

```json
{ "SchemaVersion": 2,
  "Profiles": [ { "Name":"Default",
                  "DisabledMods":["xxx"],      // 只记"关掉的"和"见过的"
                  "KnownMods":["aaa","bbb"],
                  "AutoEnableNewMods": true } ],
  "CurrentProfileIndex": 0 }
```

★ **设计要点：预设只存「差异」不存「全量」。**
`KnownMods`（保存时见过的）+ `DisabledMods`（其中关掉的）。
应用时：

```csharp
if (!preset.KnownMods.Contains(id))  → 新 mod：IsEnabled = AutoEnableNewMods; IsNew = true
else                                 → 老 mod：IsEnabled = !DisabledMods.Contains(id)
```

→ 好处：**预设不会因为"你新订阅了一个 mod"就过时**；新 mod 按策略自动决定。
→ `SchemaVersion` + `MigrateIfNeeded`：老版本存档自动升级（旧版没有 `KnownMods` 就按"全都算见过"补）。

## 8. 自检机制（`SelfTest`，环境变量驱动）

**一个可以直接在 CI / headless 里跑的端到端自检**，全靠环境变量：

| 变量 | 作用 |
|---|---|
| `LOADORDER_SELFTEST=panel` | 建面板 → 打开 → 检查注入 → 退出 |
| `LOADORDER_SELFTEST=...`（其它值） | 跑完整流程（建预设 / 切预设 / 应用） |
| `LOADORDER_SELFTEST_WRITE=1` | 允许真的写盘 |
| `LOADORDER_SELFTEST_APPLY=<预设名>` | 要应用哪个预设 |
| `LOADORDER_SELFTEST_PROBE=<modid>` | 探测哪个 mod |
| `LOADORDER_UI_COMPACT=1` | 强制紧凑布局 |
| `LOADORDER_UI_VIEWPORT=WxH` | 模拟分辨率 |

> **可抄**：把"自检"做成**环境变量驱动的独立流程**，就不需要人肉点界面，
> 也能在 headless 里验证"UI 注入成功了吗"。

## 11. 大白话总结

**这个 mod 干的事**：游戏自带的模组界面只能勾"开/关"，不能拖顺序。它补了个拖顺序的界面。

**它教我们的两件大事**：

1. **顺序这东西，游戏说了算。** 你排的顺序只用来"同一层里谁先谁后"，
   有依赖关系的 mod 一定被拉到前面；而且**游戏下次启动会用它自己排好的顺序，把你写的那份覆盖掉**。
   唯一稳的是"开/关"这个开关。
2. **想给玩家一个开关，就走游戏自己的 `settings.save`**，别自己另起一个配置文件。
   而且写之前**必须确认"现在登录的账号"和"要写的那个文件属于哪个账号"是一致的** ——
   否则会覆盖别人的配置。它写了 30 行代码专门防这个。

**另外它代码写得特别干净**，那个"壳（16KB）+ 按游戏版本加载实现（94KB）"的结构，
是这个生态里第 4 个同类样本，也是最适合抄的一个。
