# DSH 插件安装与版本兼容记录（2026-10-03）

## 一句话结论

**装第三方 DSH 插件前，先看它 `peerDependencies` 里的 `@deepseek-ai/dsh-llm` 范围是否包含本机运行的 DSH 版本。**
不匹配就先装旧版插件，**不要急着升级 DSH**。

## 实测：升到 0.1.7-rc.2 会弄坏什么

2026-10-03 把 `D:\software\dsh` 那份换成 0.1.7-rc.2 后试跑，两个问题：

1. **`dsh-chat-manager@1.5.0` 被判不兼容，整条 bundle 被跳过**
   （报 `Plugin dsh-chat-manager@1.5.0 is incompatible with dsh 0.1.7-rc.2`，它的 peer 锁死在
   `0.1.7-alpha.1`）。它的 1.5.7 又要求 `0.2.0-rc.x` —— 中间没有正好配 `0.1.7-rc.2` 的版本。

2. **`@deepseek-ai/dsh-settings` 被 profile 里的旧副本遮蔽 → 设置功能直接报错**
   `settings (@deepseek-ai/dsh-settings): TypeError: this.load is not a function`

   来源已查明（`pnpm why @deepseek-ai/dsh-settings` 在 profile 目录跑）：
   **`@y1x1n/dsh-prompt-optimizer@0.3.16`**（发送栏那个 Optimize 按钮）把它当**普通依赖**装了
   `^0.1.2-rc.1`，pnpm 提升到 `profiles/web/node_modules/`，Node 解析时优先级高于运行时的
   `.dsh-module-fallback`，于是 0.1.7 的运行时配上了 0.1.2 的 settings 包。
   （这个插件的最新版 0.3.16 依赖没变，升级它没用。）

> 也就是说：**本机插件生态整体卡在 0.1.5 线上**，单独升级 DSH 会连带出问题。

## 实际采用的方案：装旧版插件

| 插件 | 装的版本 | 为什么是这个版本 |
|---|---|---|
| `dsh-connect-trae` | **2.2.0** | 2.3.0 起要求 `dsh-llm >=0.1.7-rc.1`；2.2.0 是 `>=0.1.5-0 <0.2.0-0` |
| `dsh-connect-workbuddy` | **2.0.15** | 2.1.0 起要求 `>=0.1.7-rc.1`；2.0.15 是 `>=0.1.5-rc.1 <0.2.0` |
| `dsh-agy-link` | **0.4.42** | 它的 peer 全是 `*`，不挑版本 |

安装命令（会自动登记进 `dsh.profile.bundles`，不用手工改 package.json）：

```powershell
& "D:\software\dsh\dsh.cmd" plugin --profile web add dsh-connect-trae@2.2.0 dsh-connect-workbuddy@2.0.15 dsh-agy-link@0.4.42
```

改完 profile 配置后**必须重启 DSH** 才生效（bundle 只在启动时装载）。

### 怎么自己找"最后一个支持当前版本的插件版本"

```powershell
npm view <包名>@<版本> peerDependencies --json     # 看 @deepseek-ai/dsh-llm 的范围
```

或者拉全量版本表逐个比对（本次用的脚本逻辑：取版本号里第一段的数字下界，
判断 `0.1.5-rc.2` 是否落在范围内）。判断要点：

- `*` / 无声明 → 能用
- `>=0.1.5-0 <0.2.0-0` → 能用
- `>=0.1.7-rc.1 <0.3.0-0` → **不能用**（要升级 DSH）

### 教训：判断"某软件装没装"不能只查默认路径

2026-10-03 第一次判断时只看了 `%LOCALAPPDATA%\Programs\` 和 `%APPDATA%`，得出
"Trae 没装、WorkBuddy 没装"的**错误结论** —— 用户习惯把软件装在 `D:\software\<名字>\`，
`%APPDATA%` 里只有数据目录、程序目录在 D 盘。

可靠做法是查注册表卸载项：

```powershell
Get-ItemProperty "HKCU:\Software\Microsoft\Windows\CurrentVersion\Uninstall\*",
                 "HKLM:\Software\Microsoft\Windows\CurrentVersion\Uninstall\*" -ErrorAction SilentlyContinue |
  Where-Object { $_.DisplayName -match '关键词' } |
  Select-Object DisplayName, DisplayIcon, InstallLocation, UninstallString
```

`DisplayIcon` 一般就是主程序路径（本次靠它直接定位到 `D:\software\trae\Trae CN\Trae CN.exe`）。

## 国际版 WorkBuddy（WorkBuddy AI）—— 为什么要单独装一个

插件的国内版 / 国际版是**两套独立登录**，凭据文件里的 `domain` 决定归属：

- `workbuddy.cn`（国内版，账号「有花无实」，3000 积分）
- `workbuddy.ai` / `codebuddy.ai`（国际版）

本机原本只有国内版，所以插件自检里 `Global accounts: 0`，国际版那 20 个模型一个都不列。
（插件对"没有账号的区域"会**整个不列模型**，不是藏起来。）

### 国际版的免费政策（2026-10 查证）

| 项目 | 额度 |
|---|---|
| Free 版 | 每月 100 积分 |
| 新用户注册 | 一次性送 250 积分（两周有效） |
| 限时每日活跃 | Free 每天 +30、Pro 每天 +50 |

每日活跃的判定：**当天用 WorkBuddy 或 CodeBuddy 客户端发起过至少一次真实对话/任务**，
网页端产生的对话不计入；满足后系统自动结算，不用手动领。

### 安装记录

| 项 | 值 |
|---|---|
| 官网 | `https://www.workbuddy.ai`（国内直连可开，不用梯子） |
| 安装包 | `WorkBuddy-win32-x64-user-5.6.2.39458645-35219ed6.exe`（506.4 MB） |
| 装到 | `D:\software\WorkBuddy AI\WorkBuddyAI.exe`（5.6.2） |
| 静默安装 | `Start-Process <exe> -ArgumentList '/S', "/D=<目录>"` —— 实测 `/D` 生效，装到了指定目录 |
| 插件配置 | 用户级环境变量 `WORKBUDDY_APP_EXECUTABLE=D:\software\WorkBuddy AI\WorkBuddyAI.exe` |

**为什么必须配这个环境变量**：WorkBuddy 桌面端 **5.6.0 起把 `accessToken` / `refreshToken` /
`nickname` 加密**成 AES-256-GCM 信封，插件要靠 App 自身的原生绑定取字段密钥。
插件只按默认路径（`%LOCALAPPDATA%\Programs\WorkBuddy` 等）找 App，找不到就报
`Encrypted-credential support: unavailable` —— 本机装在 `D:\software\` 下，所以必须用环境变量指过去。
（国内版是 5.5.3，凭据还是明文，所以之前不配也能读出账号。）

两版可以共存：国内版 `D:\software\WorkBuddy\WorkBuddy.exe`（5.5.3），国际版 `D:\software\WorkBuddy AI\WorkBuddyAI.exe`（5.6.2）。

### 找下载直链踩的坑（别再重复一遍）

- workbuddy.ai 是整站 SPA，**下载地址由点击后的接口现给**：JS 包、Chrome HTTP 缓存、
  Chrome 下载库（`History` 表）里**都没有**，别浪费时间翻这些
- 用程序点「Download Now」能触发下载，但 **Chrome 会拦掉后续的自动下载**（需要真人点击 + 允许"多个下载"）
- ⚠️ **Chrome 的默认下载目录是 `D:\BaiduNetdiskDownload`**，不是 `%USERPROFILE%\Downloads`
  （在 `User Data\Default\Preferences` 的 `download.default_directory` 里查）
- ⚠️ **`.crdownload` 大小停住 ≠ 没下完**：本次那个"卡住"的文件和后来完整下好的文件
  **SHA256 完全一致** —— 它早就下完了，只是 Chrome 没改名。判断完整性要看
  PE 版本信息 / 比对哈希，别只看扩展名
- 这个安装包**尾部没有 NSIS 的 `NullsoftInst` 签名**，所以"查尾部签名"这个办法对它不适用

### 登录成功后的凭据落点（关键，别被"看起来没登录"骗了）

国际版 App 登录后写的是 **`workbuddy-desktop-ai.info`**，文件名和国内版**不一样**：

```
%LOCALAPPDATA%\CodeBuddyExtension\Data\Public\auth\
    workbuddy-desktop.info        ← 国内版 5.5.3（明文）
    workbuddy-desktop-ai.info     ← 国际版 5.6.2（加密）
```

插件是**扫描整个 auth 目录、按 uin 去重**的，所以文件名不同**不影响**识别。

真正卡住它的是**加密**：5.6.x 把 `accessToken` / `refreshToken` / `nickname` 写成
`{"$wbEncrypted":1,"envelope":…}` 的 AES-256-GCM 信封。没有 `WORKBUDDY_APP_EXECUTABLE` 时，
插件**整条账号直接丢掉**，表现成 `Global accounts: 0` —— 看起来像"没登录"，其实是"解不开"。

> 排查顺序建议：先看 `doctor` 里的 **`Encrypted-credential support:`** 那一行。
> 显示 `unavailable` 就说明是环境变量没配，跟账号本身没关系。

配好之后（本次实测）：

```
Encrypted-credential support: available (D:\software\WorkBuddy AI\WorkBuddyAI.exe)
CN (domestic): signed in as 有花无实              余额 3000
Global:        signed in as zjj357951@gmail.com   余额 350   ← 注册送 250 + Free 每月 100，正好对上
Static fallback models: CN 12, Global 20
```

⚠️ 环境变量是**用户级**的，必须**重启 DSH** 才会被它读到；在 DSH 里跑的 `pwsh` 是子进程，
同样要重启后才继承得到（临时验证可以像上面那样在命令里手动 `$env:...` 一下）。

## 把模型选择器里的"厂商"名改成中文

DSH 界面本身有语言开关（设置 → 通用设置 → 中文 / English，存在 `settings.yaml` 的 `locale.preference`），
但**模型选择器里那几组"提供方"名字是插件自己带的英文**，界面语言切不动它们
（`设置 → 模型` 里那个「编辑」弹窗只能填密钥，没有改名的地方）。

名字写死在插件文件里 —— 改这几个常量即可（**纯显示名，不影响功能**）：

| 插件 | 位置 | 原名 | 现名 |
|---|---|---|---|
| `dsh-connect-workbuddy` | `lib/index.js` → `WORKBUDDY_PROVIDER_DISPLAY_NAMES` | `WorkBuddy` / `WorkBuddy Global` | **`WorkBuddy 国内版` / `WorkBuddy 国际版`** |
| `dsh-connect-trae` | `lib/index.js` → `TRAE_PROVIDER_DISPLAY_NAMES` | `Trae` / `Trae Global` | **`Trae 国内版` / `Trae 国际版`** |
| `dsh-agy-link` | `dist/index.js` → `providerInfo()` 里的 `name` | `Antigravity (agy CLI)` | **`Antigravity 谷歌`** |

⚠️ 两条注意：

1. **必须重启 DSH 才生效**（显示名是宿主端启动时注册进模型选择器的）
2. **插件升级会覆盖回去** —— 以后再升级这三个插件，记得重新改一遍

**故意没动的两个**：

- `DeepSeek` —— DSH 自带提供方，字符串在 DSH 本体里，改了会被 DSH 升级覆盖
- `Our Free Model` —— 这个字符串同时是它的**路由 id**（`adapter.js` 的 `ROUTE_MAIN`），
  改了可能把 provider 路由弄坏，别动
