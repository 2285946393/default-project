# 斗地主尖塔 · 启动崩溃诊断：ONNX 依赖解析不到（2026-10-09）

> 现场：用户报「尖塔打不开了，可能 mod 下多了」。
> 结论：**不是 mod 数量问题，是 DouSpire 自己的 ONNX 依赖在启动阶段解析不到。**
> 本文只做诊断，**未改任何代码**（代码归国内台）。国际台已临时把 `mods/DouSpire` 挪出。

---

## 2. 根因（三段链，缺一不可）

### 2.1 DouSpire 侧：静态字段的类型来自 ONNX

`projects/dou-spire/DouSpireCode/Table/DouZeroAi.cs`

```csharp
line  7:  using Microsoft.ML.OnnxRuntime;
line 58:  private static readonly Dictionary<string, InferenceSession> Sessions = new();
```

`Sessions` 是个**静态字段**，它的**声明类型**是 `Dictionary<string, InferenceSession>`，
而 `InferenceSession` 来自 `Microsoft.ML.OnnxRuntime`。
→ 任何「读这个字段的 `FieldType`」的反射，都会强制运行时去加载 ONNX 程序集。

### 2.2 BaseLib 侧：它会对**所有 mod 类型的每一个静态字段**读 `FieldType`，且不 try/catch

`projects/ref-baselib/upstream/BaseLib-StS2-master/Patches/PostModInitPatch.cs`

```csharp
// line 142-151：挂在 ModelDb.InitIds 的 Prefix 上，启动必经
[HarmonyPatch(typeof(ModelDb), nameof(ModelDb.InitIds))]
[HarmonyPrefix]
private static void LatePostInit()
{
    ...
    foreach (var type in ReflectionHelper.ModTypes)     // 所有 mod 的全部类型
    {
        ...
        foreach (var field in type.GetFields(BindingFlags.Static | BindingFlags.Public | BindingFlags.NonPublic))
        {
            CheckSpecialSpireField(field);              // line 179
        }
    }
}

// line 197-199
private static void CheckSpecialSpireField(FieldInfo field)
{
    Type fType = field.FieldType;      // ★ 就是这一行炸的：读类型 = 要加载 ONNX
    if (!fType.IsGenericType) return;
    ...
}
```

**注意第 199 行是「先读类型再判断」**，也就是说哪怕这个字段跟 BaseLib 毫无关系
（`Sessions` 不是 `SavedSpireField`、不是 `AddedNode`），也照样会去解析它的类型。
而且这一层**没有任何 try/catch** —— 异常直接冒到 `GameStartup` → 弹错误框。

对照：RitsuLib 的 `ModTypeDiscoveryHub` 做同样的事，但它 catch 了，所以只留一条 WARN。

### 2.3 游戏加载器侧：默认 ALC 不会去 mod 文件夹找依赖

`ModManager.cs`

```csharp
line 247:  AppDomain.CurrentDomain.AssemblyResolve += HandleAssemblyResolveFailure;
line 954:  AssemblyLoadContext loadContext = AssemblyLoadContext.GetLoadContext(Assembly.GetExecutingAssembly());
line 957:      assembly = loadContext.LoadFromAssemblyPath(text2);   // 默认 ALC

line 1165: private static Assembly HandleAssemblyResolveFailure(object? source, ResolveEventArgs ev)
           // 只特判 "sts2," 和 "0Harmony," —— 其它一律返回 null
```

`LoadFromAssemblyPath`（默认 ALC）**不会**探测被加载 dll 所在目录。
所以 `DouSpire.dll` 旁边那个 `Microsoft.ML.OnnxRuntime.dll` 默认根本不会被找到。

### 2.4 为什么 DouSpire 自己那段加载没救到

`DouZeroAi.cs` 里其实**已经**做了正确的事：

```csharp
line 516: private static void EnsureRuntime()
line 524:     var managed = Path.Combine(root, "Microsoft.ML.OnnxRuntime.dll");
line 527:     System.Reflection.Assembly.LoadFrom(managed);   // 已加载过就不会重复 Load
line 529:     var native = Path.Combine(root, "onnxruntime.dll");
line 530:     if (File.Exists(native)) NativeLibrary.TryLoad(native, out _);
```

`EnsureRuntime()` 的调用点只有两处，**都在出牌时**：

```
line  90:  EnsureRuntime();   // 在 Choose() 里
line 540:  EnsureRuntime();   // 在 SessionFor() 里
```

→ **执行得太晚。** BaseLib 在 `ModelDb.InitIds`（启动阶段）就已经反射过 `Sessions` 了，
那时候 `EnsureRuntime()` 一次都没跑过。

**一句话：加载时机错位 —— ONNX 要等出牌才加载，但启动时就已经有人读它的类型了。**

## 3. 证据：最小复现实验

在 `%TEMP%\alc-probe-test` 用三个小程序验证「默认 ALC 到底会不会探目录」：

| 实验 | 做法 | 结果 |
|---|---|---|
| A | `Default.LoadFromAssemblyPath(sub/Main.dll)`，`Dep.dll` 与 `Main.dll` 同目录 | ❌ `FileNotFoundException: Could not load file or assembly 'Dep'` |
| B | 同上，另把 `Dep.dll` 拷到宿主目录（`AppContext.BaseDirectory`） | ❌ **仍然找不到**（默认 ALC 只认 `*.deps.json` 里的 TPA 清单） |
| D | 改用 `Assembly.LoadFrom(sub/Main.dll)` | ✅ `MAIN->DEP-OK` |
| E | 默认加载 + 自己挂 `Default.Resolving` 回调探目录 | ✅ `MAIN->DEP-OK` |

**实验 A 与游戏里的报错逐字一致。** 机制确认：
`LoadFromAssemblyPath` 不探目录（D/E 那两种写法才探）。

补充：`data_sts2_windows_x86_64/sts2.deps.json` 里**没有任何 onnx 条目**，
所以「把 dll 丢到游戏托管目录」也不会被认（实验 B 已证）。

| 日志 | OnnxRuntime 命中 | 结果 |

| `godot2026-10-08T19.40.07.log` | **0** | 能进游戏 |
| `godot2026-10-08T19.40.52.log` | **0** | 能进游戏 |
| `godot2026-10-09T10.33.00.log` | **0** | 侥幸进去了（到选人界面） |
| `godot2026-10-09T10.33.35.log` | 2（WARN + 致命 ERROR） | 启动即死 |
| `godot.log`（10:33:58） | 2 | 启动即死 |

`mods/DouSpire/DouSpire.dll` 的编译时间是 **今天 10:30:02**；
`onnx/` 模型目录是 **今天 00:59**。→ ONNX 是昨夜到今早新加的，8 号之前完全没这问题。

**并且它是「看运气」的**：三次启动一次进得去。两次运行的内容登记数还不一样：

```
10:33:00（活）  ModelIdSerializationCache initialized. Categories: 21 Entries: 2822 Properties: 103
10:33:35（死）  ModelIdSerializationCache initialized. Categories: 21 Entries: 2977 Properties: 123
```

> **★ 2026-10-09 10:55 更正（我第一版写错了）**
> 我一开始把「2822 vs 2977」当成「内容排序不稳定」的证据。**这是错的。**
> 后来把两份日志里的 mod 清单抽出来 diff，差别只有两行：
>
> ```

> > Spire PvP / 尖塔决斗 [SpirePvp] (0.2.5)
> ```
>
> 即 **10:33:00 加载 42 个 mod，10:33:35 加载 44 个** —— 差的就是用户今早刚订的那两个。
> `2977 − 2822 = 155` 条，正好对得上「尖塔：琐事」加的那一幕内容量。**顺序并没有乱。**

**真正和「崩不崩」相关的是「mod 集合有没有变」**：

| 日志 | mod 数 | RitsuLib 的 `ModTypeDiscoveryHub` 警告 | 结果 |
|---|---|---|---|
| 10:33:00 | 42 | **没有** | 进得去 |
| 10:33:35 | 44 | **有**（点名 `DouZeroAi.Sessions`） | 启动即死 |
| `godot.log` | 44 | 有 | 启动即死 |

且失败那两次，`LatePostInit` **连第一个 SavedProperty 警告都没打出来**就炸了
（`Found 0 SavedSpireFields` / `Adjusting keys of custom message` 这两行在失败日志里完全不存在）。

**最可能的解释**：RitsuLib / BaseLib 的类型扫描有缓存 ——
mod 集合没变时走缓存（不碰字段类型，所以侥幸过关）；**mod 集合一变就重新全量扫**
（于是碰到 ONNX 字段，崩）。
这也能解释为什么「刚装完 mod 第一次启动最容易崩」。

> ⚠️ 这一条是**推断**，不是实验证明（我没法在不启动游戏的前提下验证缓存行为）。
> 但无论是哪种解释，**结论不变**：靠「多启动几次」不是修法。

**→「多试几次说不定能进」不是修法。**

## 5. 修法（给国内台，按推荐度排）

### ★ 方案一（最小改动，一行）：把 ONNX 的加载提前到「任何反射之前」

`EnsureRuntime()` 已经写好了，只要在 mod 初始化阶段先调一次即可。

- 在 `DouSpire.Entry.Initialize()` 里调一次 `DouZeroAi.EnsureRuntime()`（**改成 public/internal 可见**）；
- 或者更保险：给 `DouZeroAi` 加一个 `[ModuleInitializer]` 静态方法，
  程序集一加载就跑 `EnsureRuntime()` —— 早于任何反射，比 `Entry` 还早。

时间上完全来得及：`Entry.Initialize()` 在日志第 862 行，`ModelDb.InitIds` 在第 2152 行。

> 注意 `EnsureRuntime()` 依赖 `DouSpireAssets.RootDir`，要确认它在 mod init 阶段已经可用。

### ★ 方案二（更彻底，建议一起做）：让字段签名里不出现 ONNX 类型

```csharp
// 现在
private static readonly Dictionary<string, InferenceSession> Sessions = new();

// 改成
private static readonly Dictionary<string, object> Sessions = new();
// 用的时候 (InferenceSession)Sessions[key]
```

这样**任何**框架（BaseLib / RitsuLib / 将来别家）反射 mod 类型都再也碰不到 ONNX。
方案一解决「这一次」，方案二解决「这一类」。两个一起做最稳。

### 方案三：在 `Entry.Initialize()` 里挂全局解析器

（实验 E 已验证可行）

```csharp
AssemblyLoadContext.Default.Resolving += (ctx, name) =>
{
    var p = Path.Combine(DouSpireAssets.RootDir, name.Name + ".dll");
    return File.Exists(p) ? ctx.LoadFromAssemblyPath(p) : null;
};
```

### 方案四：把 ONNX 相关代码拆成兄弟程序集

用 `Assembly.LoadFrom` 惰性加载（**尖塔：琐事就是这么做的**：
`STS2_Things.BaseLibBridge.dll` 与主 dll 同目录，靠 `LoadFrom` 拿）。
这个方案还能顺带解决「双框架兼容」，但工作量最大。

### ❌ 不要走的路

- **不要**改 `data_sts2_windows_x86_64/sts2.deps.json` 去登记 ONNX —— 那是游戏本体文件，
  Steam 校验会还原，且改坏了整个游戏都起不来。
- **不要**靠「多启动几次碰运气」。

## 6. 国际台已做的临时处置（可一键还原）

```
D:\software\steam\steamapps\common\Slay the Spire 2\mods\DouSpire
   ↓ 移动
D:\software\steam\steamapps\common\Slay the Spire 2\_disabled_mods\DouSpire
```

- 为什么挪这么远：`ModManager.ReadModsInDirRecursive` 是**递归**的（`ModManager.cs:550-576`），
  放在 `mods/` 下任何子目录（比如 `mods/_disabled/`）**照样会被加载**。
- 游戏只扫两个根：`<游戏目录>/mods` 和创意工坊目录（`ModManager.cs:250/254/258`）。
- **还原**：把 `_disabled_mods\DouSpire` 挪回 `mods\` 即可。
- 注意：国内台下次重新编译部署 `mods/DouSpire` 时，它会**再出现**，届时要么重新挪走，
  要么先按方案一/二修好。
