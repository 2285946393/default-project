## 二、★ 问题 A（真 bug，必须修）：`SubWavesPlanned` 只在 `BeforeCombatStart` 里赋值

### 现象

```csharp
public override Task BeforeCombatStart()
{
    SubWavesPlanned = WaveTable.All.Length;   // ← 唯一赋值点
    SubWavesSpawned = 0;
    ...
}
```

### 根因（已反编译实证）

`BeforeCombatStart` **只在 `CombatManager.StartCombatInternal()` 里被调用**（sts2.dll 第 600 行）：

```csharp
public async Task StartCombatInternal(CombatTurnState turnState)
{
    ...
    await Hook.BeforeCombatStart(turnState.State.RunState, turnState.State);   // 仅此处
```

而**读档恢复战斗不走 `StartCombatInternal`**——它是从存档直接重建 `CombatTurnState` 的。所以：

- 读档后 `BeforeCombatStart` **不重跑**
- `SubWavesPlanned` 只能是存档里那个旧值
- 而 `SubWavesPlanned` 是 `[SavedProperty]`，**在遗物刚获得、还没进任何战斗时**，它的值是 **`int` 默认值 0**

### 后果链

```
玩家进房间前存档（或遗物刚拿到）→ 读档 → 进房间开战
  → BeforeCombatStart 不跑（因为不是 StartCombatInternal 路径）
  → SubWavesPlanned = 0
  → ShouldStopCombatFromEnding() => 0 < 0 = false   ← 锁2 失效！
  → ShouldProceedToNextMapPoint() => 0 < 0 = false  ← 锁1 也失效！
  → 本体怪一死，战斗直接结算，14 波永远不来
```

**这正是 wb 在 M1.5 审查里提的「问题 A」**，M1.5 修复时改了锁2 的**公式**，但没改**初始化时机**，所以问题原封不动留下了。

> 注意：ZCode 在 M1.5 修复回执里说「读档安全性已解决」——**只解决了「开战后存档」这一半**。
> 开战后存档 → `Planned=14` 已落盘 → 读档正常。
> **进房间前存档 / 遗物刚获得 → `Planned=0` → 失效。** 这是漏掉的那一半。

### 修法（惰性兜底，wb M1.5 审查里给过的同一招）

在**每回合都会跑**的钩子里兜底。`BeforeSideTurnStart` 就是现成的：

```csharp
public override async Task BeforeSideTurnStart(
    PlayerChoiceContext choiceContext, CombatSide side,
    IReadOnlyList<Creature> participants, ICombatState combatState)
{
    if (Owner?.Creature == null || !participants.Contains(Owner.Creature)) return;
    if (Owner.PlayerCombatState == null) return;

    // ★ 惰性兜底：读档路径不跑 BeforeCombatStart，这里补齐（幂等，正常开局时已是 14）
    if (SubWavesPlanned <= 0) SubWavesPlanned = WaveTable.All.Length;

    if (combatState.HittableEnemies.Count > 0 || SubWavesSpawned >= SubWavesPlanned) return;
    ...
}
```

**为什么这样安全**：
- 正常开局：`BeforeCombatStart` 已赋 14，兜底条件 `<= 0` 不成立，无副作用
- 读档：兜底补上 14，锁1/锁2 立即恢复
- 幂等：写多次也不会错

**备选**（更狠但更重）：把 `SubWavesPlanned` 干脆删掉，改成**计算属性**不落盘：
```csharp
private int SubWavesPlanned => WaveTable.All.Length;   // 表长度是编译期常量，根本不用存
```
表长度是静态常量，**没有理由进存档**。这样连兜底都不需要，读档天然正确。
建议 ZCode 二选一——**推荐这一版**，更彻底。

## 三、建议 1（可优化）：官方自带挑空槽位方法 `EncounterModel.GetNextSlot`

ZCode 手写的 `PickFreeSlots` 能跑，但 sts2.dll 里**官方有现成的**：

```csharp
public string GetNextSlot(ICombatState combatState)
{
    return Slots.FirstOrDefault(s => combatState.Enemies.All(c => c.SlotName != s), string.Empty);
}
```

**差别**：
- 官方：返回 `string`，找不到空位返回 `string.Empty`（**空串**，不是 null）
- ZCode：返回 `List<string?>`，找不到补 `null`

两者行为关键区别在**"找不到空位"**时：官方给 `""`，ZCode 给 `null`。而 wb 在《波次系统API备忘》里记过——`SortEnemiesBySlotName` 用 `Slots.IndexOf(SlotName)` 排序，**`null` 返回 -1 排最前，`""` 也排最前**，两者都会导致位置错乱。所以真要"宁可叠不崩"的话两者半斤八两。

**但 ZCode 的版本有一个实际优势**：它能**一次挑完 N 个**（先 `taken` 快照，再循环挑），而官方 `GetNextSlot` 是**一次只挑一个**，连调 N 次时因为怪还没实际落位，`Enemies` 没更新，**会挑到同一个槽位**——ZCode 的 `taken` 快照恰好避开了这个坑。

**结论**：ZCode 的 `PickFreeSlots` 写法**比我原本想推荐的官方方法更对**。保留。这条从「问题」降级为「说明」——**不是 bug，是 ZCode 想得比官方 API 更周到**，记一笔。

## 四、M2.5 缺口（不是 bug，是已知待办）

ZCode 在 `WaveTable.cs` 注释里自己写了：「v1 不动怪属性（强化接口未验证），精英/Boss 波靠数量与最硬的怪堆出来」。

**这个自述属实，但有个实际隐患**：14 波里第 4、8、12 波标了「精英」、第 14 波标了「BOSS」，如果只是数量堆（4 只普通怪），**玩家在前 3 波已经打过同样的怪**，精英波和 Boss 波会「没有压迫感」——玩家会觉得"这不还是那几只吗"。

**这不是 M2 v1 的错**（强化接口没验证，不碰是对的），但 M2.5 排期时，**「反编译怪属性强化接口」应该排在最前面**，优先级高于「波次预告面板」。理由：预告面板是锦上添花，强化接口是「精英/Boss 波成立与否」的地基。

**给 M2.5 的第一个具体任务**：反编译 `MonsterModel` 有哪些可写的数值/能力（HP、伤害、`Power` 挂载），这就是 wb 的活，先挖出来放 `notes/`。

## 五、确认无误的部分（逐条实证）

### 5.1 `CreatureCmd.Add<T>` 签名 ✅

ZCode 的 `await CreatureCmd.Add<LeafSlimeM>(combatState, slot);` —— **完全匹配**。

### 5.2 间隙发牌 ✅

```csharp
public static IEnumerable<CardModel> GetDistinctForCombat(Player player, IEnumerable<CardModel> cards, int count, Rng rng)
public static async Task<IReadOnlyList<CardPileAddResult>> AddGeneratedCardsToCombat(
    IEnumerable<CardModel> cards, PileType newPileType, Player? creator, CardPilePosition position = CardPilePosition.Bottom)
```

ZCode 的：
```csharp
CardFactory.GetDistinctForCombat(Owner, pool, 1, Owner.RunState.Rng.CombatCardGeneration)
```

**参数、顺序、类型全对。** 且 `AddGeneratedCardsToCombat` 内有 `if (!CombatManager.Instance.IsInProgress) return;` 守卫——真到锁2 放行后调用也不会崩。

### 5.3 `HittableEnemies` 作清场判据 ✅

文档原话：「A hittable creature is alive and can be "hit" by effects」。
`combatState.HittableEnemies.Count > 0` 判断"场上还有能打的" —— **语义正确**。

### 5.4 `participants.Contains(Owner.Creature)` ✅

`BeforeSideTurnStart` 文档原话：
> Creatures participating in this turn. If a player is taking an extra turn in multiplayer, other players may be missing from this list, and the models they own should usually exit early in this case.

→ **守卫正确且必要**，且"exit early"正是 ZCode 的 `return`。

### 5.5 波次推进不看 `TurnNumber` ✅

ZCode 的推进逻辑是「清场（`HittableEnemies.Count == 0`）→ 下一波」，**完全不看回合数**。
这正是 wb 在《凛冬尖塔-M2波次机制备忘》里推的正解（④ 别依赖 TurnNumber，改事件驱动）。**对齐。**
