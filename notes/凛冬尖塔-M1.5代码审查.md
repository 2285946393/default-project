## 二、⚠️ 发现一个真问题：读档后「锁2」会失效

### 问题

`_nextSubWavePending` 是 **`private bool`，没有 `[SavedProperty]`**（代码注释也写明"纯战斗内状态，不进存档"）。

结合 `WavesSpawned` 是**有** `[SavedProperty]` 的，会产生这个组合：

**场景：A 波刷完（第 2 回合）后，玩家存档退出 → 重新读档**

1. 读档 → `BeforeCombatStart()` **不会重跑**（战斗已经开始了）→ `_nextSubWavePending` 保持**默认值 `false`**
2. `WavesSpawned` 从存档恢复 = 1
3. 玩家清掉本体怪 + A 波 → **`ShouldStopCombatFromEnding()` 返回 false → 战斗直接结算**
4. **B 波永远不来了**，验证流程断掉

### 为什么这个风险是真实的

- `BeforeCombatStart` 是否在"读档恢复战斗"时触发，**取决于本体实现**（存档恢复可能走的是 `FinishedCombat` 或静默重建路径，不一定重跑所有 start 钩子）。
- 就算重跑了，`_nextSubWavePending = true` 会重新武装——但那时 B 波还没刷，逻辑上勉强自洽；
  **若没重跑，就是上面那个 bug。**
- 本体的战斗存档恢复机制，注释里提到过 `CombatRoomMode.FinishedCombat`（"loading a save after combat ended"），
  说明**读档路径确实与正常开局不同**。这是一个已知会分叉的地方。

### 建议的修法（三选一，按推荐度排序）

**方案 1（推荐）：把 `_nextSubWavePending` 变成"从状态推导"，而不是"记一个布尔"**

```csharp
// 不存布尔，直接从"已经刷了几波"推出来。
// 波次表没走完 + 战斗还在进行 → 扣住战斗。
public override bool ShouldStopCombatFromEnding()
    => WavesSpawned < TotalSubWavesInThisCombat;   // 例：M1.5 是 2 波
```

优点：**天然抗读档**（`WavesSpawned` 已经进存档了），且不需要 `BeforeCombatStart` 的提前武装。
缺点：需要知道"本场战斗总共几波"（M1.5 硬编码 2 即可；M2 从波次表算）。

**方案 2：给 `_nextSubWavePending` 加 `[SavedProperty]`**

优点：改动最小。
缺点：多一个存档字段；且 `BeforeCombatStart` 若在读档时不跑，字段虽恢复但**值是存档那一刻的**，
需确认语义正确。

**方案 3（兜底）：在 `BeforeSideTurnStart` 里也兜一层**

```csharp
// 每次回合开始都校正一次，防止读档后状态不同步。
if (pcs.TurnNumber >= 2 && WavesSpawned < 2) _nextSubWavePending = true;
```

优点：不需要动存档。
缺点：**治标**，逻辑上有点绕（为什么"回合数≥2 且波数不够"就等于"还有波"？）。

→ **建议方案 1**。它在 M2 里也会更自然：波次表本来就该有"总共几波"这个数据，
`ShouldStopCombatFromEnding` 直接对比"已刷波数 vs 总波数"，**没有任何额外状态需要维护**。

## 三、两个小建议

### 建议 1 · `SpawnOnFreeSlot` 每次只挑"第一个空槽"，多波会重复占位

```csharp
foreach (var s in slots)
    if (!taken.Contains(s)) { slot = s; break; }   // 每次从 slots[0] 开始找
```

单次调用没问题（每次都重新扫 `combatState.Enemies` 的已占槽位），**逻辑是对的**。
但注意：`taken` 只统计了**当前还在场上的敌人**。如果 A 波的怪**已被打死**，
它的槽位名会从 `taken` 里消失，B 波就会**复用同一个槽位**。

- M1.5 无所谓（A 波死了 B 波才来，复用槽位反而对）。
- **M2 要注意**：若同一波里同时存在多只怪、且有怪中途死亡，可能出现"位置跳变"。
  → 到时候考虑用"本场战斗已分配过的槽位集合"而不是"当前在场的槽位"。

### 建议 2 · `Encounter?.Slots` 在自定义遭遇下可能为空

`SpawnOnFreeSlot` 依赖 `combatState.Encounter?.Slots`。若本场遭遇（如本体某个遭遇）
`Slots` 返回空数组（基类默认 `Array.Empty<string>()`），则 `slot` 恒为 `null` → 退回默认站位。

- M1.5 没问题（叠怪降级是设计好的）。
- **M2 做自定义遭遇时，记得自己在 `Slots` 里把 5 个槽位名写全**，否则波次怪还是会叠。
  → 这与 `notes/凛冬尖塔-波次系统API备忘.md` 第四节给的模板一致（`new[] { "l2","l1","c","r1","r2" }`）。

[SavedProperty] public int SubWavesSpawned { get; set; }   // 每放一波 +1

## 三、⚠️ 我又发现两个新的边界问题（要不要修由 ZCode 定）

### 问题 A（本次修复引入的回归风险）：`BeforeCombatStart` 不重跑时 `SubWavesPlanned` 可能为 0

`SubWavesPlanned = 2` 只在 `BeforeCombatStart()` 里设置。而**这次的修复恰恰建立在"读档时 `BeforeCombatStart` 不重跑"这个前提上**——
那就会出现：

**场景：玩家在"还没打过任何一场凛冬战斗"的状态存档 → 读档 → 进第一场战斗**

- 若 `BeforeCombatStart` 在**新战斗开始时正常触发** → 没问题（`Planned=2, Spawned=0`）。✅
- 若某些读到战斗中途的路径**不触发**它 → `Planned` 保持默认 **0**，`Spawned` 也是 0
  → `0 < 0` = false → **锁2 失效，本体怪清完就直接结算**（老 bug 复发）

**换句话说**：这次修复把"锁2 的状态"从内存布尔挪到了存档计数器，方向对；
但 **`SubWavesPlanned` 的赋值时机仍然只在 `BeforeCombatStart` 里**，没有真正摆脱"该钩子是否重跑"的依赖。

**建议**（其实是同一个思路再推一步）：**别让它依赖任何"开始钩子"**——
把"本场计划几波"变成**纯函数**，或就地兜底：

```csharp
public override bool ShouldStopCombatFromEnding()
{
    // 兜底：万一 BeforeCombatStart 没跑（读档路径），本场计划值仍是 0，就地补上。
    if (SubWavesPlanned == 0) SubWavesPlanned = 2;   // M1.5 固定；M2 从波次表算
    return SubWavesSpawned < SubWavesPlanned;
}
```

但**注意**：`SubWavesPlanned` 是 `[SavedProperty]`，在这里写它要确认该模型此刻是 mutable 的
（`AssertMutable` 会拦只读模型）。**更保险的做法是不在谓词里改状态**，
改成在 `BeforeSideTurnStart`（每回合都跑，不是只在开战跑）里做一次 `if (SubWavesPlanned == 0) SubWavesPlanned = 2;`。

→ **这条在 M1.5 现实中的触发概率不高**（正常流程 `BeforeCombatStart` 会跑），
**但 M2 做波次表时必须解决**，因为那时"本场几波"是算出来的、更需要明确的初始化时机。

### 问题 B（仍然存在，M2 必修）：`SubWavesSpawned` 的回合条件依赖 `TurnNumber`

```csharp
if (pcs.TurnNumber == 2 && SubWavesSpawned < 1) { ... A 波 ... }
else if (pcs.TurnNumber >= 3 && SubWavesSpawned < 2) { ... B 波 ... }
```

`SubWavesSpawned < N` 这半边已经抗读档了 ✅，但**前面的 `TurnNumber` 判断仍然把它绑在回合号上**：

**场景**：A 波刷出后（第 2 回合）存档 → 读档回到**同一场战斗的第 2 回合**
→ `SubWavesSpawned` 从存档恢复 = 1 → `== 2 && 1 < 1` = false → A 波不重刷 ✅（正确，不重复刷）
→ 但接着打到第 3 回合 → `>= 3 && 1 < 2` = true → B 波照常出 ✅（正确）

**看起来是对的**。但换个场景：**A 波还没刷的时候就存档（第 1 回合）→ 读档**
→ 若读档后 `TurnNumber` 从 1 继续 → 第 2 回合刷 A 波 ✅。
→ 若读档时 `TurnNumber` 跳到 3（比如本体恢复逻辑导致）→ `>= 3 && 0 < 2` = true
→ **B 波会先于 A 波刷出，且 `SubWavesSpawned` 直接跳到 2 → A 波永远不来**。

→ **M2 正经解法**：波次推进不该绑 `TurnNumber`，应该是
"**当前波清空 → 推进到下一波**"这种**事件驱动**（监听敌人清空/回合结束），
`TurnNumber` 只作为参考。这样读档、跳回合都不会乱。
