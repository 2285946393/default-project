## 一、为什么是这一批（用户原话）

> 「自己多加些凛冬牌。要有创意。比如那我方场上被摧毁，对所有敌人造成一次伤害。这种效果牌。
>  你不会动脑子直接改成如果我的牌被消耗。对所有敌人造成一次伤害吗。
>  把凛冬里面要触发效果的牌换成我们这边要触发效果的牌。诸如此类还要我多说吗」

**开工前盘出来的真实缺口**：M3.8 结束时凛冬卡池 16 张，**一张触发式都没有** —— 全是「打出即生效」。
《凛冬前线》的卡之所以好玩，一大半来自「某件事发生时才生效」。这是当时最大的短板。

用户点名的两个范式：
1. **我方随从被摧毁 → 对全体敌人造成一次伤害** → 做了 `LastFrostPower`（遗霜）
2. **我的牌被消耗 → 对全体敌人造成一次伤害** → 做了 `AvalanchePower`（雪崩）

「诸如此类还要我多说吗」= 不要逐条等他列举，自己把范式铺开 → 一共铺了 **6 个不同的触发时机**。

## 二、做了什么（11 张卡 + 8 个能力）

| 卡 | 费 | 稀有 | 触发时机（全部是**我方侧**事件） | 效果 |
|---|---|---|---|---|
| 遗霜 `LastFrostCard` | 1 | Common | 我方随从被摧毁 | 全体敌人 **6×层数** |
| 霜之遗赠 `FrostLegacyCard` | 1 | Common | 我方随从被摧毁 | 获得 **8×层数** 格挡 |
| 霜葬 `FrostBurialCard` | 0 | Uncommon | （主动）摧毁最弱随从 | 全体 14，**消耗** |
| 雪崩 `AvalancheCard` | 1 | Common | 我的牌被消耗 | 全体 **5×层数** |
| 余烬 `WinterEmberCard` | 1 | Uncommon | 我的牌被消耗 | 抽 **1×层数** 张 |
| 霜燃 `FrostBrandCard` | 1 | Common | （消耗源）抽 2 张 | **消耗** |
| 冰棱 `IceShardCard` | 0 | Common | （消耗源）7 点伤害，是**攻击牌** | **消耗** |
| 凛冬之怒 `WinterWrathCard` | 2 | Rare | 我方随从受到伤害 | 全体 **3×层数** |
| 碎冰 `IceShatterCard` | 1 | Uncommon | 敌人的格挡被打破 | 对该敌人 **8×层数** |
| 寒风 `ColdWindCard` | 1 | Common | 我弃一张牌 | 全体 **2×层数** |
| 霜之回响 `FrostEchoCard` | 2 | Rare | 我打出一张攻击牌 | 全体 **3×层数** |

能力全部 `StackType.Counter` → 重复打出叠层变强（延续 M3.7「重复部署 = 强化」的手感）。

### 三条自洽的构筑线（不是 11 张散牌）

- **殉爆线**：遗霜 / 霜之遗赠（被动）+ 霜葬（主动扳机）
  → 霜葬先 `Kill`（正常走死亡流程 → 遗霜同时触发）再结算 14 点 ⇒ **0 费 20 点全体爆发**
- **消耗线**：雪崩（输出）+ 余烬（续航）+ 霜燃 / 冰棱（发动机）
- **增幅线**：霜之回响（攻击牌放大）+ 寒风（弃牌）+ 碎冰（破甲）+ 凛冬之怒（挨打反击）

### ★★ 这一批最重要的自我约束：**消耗线必须有发动机**

开工前盘过整个凛冬卡池 —— **一张带 `Exhaust` 关键字的牌都没有**。
如果不补「霜燃 / 冰棱」，玩家打出雪崩后会看到一句**永远不兑现的描述**（死牌）。

⇒ 「霜燃 / 冰棱」不是装饰，是消耗流的发动机：
- 霜燃 = 1 费抽 2，挂余烬后净抽 1 张，同时喂雪崩
- 冰棱 = 0 费 7 伤，且是**攻击牌** → 一次点火同时喂雪崩 + 霜之回响

**教训**：做任何「触发式」卡之前，先数一遍**这个触发点在当前卡池里能不能真的发生**。
触发条件存在 ≠ 玩家能触发。

### 数值平衡口径（承接 M3.7 用户实测「第三波就死」的教训：先算再写）

- 低频高价值触发（随从死亡、破甲）→ 单次给足（6 / 8）
- 高频触发（挨打、弃牌、打攻击牌）→ 单次压低（3 / 2 / 3）
  - 尤其「寒风」：`AfterCardDiscarded` **包含回合结束自动弃手牌**，
    5 张手牌 = 10 点全体，所以压到 2/张
- 消耗线（雪崩 5）取中间值：消耗本身要付资源，值得中等回报

## 三、反编译取证（本批全部 API 都不是猜的）

### 1. 钩子从哪来 —— `PowerModel.ShouldReceiveCombatHooks`

`MegaCrit.Sts2.Core.Models.PowerModel` 第 422 行：

```csharp
public override bool ShouldReceiveCombatHooks => true;
```

⇒ Power **一定会收到战斗钩子**，只要覆写 `AbstractModel` 上的同名虚方法即可。

### 2. 完整签名（ilspycmd 反编译 `MegaCrit.Sts2.Core.Models.AbstractModel`）

```csharp
Task AfterDeath(PlayerChoiceContext, Creature, bool wasRemovalPrevented, float deathAnimLength)
Task AfterCardExhausted(PlayerChoiceContext, CardModel, bool causedByEthereal)
Task AfterCardDiscarded(PlayerChoiceContext, CardModel)
Task AfterCardPlayed(PlayerChoiceContext, CardPlay)
Task AfterDamageReceived(PlayerChoiceContext, Creature, DamageResult, ValueProp, Creature?, CardModel?)
Task AfterBlockBroken(PlayerChoiceContext, Creature target, Creature? breaker)
Task BeforeDeath(Creature)
Task BeforeSideTurnStart(PlayerChoiceContext, CombatSide, IReadOnlyList<Creature>, ICombatState)
Task AfterSideTurnEnd(PlayerChoiceContext, CombatSide, IEnumerable<Creature>)
... （AfterCardDrawn / AfterEnergySpent / AfterCardChangedPiles / AfterHandEmptied 等共 40+ 个）
```

★ 类型全名是 `MegaCrit.Sts2.Core.Models.AbstractModel`（不是 `Sts2.Models.AbstractModel`）。

### 3. 决定性证据：挂在**玩家**身上的能力，能不能监听到**随从**的死亡？

`Hook.AfterDeath` 的实现：

```csharp
foreach (AbstractModel model in runState.IterateHookListeners(combatState))
    await model.AfterDeath(...);
```

`RunState.IterateHookListeners` 只 yield 牌库卡 / 遗物 / 药水 / modifiers，
**但有 `childCombatState.IterateHookListeners()` 这一段**。追进去：

```csharp
for (int i = 0; i < combatState._allies.Count + combatState._enemies.Count; i++)
{
    Creature creature = ...;
    list.AddRange(creature.Powers);      // ← ★ 所有生物（玩家 + 随从 + 敌人）的 Powers 全在监听列表里
    ...
}
```

⇒ **挂在玩家身上的 `LastFrostPower` 一定会被 `AfterDeath` 通知**。机制成立，不是赌。

### 4. `CreatureCmd.Kill` 真的会走死亡钩子吗（霜葬 ⇄ 遗霜 的核心 combo）

`CreatureCmd.Kill(creature)` → `Kill(collection)` → `KillWithoutCheckingWinCondition`，
其中第 552 行：

```csharp
await Hook.AfterDeath(runState, combatState, creature, wasRemovalPrevented: false, deathAnimLength);
```

⇒ **会**。而且 `wasRemovalPrevented: false`，我们 `if (wasRemovalPrevented) return;` 的守卫不会误挡。
⇒ 霜葬 → 遗霜 的 combo 静态可证。

### 5. 其它核实到的 API

- `CreatureCmd.Kill(Creature, bool force = false)` —— 摧毁我方随从用这个
- `CardKeyword` 枚举：`None / Exhaust / Ethereal / Innate / Unplayable / Retain / Sly / Eternal`
  → 让牌消耗：`public override IEnumerable<CardKeyword> CanonicalKeywords => new[] { CardKeyword.Exhaust };`
  ★ **是 `public` 虚成员**（`CanonicalVars` 才是 `protected`），写成 `protected` 会报 CS0507（踩过）
- `Creature.IsPet => PetOwner != null` —— 玩家本体的 `PetOwner == null`，
  所以 `IsPet` 恰好能把「玩家本体」和「我方随从」区分开，无需额外判断
- `Creature.Side`（CombatSide）—— 判敌我用 Side，**不要用 `IsMonster`**（我方随从也是 MonsterModel）
- `CardPlay`：`Card` / `Player` / `Target` / `ResultPile` / `Resources` / `IsAutoPlay` / `PlayIndex` / `PlayCount`

## 四、三个必须防的坑（写在代码注释里了）

1. **钩子是全局的**（敌人死、队友的牌消耗都会调进来）→ 每张都必须自己过滤阵营/归属，
   否则会出现「敌人死了给我方发伤害」「联机时别人打牌我触发」。
   基类里统一提供 `IsMyMinion` / `IsMyCard` / `IsEnemy` 三个判定。
2. **`AfterDeath` 里 creature 可能已从 `Pets` 移除** → 不能用 `Pets.Contains(creature)` 判阵营，
   必须靠 `IsPet` + `PetOwner`。
3. **伤害来源用 `ValueProp.Unpowered`**：这是「反应」，不该吃力量加成
   （和 M3.1 起的 `ArrowTowerPower` / `MilitiaAttackPower` 保持一致）。
