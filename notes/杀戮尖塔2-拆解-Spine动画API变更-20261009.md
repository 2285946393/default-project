# 拆解 · 游戏改过一个 Spine 动画 API，把一批 mod 打断了

> 2026-10-09 · 国际台（只读侦查）
> 触发：日志里反复出现
> `System.MissingMethodException: Method not found: 'MegaCrit.Sts2.Core.Bindings.MegaSpine.MegaTrackEntry MegaCrit.Sts2.Core.Bindings.MegaSpine.MegaAnimationState.SetAnimation(System.String, Boolean, Int32)'`
>
> 我写了个工具把**全机 306 个 mod dll** 的 IL 扫了一遍，把「谁在调这个不存在的签名」精确列了出来。

---

## 一、结论一句话

游戏把 `MegaAnimationState.SetAnimation(string, bool, int)` 的**返回值从 `MegaTrackEntry` 改成了 `void`**。
编译在旧版本上的 mod，调用点会在运行时抛 `MissingMethodException` ——
**动画静默失效**（游戏不会崩，只在控制台打一行 ERROR）。

**变更发生在 0.107.1 与 0.109.0 之间。**

---

## 二、证据

### 2.1 游戏本体现在的签名（`data_sts2_windows_x86_64/sts2.dll`）

```
### public class MegaCrit.Sts2.Core.Bindings.MegaSpine.MegaAnimationState
    method public void          SetAnimation(string animationName, bool loop, int trackId)      ← 返回 void
    method public MegaTrackEntry AddAnimationTracked(string animationName, float delay, bool loop, int trackId)
    method public void          AddAnimation(string animationName, float delay, bool loop, int trackId)
    method public MegaTrackEntry GetCurrent(int trackIndex)
```

→ 想拿 `MegaTrackEntry`，**新的正确写法是 `AddAnimationTracked(...)`**，不是 `SetAnimation(...)`。

### 2.2 RitsuLib 的多版本变体直接给这个变更「定了日期」

RitsuLib 用 `compat/<游戏版本>/STS2-RitsuLib.Runtime.dll` 分发多份实现。看它各版本期望的签名：

| RitsuLib 变体 | 它期望的 `SetAnimation` 返回值 |
|---|---|
| `compat/0.107.1/` | **`MegaTrackEntry`**（旧） |
| `compat/0.109.0/` | `void`（新） |
| `compat/0.110.0/` | `void`（新） |
| `compat/0.111.0/` | `void`（新） |

**→ 断点在 0.107.1 → 0.109.0 之间。** 这正是它要维护四个 compat 目录的原因。

### 2.3 还有第二个类型也有同名方法

```
### public struct MegaCrit.Sts2.Core.Bindings.MegaSpine.SpineAnimationAccess
    method public void SetAnimation(string name, bool loop, int track)
    method public void AddAnimation(string name, float delay, bool loop, int track)
    method public MegaTrackEntry GetCurrentTrack(int track)
    method public MegaAnimationState GetAnimationState()
```

`SpineAnimationAccess` 是包着 `MegaSprite` 的**值类型门面**，`SetAnimation` 同样是 `void`。
游戏自己也在用（`sts2.dll` 里 ~90 处 `void SetAnimation` 调用，包括 `SpineAnimationAccess::SetAnimation` 自己）。

## 四、★ 社区已经写了 **4 套** 兼容层（最值得抄的模式）

同一个坑，四个作者各自做了「包一层」的兼容函数：

| 兼容层 | 出自 | 签名 |
|---|---|---|
| `ChaosMod.XCskinSpineCompat.SetAnimation` | `Chaos_XC_defect01`（3748174613） | `MegaTrackEntry (object, string, bool, int)` |
| `Spirectl.Sts2.Live.GameApi.GameApiSpine.SetAnimation` | CouchCoop（`Spirectl`） | `MegaTrackEntry (MegaAnimationState, string, bool, int)` |
| `CznCore.Presentation.SpineAnimationCompat.SetAnimation` | ChizuruIroncladSkin / TressaSilentSkin | `void (MegaAnimationState / SpineAnimationAccess, string, bool, int)` |
| `Sts2Compat.Visuals.MegaSpineCompat.SetAnimation` | Kafka / shadowverse 系 | `void (MegaAnimationState, string, bool, int)` |

**共同思路**：调用方只认自己的 `XxxCompat.SetAnimation(...)`，
兼容层内部按**当前游戏版本**决定是「直接调」还是「调完再补一个 `GetCurrent(track)` 拿 track entry」。

> **可复用结论**：游戏 API 一旦破坏性变更，正确做法**不是**在每个调用点加版本判断，
> 而是**收口到一个 compat 类型里**，让调用点看不见版本差异。
> RitsuLib 用 `compat/<版本>/` 整套 dll 来做同一件事（更重，但连框架内部都能切）。

## 五、对我们自己 4 个 mod 的结论

|---|---|

## 六、工具：`MemberRefScan`（新写的，以后排同类问题直接用它）

`projects/sts2-moddev-workspace/04-工具/查询工具源码/MemberRefScan/`

**作用**：跨程序集扫「谁在调用某个方法/字段」。
游戏报 `MissingMethodException` / `MissingFieldException` 时，日志**只告诉你签名不存在，不告诉你是谁在调**；
这个工具扫一堆 dll 的 IL，把调用方精确指出来（dll / 类型 / 方法 / `call` 还是 `callvirt`）。

```bash
# 编译
cd "projects/sts2-moddev-workspace/04-工具/查询工具源码/MemberRefScan"
dotnet build -c Release

# 扫工坊全部 mod，找 SetAnimation 的调用点
bin/Release/net9.0/MemberRefScan.exe \
  "D:/software/steam/steamapps/workshop/content/2868840" \
  out.txt SetAnimation

# 只找某个声明类型上的
... out.txt SetAnimation MegaAnimationState
```

- 用 **Mono.Cecil** 读 IL，**不加载、不执行** mod 代码（安全）。
- 原生 dll（`onnxruntime.dll` 之类）读不了会跳过并列出来。
- 输出按**成员签名分组**，每组列出所有调用点 —— 一眼能看出「旧签名 vs 新签名 vs 兼容层」。
- 顺带能扫出**同名但不同签名的东西**（这次就是靠它发现生态里有 4 套兼容层）。

## 八、顺带发现：CombatSolver 会快照「mod 加载顺序」

`Slay the Spire 2/.combatsolver-precombat/process-<pid>/startup-mods/`
里有 **84 个带序号的目录**（`00_MemeSpire` … `83_voicemod`）。

- 这是 **CombatSolver（战斗路线求解器）** 在开战前把当前 mod 集合**按加载顺序**复制的一份快照，
  用来复现对局（目录里有个 `.combatsolver-precombat-owner` 标记文件）。
- **副作用：这是一份免费的「权威加载顺序表」。** 排查「谁在谁前面加载」「内容排序为什么不同」时，
  不用猜 —— 直接看这个目录。
- 序号里能看到框架的位置：`34_STS2-RitsuLib` … `51_BaseLib` … `42_CombatSolver`。
  ⚠️ **`BaseLib` 排在 `RitsuLib` 后面 17 位**，而我们自己的 mod 在 `68_QuestSpire` / `69_FrostSpire` / `70_DouSpire`。
- ⚠️ 注意这个目录是**会长的**：每次开战都可能新建一个 `process-<pid>/`（本次机器上 `process-10300` 是空的、`process-30500` 有效）。
