# 卡 1 · 极光流体（WebGL 实时流体）

**一句话定位**：纯 WebGL 手写 shader 的实时流体模拟，单文件 23KB、零第三方库。

## 背景 / 目标
想做一个"能玩"的图形作品，验证自己对 **GPU 渲染管线 + 数值方法** 的理解。目标：鼠标搅动出真实的流体感，且稳定 60fps。

## 方案选型与对比
| 方案 | 结论 |
|---|---|
| Canvas 2D | 逐像素在 CPU 上算，192×192 就掉帧，放弃 |
| **WebGL（选用）** | 每个像素在 GPU 并行，片元着色器天然适合网格计算 |
| WebGPU | 更强（compute shader），但当时浏览器兼容性不够 |
| WebGL2 | 原生支持浮点纹理；但 **WebGL1 兼容性更广**，用 `OES_texture_half_float` 扩展补上 |

## 落地细节（能讲这些就够深了）
1. **FBO 双缓冲（ping-pong）**：GPU 不能在同一 pass 里同时读写同一纹理，所以速度场 / 压力场 / 染料场都是"一读一写两块纹理"，每步 `swap()`。
2. **半浮点纹理**：用 `OES_texture_half_float`，精度够、显存/带宽省一半。
3. **双分辨率（性能关键）**：求解器跑在 **192**（速度/压力），染料只负责好看，跑在 **1024**。
4. **Stable Fluids 全流程**（每一步都是一个 fragment shader）：
   `curl（算涡量）→ vorticity confinement（涡量补偿）→ divergence（算散度）→ 压力场 Jacobi 迭代 24 次 → gradient subtract（投影成无散度速度）→ 半拉格朗日 advect（速度+染料）`
5. **splat**：`exp(-dot(p,p)/radius)` 高斯核，鼠标位移差当速度、调色板取色当染料。
6. **稳定性**：`dt` 上限 clamp 到 0.0166；`vel` 夹到 ±1000；设备像素比上限 2。
7. **显示层**：`pow(color, 0.82)` 提亮、暗角、`fract(sin(...))` 抖动去色带。
8. **无障碍**：`prefers-reduced-motion` 关掉自动撒点、`prefers-reduced-transparency` 关毛玻璃。

## 收益 / 数据
单文件 23KB、零依赖、192 网格下稳定 60fps、支持鼠标 + 多点触控。

## 高频追问 & 参考答案
- **为什么要 vorticity confinement？** 数值方法（尤其半拉格朗日）会耗散掉小尺度涡旋，画面变"糊"。它算出场里的涡量，加一个把它往回推的力，重新注入能量 → 极光更"活"。
- **为什么用 Jacobi 迭代而不是直接解压力泊松方程？** GPU 适合"每个像素做同样的简单计算"，迭代法天然并行；24 次在视觉上已收敛。
- **半拉格朗日为什么稳定？** 它是沿速度场**回溯采样**，无条件稳定；代价是数值耗散（所以才有 vorticity confinement 补）。
- **怎么保证 60fps？** 分辨率分层 + dt clamp + DPR 上限 + 关掉 antialias/depth/stencil。
- **如果数据量（分辨率）涨 10 倍还成立吗？** 不行，192→1920 计算量涨 100 倍。届时要上 WebGPU compute 或降到更低精度/多级网格。

## 如果重来
WebGPU + compute shader 做压力迭代；把物理计算搬 Rust/WASM；加移动端自动降分辨率。

## ⚠️ 如实说明
- 是**我手写的 GLSL 与 JS 管线**，但算法源自经典的 **Stable Fluids（Jos Stam）**——大方承认，这是行业常识。
- 不要吹"我推导了 Navier-Stokes"，说"我实现了它的离散化/迭代求解"。

# 卡 2 · 深渊塔（15 层爬塔 Roguelike）

**一句话定位**：单文件、数据驱动的 15 层爬塔 roguelike，3 种进攻策略 + 随机事件 + 双结局。

## 背景 / 目标
想做一个"有叙事、有策略、有随机"的**完整**小游戏，而不只是一个 demo。

## 方案选型与对比
- **为什么用 DOM 而不是 Canvas 渲染？** 这个游戏 90% 是文本 / 卡片 / 按钮（对话、英雄卡、事件选项）。DOM 开发快、天然可访问、易维护，性能完全不是瓶颈。Canvas 反而要手写文本排版和点击命中。
- **数据驱动**：英雄 / 区域 / Boss / 策略 / 事件全部是配置数组，逻辑与数据分离。

## 落地细节
1. **单一 `state` 对象 + 全量 `renderAll()`**：状态改了就把整个界面重渲染一遍。规模小（<50 个节点），简单可靠。
2. **战斗公式**（`doDispatch`）：
   `heroPower = atk*2 + def + spd + 策略加成 + rand*14`
   `enemyPower = atk*2 + def + spd + rand*8`
   比大小定胜负；伤害再按策略的 `defDmg` 系数和胜负修正，最低 1 点。
3. **难度曲线**：敌人属性随层数线性缩放（`40+floor*10` 等），每 5 层一个 Boss（属性更高、奖励更好）。
4. **背景随深度变色**：`hue` 从 258 线性插值到 4（紫 → 红），层数越深越"烫"。
5. **事件系统**：每个事件带 `choices[]`，每个选项一个声明式 `effect`（加金 / 回血 / 加好感 / 陷阱判定），`resolveEvent` 统一结算。
6. **打字机对话**：`typeText` 用 `setTimeout` 逐字吐，带光标闪烁。
7. **时间回溯**：消耗"沙漏"回到第 1 层（保留英雄与金币），给玩家容错。

## 收益 / 数据
15 层、5 个英雄、3 种策略、5 类随机事件、3 个 Boss、2 种结局；单文件 40KB。

## 高频追问 & 参考答案
- **全量重渲染有性能问题吗？** 当前规模没有；若节点上千，要改成增量更新或引入 diff（如虚拟 DOM 思路）。
- **数值怎么平衡的？** 战力公式给"攻击"最高权重（×2），再叠随机区间和策略系数，避免一边倒；靠反复试玩调参。
- **怎么加一个新事件？** 往 `EVENTS` 数组里加一个对象就行，`effect` 是声明式的，不用改流程代码。
- **怎么保证随机但不劝退？** 失败只掉血、不掉层；有休整回血、回溯兜底；事件收益偏正。

## 如果重来
- 加 **localStorage 存档**（现在**没有**存档，刷新即重来）；
- 把"战斗 → 结算 → 事件 → 下一层"抽成显式**状态机**，现在是用 `state.ended` 标志位 + 模态弹层拼的；
- 改成增量渲染。

## ⚠️ 如实说明
- **不要说"我写了状态机"**——现在是事件驱动 + 标志位，不是形式化 FSM。可以说"回合制流程"。
- **不要说"支持存档"**——**没有存档功能**（简历已修正）。若面试官问，坦率说"目前没做，这是我下一步要补的"。

# 卡 3 · 元素秘境（Rust / WASM 落沙沙盒）

**一句话定位**：移植改造 **sandspiel（MIT）** 的 Rust/WASM 内核，手写 wasm-bindgen 胶水层 + 原生 WebGL 渲染，76KB 单文件。

## 背景 / 目标
想学 WebAssembly：搞懂 **WASM 与 JS 的内存模型、胶水层、以及"为什么高性能计算要用 WASM"**。选落沙（sandbox）因为它规则简单、但计算量随格子数爆炸，正好能体现 WASM 的价值。

## 方案选型与对比
- **为什么用 WASM 而不是纯 JS？** 落沙是 **O(格子数) 的逐格规则计算**，每帧几十万格。Rust 编译的 WASM 在数值循环上比 JS 快，且能复用成熟的 sandspiel 内核。
- **为什么内嵌 base64？** 项目坚持"单文件、双击即玩"，不能有外部 `.wasm` 请求；代价是 base64 让体积 +33%。

## 落地细节（**这些才是"我做的"**）
1. **移植 + 加载**：内嵌 WASM 的 base64，运行时 `atob` → `WebAssembly.instantiate`，按 wasm-bindgen 约定提供 `imports`（`random`、`throw`、`externref` 初始化表）。
2. **手写胶水层**：把 WASM 导出的 `universe_new/paint/tick/cells/pushUndo/popUndo` 包成 JS 对象；`cells` 直接拿 `memory.buffer` 的 `Uint8Array` 视图。
3. **原生 WebGL 渲染**：移植 sand.glsl——内联手写 `hsv2rgb`、2D/3D simplex noise；把 cells 数组当纹理上传（首次 `texImage2D`，之后 `texSubImage2D` 增量更新）。
4. **零拷贝**：cells 的 `Uint8Array` 视图直接喂给 `texSubImage2D`，中间不复制。
5. **世界尺寸**：按窗口宽高比 + **格子预算**（桌面 220k / 移动 110k）算出 `W×H`，再等比缩放显示。
6. **软笔刷（我的优化）**：一开始用"实心圆"撒沙，结果**一整块沙同时出现、整体下坠**，很假。改成**圆内按密度逐格随机撒点**，每粒沙由 WASM 内部 rng 独立取随机数，下落抖动彼此独立 → 形成自然的沙流；固体元素（结界/黑曜岩等）仍保持实心。
7. **中文 UI**：20 种元素做成暗黑幻想命名（流沙/狱炎/噬魂蚁/复制魔印…），暂停 / 撤销 / 快捷键 / 开场沙丘动画。

## 收益 / 数据
单文件 76KB、桌面 22 万格、20 种元素、5 档笔刷；每帧 tick + 纹理上传稳定。

## 高频追问 & 参考答案
- **WASM 和 JS 怎么传数据？** 共享线性内存：`instance.exports.memory.buffer`。JS 侧建 `Uint8Array` 视图直接读写，**零拷贝**；复杂结构靠 wasm-bindgen 生成的指针/长度约定。
- **为什么笔刷不用实心圆？** 见上"软笔刷"——实心圆破坏颗粒感，逐格随机才像沙。
- **WASM 相比 JS 的收益？** 数值密集循环更快；但**不是万能的**——频繁跨边界调用、小计算量时，胶水开销会吃掉收益。
- **如果格子数涨 10 倍？** 220k→2.2M，CPU 逐格 tick 会成瓶颈；届时要上 SIMD / 多线程 WASM / 或把 tick 也搬到 GPU（compute）。
- **你的贡献是什么？**（**必问，背熟**）"内核是 **sandspiel（MIT 协议）** 的，我负责：移植与加载、手写 wasm-bindgen 胶水层、原生 WebGL 渲染、中文 UI 与 20 种元素设计、软笔刷优化、以及按设备做性能适配。"

## 如果重来
用 Vite + wasm-pack 正常工程化（分离 `.wasm` + 预加载），而不是 base64 内嵌；把渲染也拆成模块。

## ⚠️ 如实说明
- **绝对不要说"我用 Rust 从零写了内核"**——内核是 sandspiel 的。说"移植改造 + 手写胶水/渲染"。（简历已修正）
- 但**不要因此心虚**：能读懂 Rust↔JS 的 ABI、手写 glue、把 GLSL 移植过来、做性能适配，这本身就是硬功夫。

# 卡 4 · 面试间（AI 模拟面试官）⭐ 投 AI 岗先背这张

**一句话定位**：一个能真跑起来的 AI 模拟面试工具——AI 按岗位出题、逐题点评追问、结束出结构化复盘报告；在开源 UI 骨架之上**重写数据层 / AI 调用层 / 交互层**，并用自研 BM25 做中文 RAG。

> 代码位置 `projects\ai-interviewer\`；技术栈 Next.js 15（App Router）+ React 19 + TS + Tailwind 4 + Vercel AI SDK 4 + Zod。

## 背景 / 目标

自己正在秋招，需要一个能反复练面试的东西；顺便验证一件事——**能不能独立把一个 LLM 应用从 0 做到能用**（不只是调通一次 API 那种 demo）。判据是：不配 API Key 也不崩、换模型不改业务代码、能贴自己的 JD 出题。

## 方案选型与对比（**面试官最爱问这里**）

| 决策点 | 选了 | 没选 | 理由 |
|---|---|---|---|
| 数据存储 | **localStorage** | Firebase / 数据库 | 求职练习工具，注册一次就流失一批人；本地存档首次可用时间 0 秒，且天然没有隐私顾虑——简历原文不出浏览器 |
| 模型接入 | **OpenAI 兼容 SDK** | 各厂商自家 SDK | 只依赖兼容协议，换 DeepSeek / 硅基流动 / 智谱只改环境变量，业务代码零改动 |
| 语音 | **浏览器原生 Web Speech API** | Vapi（付费云语音） | 白嫖浏览器能力，中文音色可用；省掉一整个付费依赖和密钥管理 |
| 检索 | **BM25 稀疏检索** | 向量库 / embedding | 见下方专门展开 |
| 出题格式 | **Zod schema 结构化输出** | 直接解析自由文本 | 评分报告有固定 5 维度，用 schema 约束比事后正则可靠 |

## 落地细节（能讲这些就够深了）

1. **Provider 抽象层**（`lib/ai.ts`，全文 15 行）：用 `createOpenAICompatible` 建 provider，`baseURL / apiKey / model` 全部读环境变量，导出统一的 `chatModel` 和 `hasApiKey` 标志。换模型 = 改 `.env.local` 三行。
2. **自研 BM25 检索**（`lib/rag.ts`，零依赖，约 180 行）：
   - **中文 bigram 分词**：中文没有空格，又不引入分词词典，所以切成连续二字组合（"模拟面试"→ 模拟/拟面/面试）。英文数字走原样 token。
   - **标准 BM25 打分**：`k1=1.5`、`b=0.75`，IDF 用 `log(1 + (N - df + 0.5)/(df + 0.5))`，文档长度做了归一化。
   - **文档切分**：420 字一块、80 字重叠；切点优先找 `\n` / `。` / `；` 这类自然边界（且必须在窗口后半段），避免把一句话劈开。
   - **组装上下文**：topK=4，拼成带来源标注的「片段 1｜来源：xxx」，注入到出题 prompt 里，并额外加一条要求"题目要具体到材料里的项目名"。
   - **检索测试面板**：知识库页能直接看到命中了哪几段、得分多少——结果可解释，不是黑盒。
3. **检索跑在浏览器端**：只把拼好的上下文片段发给服务端，**知识库原文不上传**。零额外 API 成本，也顺手解决了隐私问题。
4. **三级降级**（每个 API route 都做了）：
   - 出题失败 → 内置题库（`ROLE_MAP` 里每个岗位预制了 `fallbackQuestions`）
   - 点评失败 → 本地模拟文案
   - 评分失败 → 本地估算（按作答覆盖率 + 平均回答长度算分）
   任何一环挂掉，用户都能把整场面试走完，**界面不白屏**。
5. **解析 LLM 输出的四级兜底**（`generate/route.ts` 的 `parseQuestions`）：先直接 `JSON.parse` → 失败就正则抠出 `[...]` 再 parse → 再失败就提取所有长度 >6 的引号串 → 最后按行拆、剥掉 `1. - *` 之类的列表符号。**因为模型不保证只吐 JSON，这层必须有。**
6. **评分用 `generateObject` + Zod**（`feedback/route.ts`）：schema 固定 `totalScore / categoryScores / strengths / areasForImprovement / finalAssessment`；prompt 里写死 5 个维度名必须完全一致（专业能力 / 表达与沟通 / 逻辑与结构 / 岗位匹配度 / 自信与应变），并要求"60 分代表达到面试及格线"，防止模型一律给高分。
7. **prompt 里禁用 markdown 符号**：因为点评会被语音朗读，`*` `#` `` ` `` 读出来很怪。这是个"AI 输出要服务于下游消费者"的细节，值得提。
8. **语音中文音色优选**（`lib/speech.ts`）：`onvoiceschanged` 异步加载音色（Chrome 首次是空的，必须监听这个事件），优先挑 Xiaoxiao / Yunxi 等中文音色，朗读前先 `cancel()` 防打断叠音。

## 收益 / 数据

- 三套内置题库（前端 / AIGC 运营 / 电子信息工程），支持贴 JD 自定义岗位
- 5 个能力维度结构化复盘 + 逐题回顾
- `tsc --noEmit` 零错误、`next build` 通过、端到端零控制台报错
- **不配 API Key 也能完整跑通全流程**（这是设计目标，不是妥协）

## 高频追问 & 参考答案

- **为什么用 BM25 不用向量检索？**（**几乎必问，背熟**）
  > "三个原因。一是**场景**：知识库是我自己的 JD、简历、面经，都是中文短文档，词汇重合度高，BM25 这种关键词匹配的命中率已经够用，向量检索的优势主要体现在语义改写和长文档上。二是**成本和延迟**：向量检索要么调 embedding API、要么在浏览器里跑模型，前者要钱要网络、后者要下几十 MB 模型；BM25 纯 JS 计算、毫秒级、零成本。三是**可解释**：BM25 能直接告诉用户命中了哪一段、为什么命中，我做了个检索测试面板把片段和分数显示出来；向量检索出问题很难 debug。**如果以后知识库涨到几百篇长文档，我会换混合检索（BM25 召回 + 向量重排）**，现在这个规模上向量是过度设计。"

- **中文为什么要 bigram？** 中文词之间没空格，直接按字符切会丢失词序信息，按词切又要引词典。bigram 是不用词典的折中：切出所有相邻二字组合，既保留了局部语序，又不用维护词表。代价是索引膨胀约 2 倍、会有一些无意义组合，但 BM25 的 IDF 天然会压低这些噪声词的权重。

- **`k1` 和 `b` 是干什么的？** `k1` 控制词频饱和——一个词出现 10 次不该比出现 1 次重要 10 倍，所以做了饱和曲线；`b` 控制文档长度归一化——长文档天然更容易命中，`b=0.75` 是常用折中值。这两个值我用的是文献默认值，没有针对自己的语料调参，**这是可以改进的点**。

- **为什么检索放前端而不是服务端？** 一是省一次往返和一次服务端计算；二是**隐私**——我的简历原文只留在浏览器里，只有命中的那几个片段会随请求发出去。这也和 localStorage 存数据是一致的思路。

- **三级降级会不会掩盖真实错误？** 会，所以每次降级返回体里都带了 `source` 字段（`ai` / `fallback`）和 `message`，前端能显示"当前用的是内置题库"。服务端也 `console.error` 了原始错误。**降级是为了用户体验，不是为了藏问题。**

- **模型返回的不是合法 JSON 怎么办？** 这就是 `parseQuestions` 那四级兜底存在的原因。层层降级：直接解析 → 抠中括号数组 → 提取引号串 → 按行切并剥列表符号。真实跑下来模型偶尔会在 JSON 外面包一层解释文字或代码块，前两级就能救回来。

- **为什么用 `generateObject` 而不是让模型自己吐 JSON？** 评分报告结构固定，用 Zod schema 约束后返回值直接是类型安全的对象，不用手写校验；不合格时 SDK 会重试或抛错，我再兜底到本地估算。

- **状态怎么管的？** 没用 Redux / Zustand，就是 React Hooks + 一个 `storage.ts` 数据层封装 localStorage 的增删改查。这个体量引入状态库是负担。

- **如果知识库涨到 10 万篇文档？** 现在是每次检索都**重建索引**（`retrieveContext` 里 new 一个 `BM25Index`），文档一多这个开销就顶不住。届时要建倒排索引并缓存、把索引构建挪到 Web Worker、再考虑向量召回。**我知道现在这个实现的瓶颈在哪。**

## 如果重来

- BM25 索引做缓存 + 增量更新，别每次重建；
- 补**混合检索**（BM25 召回 + 向量重排）作为可选档；
- 加**多轮追问的上下文管理**（现在每轮相对独立，长对话会丢前文）；
- 补**流式评估进度**和面试中途导出，现在必须整场结束才出报告。
