## 2. ★★★ 它的核心：三层"读懂怪物 AI"

游戏**不提供**"这个怪下一步出什么"的数据 —— 那写在每个怪的 C# 代码里。
这个 mod 用了三层来还原：

### 第一层：反射状态机（自动，覆盖所有怪）

`MonsterModel.MoveStateMachine` 是个 `MonsterMoveStateMachine`，里面有
`Dictionary<string, MonsterState>`。三种状态：

| 状态类型 | 含义 | 关键成员 |
|---|---|---|
| `MoveState` | 出一招 | `.Intents`（`IReadOnlyList<AbstractIntent>`）、`.FollowUpStateId` |
| `RandomBranchState` | 按权重随机分支 | `.States`（`IEnumerable<StateWeight>`） |
| `ConditionalBranchState` | 按条件分支 | `.EvaluateStates()` → 选中的 stateId、`.GetStates()` |

`StateWeight`（**是个 struct**）带 `.GetWeight()` / `.stateId` / `.repeatType` / `.maxTimes` / `.cooldown`。

→ 光靠反射就能画出**状态图骨架**，但有两个缺口：
① 条件分支的**条件是什么**，反射读不出来（`ConditionalBranchState` 内部是委托）；
② 每招**具体干什么**（上什么状态、加什么牌），也读不出来。

### 第二层：★ 扫 IL 字节码（补缺口②）

`MoveDetailResolver.cs`（886 行）干的事：**把招式的实现反汇编，看它调了哪些命令**。

```csharp
// 1. 拿到 MoveState 的私有委托字段
OnPerformField = typeof(MoveState).GetField("_onPerform",
                     BindingFlags.Instance | BindingFlags.NonPublic);

// 2. 如果是 async lambda，先钻进状态机的 MoveNext
var t = method.GetCustomAttribute<AsyncStateMachineAttribute>()?.StateMachineType;
if (t != null) { ScanMethod(t.GetMethod("MoveNext", ...), ...); return; }

// 3. 逐条 IL 指令找这三种"它干了什么"的标记：
//    MegaCrit.Sts2.Core.Models.ModelDb.Power<T>()            → 泛型实参 = 上的状态类型
//    MegaCrit.Sts2.Core.Commands.PowerCmd.Apply(...)         → 同上（含非泛型版）
//    MegaCrit.Sts2.Core.Commands.CardPileCmd
//        .AddToCombatAndPreview<T>()                         → 泛型实参 = 加的牌
// 4. 再往前扫最多 40 条指令，找 decimal 常量 / op_Implicit / Newobj，
//    把"数值"也捞出来（ScanDecimalAmountBefore）
```

> **这是整篇笔记里最"野"的一招**：游戏没给数据，它就去读 IL。
> 适用场景很窄（只在"招式是 `async Task` 方法且用命令式 API"时成立），
> 但它证明了一件事：**`Command` 类 API 是可静态识别的**。

### 第三层：手写覆盖数据（补缺口①，并且能纠正②）

`intentgraph.json` 就是人手写的补丁：条件表达式、分支标签、初始状态、图标覆盖、
布局微调。下面 §6 讲格式。

**三层的关系**：
```
反射状态机（骨架，全自动）
   └─ 手写 IntentDefinition（条件 / 标签 / 覆盖）  ← 优先，有就用它
   └─ IL 扫描（招式详情）                          ← 只在"显示行动详情"开关打开时跑
```

## 4. ★★ 工程模式（4 条可以直接照抄）

### 4.1 壳 + 版本化核心（第 4 次见到这个套路）

```csharp
[ModInitializer("Initialize")]
public class Initializer {
    public static void Initialize() {
        Libgcc();                              // Linux 上手动 dlopen libgcc_s.so.1（Harmony 要）
        LoadDll("Antlr4.Runtime.Standard");    // ★ 兄弟 dll 必须自己 LoadFrom（见 4.2）
        string suffix = SelectVersion();       // "-lt-0.110.0" 或 ""
        LoadDll("intentgraph2core" + suffix)
            ?.GetType("IntentGraph2.IntentGraphMod")           // ★ 反射，零编译期引用
            ?.GetMethod("InitializeMod", BindingFlags.Static | BindingFlags.Public)
            ?.Invoke(null, null);
    }
    private static string SelectVersion() {
        if (ReleaseInfoManager.Instance.ReleaseInfo != null &&
            new Version(ReleaseInfoManager.Instance.ReleaseInfo.Version.TrimStart('v'))
                < new Version("0.110.0"))
            return "-lt-0.110.0";
        return string.Empty;
    }
}
```

> ★ 之前记的"壳 + 版本化实现"生态套路（RitsuLib / 尖塔琐事 / LoadOrderManager），
> 这是**第 4 个实例**。而且它给出了**最干净的版本判断写法**：
> `ReleaseInfoManager.Instance.ReleaseInfo.Version`，不用去猜版本字符串从哪来。

### 4.2 ★ 兄弟 dll 必须自己 `LoadFromAssemblyPath`

```csharp
Assembly asm = typeof(SomeType).Assembly;
AssemblyLoadContext ctx = AssemblyLoadContext.GetLoadContext(asm);
ctx.LoadFromAssemblyPath(Path.Join(Path.GetDirectoryName(asm.Location), name + ".dll"));
```

→ **又一次验证**了之前用最小复现证明的结论：默认 ALC 不会探 mod 自己的目录，
**拷文件到哪都没用，必须代码里显式加载**。

### 4.3 ★★★ 免依赖的双框架适配（完整配方）

manifest 里 **`deps: []`** —— 一个框架都不声明。然后：

```csharp
public static void PostInitializeMod() {
    if (GetLoadedMods().Any(m => m.manifest?.id == "BaseLib")) {
        try {
            var asm = LoadDll("intentgraph2baselib");
            baseLibHelper = (IBaseLibHelper)AccessToolsExtensions
                .CreateInstance(asm.GetType("IntentGraph2.BaseLib.BaseLibHelper"));
            baseLibHelper.RegisterConfig();
        } catch (Exception ex) { baseLibHelper = null; Warn(...); }   // ★ 失败只是降级
    }
    if (GetLoadedMods().Any(m => m.manifest?.id == "STS2-RitsuLib")) { /* 同理 */ }

    // 两个都在 → 双向同步配置，用户在哪边改都一样
    if (ritsuLibHelper != null && baseLibHelper != null) {
        baseLibHelper.Config.SetFrom(ritsuLibHelper.Config);
        baseLibHelper.Config.OnUpdated += _ => { ritsuLibHelper.Config.SetFrom(baseLibHelper.Config); ritsuLibHelper.SaveConfig(); };
        ritsuLibHelper.Config.OnUpdated += _ => { baseLibHelper.Config.SetFrom(ritsuLibHelper.Config); baseLibHelper.SaveConfig(); };
    }
}
```

**两边的配置写法（同一份配置，两种框架各写一遍）：**

```csharp
// —— BaseLib 侧：继承 SimpleModConfig，用 [ConfigSection] 标注，静态属性转发 ——
public class HelperModConfig : SimpleModConfig {
    internal static IntentGraphModConfig BaseConfig { get; } = new();
    [ConfigSection("Display")]
    public static bool ShowMonsterMoveNames {
        get => BaseConfig.ShowMonsterMoveNames;
        set { BaseConfig.ShowMonsterMoveNames = value; BaseConfig.NotifyUpdated(nameof(ShowMonsterMoveNames)); }
    }
}

// —— RitsuLib 侧：DataStore 注册 + 每个设置一个 ModSettingsValueBinding ——
RitsuLibFramework.BeginModDataRegistration("intentgraph2", true);
RitsuLibFramework.GetDataStore("intentgraph2")
    .Register<IntentGraphModConfig>("Settings", "settings.json", SaveScope.Persistent,
        () => new IntentGraphModConfig(), true, migrationConfig: null, migrations: null);
new ModSettingsValueBinding<IntentGraphModConfig, bool>("intentgraph2", "Settings", SaveScope.Persistent,
    s => s.ShowMonsterMoveNames, (s, v) => { s.ShowMonsterMoveNames = v; s.NotifyUpdated("ShowMonsterMoveNames"); });
```

→ **核心是：配置模型（`IntentGraphModConfig`）框架无关，两个适配器只是壳。**
→ 我们 4 个自研 mod 现在只挂 RitsuLib。**要扩 BaseLib，照这个抄就行。**

## 5. 数据格式：`intentgraph.json`

顶层是 **`Dictionary<怪物类型全名, IntentDefinition[]>`**，`IntentDefinition` 字段：

| 字段 | 类型 | 作用 |
|---|---|---|
| `condition` | string（表达式，默认 `"true"`） | **哪条定义生效**；数组从后往前找第一个为真的 |
| `upToDateCondition` | string? | 不成立就在图上标「已过时」 |
| `alternativeMonsterId` | string? | 换用别的怪的图 |
| `secondaryInitialStates` | `{id, offset}[]` | 额外的初始状态（同一个怪多套循环） |
| `graph` | Graph? | 完全手画一张图（替代自动生成） |
| `graphPatch` | Graph? | 在自动生成的图上**打补丁**（加标签/图标/箭头） |
| `stateMachine` | `StateMachineNode[]?` | **手写状态机**（替代反射出来的那个） |
| `moveReplacements` | `{招式名: MoveReplacement}` | 覆盖某招的图标/箭头/条件 |
| `offset` | Position | 整体位移 |

`StateMachineNode`：`name` / `moveName` / `alternativeMoveNames` / `isInitialState` /
`initialStatePriority` / `children[]{node,label}` / `followUpState` / `horizontalLayout` /
`placeholderIntentCount` / `notSimpleLoopStart` / `offset`

`Graph`：`width` / `height` / `icons[]` / `iconGroups[]` / `labels[]` / `arrows[]` / `moves[]`

> 反序列化用 `JsonSerializerOptions{ PropertyNamingPolicy = CamelCase,
> DefaultIgnoreCondition = WhenWritingDefault, Encoder = UnsafeRelaxedJsonEscaping }`
> —— **`UnsafeRelaxedJsonEscaping` 是为了让中文不被转义**，写自己的 JSON 配置时照抄。

## 6. 表达式语言（ANTLR4 解析）

**运算符**：`> < == >= <= != && || !` + 括号 + 整数字面量 + `true/false`。
**求值**：ANTLR 生成 parser → 自己转成 `IExpression` 树（`ValueOperand` / `VariableOperand` /
`OneOperandExpression` / `TwoOperandExpression`）→ `.GetBool()`。

**变量表**（`VariableContext.cs`，这是这份笔记的第二值钱部分）：

| 变量 | 含义 |
|---|---|
| `m.<属性名>` | **反射读 `MonsterModel` 的属性，读不到再读字段** |
| `m.hasPower_<状态Id>` | 身上有没有这个状态（bool） |
| `m.powerAmount_<状态Id>` | 这个状态几层（int） |
| `mm.count` | 状态机里有几个状态 |
| `mm.hasMove_<招式>` | 有没有这招 |
| `mm.startsWith_<招式>` | 初始状态是不是它 |
| `mm.nextMoveOf_<A>_is_<B>` | A 的后继是不是 B |
| `slotName_is_<槽位>` | 自己在哪个槽 |
| `act` | 当前第几幕 |
| `slotIndex` | 自己在 `Encounter.Slots` 里的下标 |
| `ascension` | 进阶等级（**读 `AscensionManager` 私有字段 `_level`**） |
| `showMoveNames` / `showMoveDetail` / `inBestiary` | 自己的配置开关 |

**实际用法举例**（本体 `intentgraph.json`）：

```
"upToDateCondition": "mm.hasMove_STUN_MOVE && mm.nextMoveOf_STUN_MOVE_is_BEAST_CRY_MOVE"
"condition": "showMoveDetail"
```

**分支标签表**（`localization/<lang>/intentgraph.json`）：
`branch.<怪物全名>.<状态Id>.<子状态Id>` = 人写的条件说明。共 **133 条**（中文），例如：

```
branch.…TwoTailedRat.RAND.SCRATCH_MOVE   = 33%, 如果可召唤则8%, ≤1
branch.…KnowledgeDemon.CurseOfKnowledgeBranch.SLAP_MOVE = 已使用负面3次
branch.…Queen.YOURE_MINE_NOW_BRANCH.OFF_WITH_YOUR_HEAD_MOVE = 落单
branch.…FrogKnight.HALF_HEALTH.BEETLE_CHARGE = HP<50%，只能用1次
```

> 这 133 条 **本身就是一份"怪物 AI 分支条件"的攻略资料**。

## 10. 人话总结

- **它干什么**：悬停敌人，弹一张图告诉你"这怪接下来可能出什么、什么条件下出、概率多少"。
- **为什么值得学**：它是我们拆过的 mod 里**最会"读游戏运行时数据"的**。
  游戏不提供"怪物 AI 是什么"，它就**三层硬抠**：反射状态机 → 扫 IL 字节码 → 手写覆盖。
- **最值钱的三样东西**：
  1. **一份完整的游戏 API 清单**（§3，60 多个），尤其是 UI/节点那批（我们做界面必用）。
  2. **免依赖双框架适配配方**（§4.3）—— 想同时支持 BaseLib + RitsuLib 就照这个抄。
  3. **跨 mod 内容包约定**（§4.4）—— 不用依赖、不用注册，丢个 JSON 就生效。
- **我们大概率会用上的**：`ScriptManagerBridge.LookupScriptsInAssembly`（放 C# 脚本进 pck 的
  必要条件）、`FontControlUtils.ApplyLocaleFontSubstitution`（中文字体）、
  `Font.GetStringSize`（布局）、`GodotTreeExtensions.*Safely`（安全改节点树）。
- **要注意的**：它用了 `CombatManager.DebugOnlyGetState()` 这种"名字里带 DebugOnly"的 API，
  以及 IL 扫描、私有字段反射 —— **属于"能用但官方随时可能改"的灰色地带**。
  我们自己要用的话，收口到一个类型里，别散落（沿用 Spine 那次的教训）。
