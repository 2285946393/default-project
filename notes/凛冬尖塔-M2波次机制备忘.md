## 零、一次性说清：M2 的核心难题与答案

M2 要让"一波打完自动出下一波"，直觉做法是**绑回合号**（M1.5 就是这么干的：
`TurnNumber == 2` 出 A 波、`>= 3` 出 B 波）。

**这个做法在 M2 必须换掉**，理由（已在代码审查里提过）：
读档、跳回合、战斗被锁2扣住期间的回合号漂移，都会让绑回合号的波次逻辑错乱。

**正确做法：事件驱动 + 由官方的那一个判定点驱动。**

## 一、★ 关键机制：战斗结束判定的完整逻辑链

这是 M2 波次系统的**心脏**。反编译 `CombatManager.IsCombatEnding`：

```csharp
private bool IsCombatEnding(CombatTurnState turnState)
{
    if (!turnState.IsInProgress) return false;
    if (turnState.PendingLoss != null) return true;

    // ① 场上还有活的"主要敌人" → 不结束
    if (turnState.State.Enemies.Any(e => e != null && e.IsAlive && e.IsPrimaryEnemy))
        return false;

    // ② ★ 官方留的口子：问所有 model "该不该扣住战斗"
    if (Hook.ShouldStopCombatFromEnding(turnState.State))
        return false;

    // ③ 都没拦住 → 战斗结束
    return true;
}
```

**注意 `IsPrimaryEnemy` 这个词**——判定用的是**"主要敌人"**，不是"所有敌人"。
→ 这意味着：**如果召唤物（非 primary）还活着，战斗照样会结束。**
→ **对凛冬很关键**：波次怪必须被登记为 primary enemy，否则它们活着战斗也会结束。
（M1.5 用 `CreatureCmd.Add<T>` 加的怪，是否 primary 需确认——**这是一个要验证的点**，见 §五。）

`IsCombatEnding` 由 `CheckWinCondition` 调用（`CombatManager` 1392 行），
而 `CheckWinCondition` 在**多个安全点**被调用（832 / 849 / 1091 行，以及敌人每回合行动后）。

**这就是"事件驱动"的正确挂钩点**：不需要自己监听什么事件，
**只要 `ShouldStopCombatFromEnding` 返回 true，战斗就停在原地等着**——
然后你在下一个回合开始时把新波刷出来，再把该钩子放行。

## 二、★ 必须知道的坑：战斗"结束中"时钩子会被丢弃

`Hook.IterateCombatHookListeners` 的官方文档（逐字重点）：

> Iterates combat hook listeners, but **yields nothing if combat is over or ending**
> (`CombatManager.IsOverOrEnding`) **when the dispatch begins**. Most combat hooks should use this
> instead of `ICombatState.IterateHookListeners` directly, **so a hook dispatched after combat has
> started ending fires for no one** (for example after a Strike that Hellraiser plays automatically
> kills the last enemy while cards are still being drawn).

**翻译**：战斗一旦进入"结束中"状态，**之后派发的战斗钩子不会有人收到**。

**对凛冬的三个直接影响**：

1. **不要指望"敌人死光之后"的钩子**——那时如果没被 `ShouldStopCombatFromEnding` 拦住，
   战斗已进入结束态，你的钩子收不到。
2. **`ShouldStopCombatFromEnding` 是例外**：文档明确说它是**直接派发、不走这个守卫**的
   （原文在 xml：*"Dispatched directly, not through the IterateCombatHookListeners guard:
   it is a predicate that drives the decision of whether combat ends"*）。
   所以**它是唯一可靠的"救场"手段**。
3. **判断"战斗是否还在进行"要用 `IsOverOrEnding`**，不要用 `IsEnding` 或 `!IsInProgress`。
   官方文档原话：*"they can return unexpected results at certain boundary points"*。

**结论：波次推进必须做到"在敌人被打空之前就把 `ShouldStopCombatFromEnding` 立起来"。**
M1.5 的 `BeforeCombatStart` 提前武装（`SubWavesPlanned = 2`）正是这个思路——**方向是对的，要保留**。

## 三、★ 波次状态的正确设计（回答代码审查里的问题 A 与 B）

### 问题 A 的根因

`SubWavesPlanned` 只在 `BeforeCombatStart` 里赋值。而"战斗结束时钩子被丢弃"这条告诉我们：
**如果战斗已经开始结束，任何"事后补救"都来不及。** 所以初始值必须在**战斗开始前**就位。

### 推荐的数据设计（M2 用）

```csharp
// —— 局级（跨战斗）——
[SavedProperty] public int CurrentWaveIndex { get; set; }   // 全局第几波（0 起）
// 波次表本身：确定性生成，不需要存 —— 用 runState 种子重算即可（同 quest-spire 做法）

// —— 场级（每场战斗独立）——
[SavedProperty] public int WavesDoneThisCombat { get; set; }   // 本场已清完几波
[SavedProperty] public int WavesTotalThisCombat { get; set; }  // 本场共几波（开战即写入！）
```

**关键点：`WavesTotalThisCombat` 必须在"战斗刚开始、还没进结束态"时写入。**
`BeforeCombatStart` 是合适的（但要确认读档路径也走到它——见问题 A）。
**更稳的双保险**：在 `BeforeSideTurnStart`（每回合都跑）里做一次惰性初始化：

```csharp
public override Task BeforeSideTurnStart(...)
{
    if (WavesTotalThisCombat == 0)   // 读档兜底：还没初始化就地补上
    {
        WavesTotalThisCombat = PlanWavesForThisCombat();
        WavesDoneThisCombat = 0;
    }
    ...
}
```

**为什么这样能解决"读档 + 跳回合"**：
判定只看 `WavesDoneThisCombat < WavesTotalThisCombat`，
**两个数都存在存档里**，与 `TurnNumber` 完全解耦。✅

### 波次推进的触发（问题 B 的正解）

**不要用 `TurnNumber == 2 / >= 3`。** 改成"**场上敌人被清空 → 出下一波**"：

```csharp
public override Task AfterSideTurnEnd(...)   // 或 BeforeSideTurnStart，看时机
{
    // 本波清空了吗？（只看 primary enemy）
    bool cleared = !combatState.Enemies.Any(e => e != null && e.IsAlive && e.IsPrimaryEnemy);
    if (cleared && WavesDoneThisCombat < WavesTotalThisCombat)
    {
        WavesDoneThisCombat++;
        SpawnWave(WavesDoneThisCombat);   // 刷下一波
        // ShouldStopCombatFromEnding 会自动从 true 变 false（当 Done == Total 时）
    }
    return Task.CompletedTask;
}
```

**为什么这个写法抗读档**：它不依赖"现在是第几回合"，
只依赖"场上有没有怪 + 已经打完了几波"，**两者都是可恢复的状态**。

## 四、M2 波次表的架构建议

```
WinterWaveTable（静态/确定性）
  ├─ 用 runState.Rng.Seed + CurrentActIndex 播种 → 保证联机一致、读档可重算
  └─ 输出：本幕的波次清单 [(波型, 敌阵容, 槽位表), ...]

FrostPactRelic（已有，扩展）
  ├─ CurrentWaveIndex / WavesDoneThisCombat / WavesTotalThisCombat  ← 三个 [SavedProperty]
  ├─ ShouldStopCombatFromEnding() => WavesDone < WavesTotal          ← 有波未完 → 扣住
  ├─ ShouldProceedToNextMapPoint() => LockRoom                       ← 出不了房间
  └─ 波次推进：清场检测 → 刷下一波

每次"波" = 一个 EncounterModel 子类（或动态构造）
  ├─ Slots => ["l2","l1","c","r1","r2"]          ← 5 槽位模板（见 API 备忘 §四）
  └─ GenerateMonsters() => 按槽位表摆怪
```

**波次间奖励**：`RewardsCmd.OfferCustom`（quest-spire 已验证写法）。
**波次预告面板**：可以用 `CombatRoomMode.VisualOnly`（敌人可见不能打），
或纯 UI 面板（照抄 QuestPanel 手艺）。

## 五、✅ 已解决：波次怪一定是 primary enemy（悬念清掉）

我一开始担心"`CreatureCmd.Add` 加的怪可能不是 primary enemy，导致战斗提前结束"。
**反编译后确认：这个担心不成立，`IsPrimaryEnemy` 是推导属性，不需要手动设置。**

```csharp
/// Is this creature a <b>primary enemy</b>?
/// A <b>primary enemy</b> can stay alive all alone.
/// A <b>secondary enemy</b> will automatically die unless there's also a living primary enemy.
/// Most enemies are primary enemies. Enemies with powers like MinionPower or IllusionPower are secondary.
public bool IsPrimaryEnemy
{
    get
    {
        if (Side != CombatSide.Enemy) return false;
        return !IsSecondaryEnemy;
    }
}

public bool IsSecondaryEnemy
{
    get
    {
        if (Side != CombatSide.Enemy) return false;
        return Powers.Any(p => p.OwnerIsSecondaryEnemy);   // ← 只有带特定 power 才是 secondary
    }
}
```

**结论（重要，直接影响 M2 设计）**：

1. **只要是 `CombatSide.Enemy`，且没挂 `MinionPower` / `IllusionPower` 这类 power，就是 primary**。
   → **`CreatureCmd.Add<T>` 加的普通怪天生就是 primary enemy** ✅
   → 所以"波次怪活着时战斗不会结束"这条**自动成立**，不需要额外做任何事。

2. **`IsPrimaryEnemy` 没有 setter，是只读推导属性** —— 不能手动设，也不需要。

3. **⚠️ 但有一个反向风险要注意**：如果波次怪挂了"仆从类"power（`MinionPower` 等），
   它会变成 secondary → **本体怪一死，它就自动死**（文档原话：*"A secondary enemy will
   automatically die unless there's also a living primary enemy"*）。
   → **M2 设计时，波次怪不要用仆从类机制**，否则会出现"波次怪莫名暴毙"。

4. **顺带**：这意味着**本体怪和波次怪在判定上是平级的**——
   只要场上还有任何一只活着的非仆从敌人都算"战斗未结束"。
   → 所以 M1.5 里"本体怪 + A 波全灭 → 战斗不结算"能生效，
   **可能是"本体怪还在"撑着的，不一定是 `ShouldStopCombatFromEnding` 在起作用**。
   → **验证清单第 2 条要看清**：必须**本体怪和 A 波怪全部死光**，才真正测到锁2。
   （M1.5 的清单里写的是"本体怪+A波全灭"，是对的 ✅）

## 八、三条最重要的原话（背下来）

1. **`ShouldStopCombatFromEnding` 官方注释**：
   > "If all enemies are dead, should we stop combat from ending?
   > This should be set to true when all enemies are dead but new enemies are about to spawn."

2. **`IterateCombatHookListeners` 官方注释**：
   > "yields nothing if combat is over or ending when the dispatch begins ...
   > so a hook dispatched after combat has started ending fires for no one"

3. **`CombatManager.IsOverOrEnding` 官方注释**：
   > "When you want to skip/cancel an effect because combat is not in progress, you should usually
   > use this instead of `IsEnding` or `!IsInProgress`, because they can return unexpected results
   > at certain boundary points."
