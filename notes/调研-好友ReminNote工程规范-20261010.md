## 二、可抄点 ①：Slice（切片）——「做之前先写简报」

他每个功能块开工前，先写一篇 `docs/slices/P?-??-implementation-brief.md`。
34 篇，命名规律：

```
P0-03-implementation-brief.md          实现的
P0-06-manual-test.md                   人工测的
P2-02-parser-glued-date-fix.md         修 bug 的
P2-05-ci-gate-fix.md                   修 CI 的
P2.75-00-contract-freeze.md            ★ 契约冻结
P3-09-final-gate.md                    最终门禁
```

**规则是写死的**（原文）：

> 每个 Slice 必须保持**小而可验证**，完成后报告**改动、构建/测试结果、手动测试步骤与已知限制**。
> **没有用户明确指示，不自动进入下一个 Slice。**

### 💡 能抄什么

本仓库 `notes/` 已经有类似的东西（`尖塔任务-mod-开发交接.md` 就是），但**缺两样**：

1. **`manual-test` 独立成篇** —— 他每块都写"人手怎么点一遍才算过"。
   本仓库的 mod 改完常常只在对话里说一句"能跑了"，第二天就忘了怎么验。
2. **`contract-freeze`（契约冻结）** —— 动手前先把"这个接口长什么样、不许改什么"钉死。
   **本仓库最需要这个**：凛冬尖塔和 dou-spire 是**多 AI 并行**的，
   两边同时改一个文件的事已经踩过（AGENTS.md 里写着"发现刚被改过就让位"）。

**建议动作**：给 `notes/` 加一条约定 —— 动到 `projects/` 里多文件工程时，
先在 `notes/` 写一篇 `xxx-切片简报.md`，只写三行：
**要做什么 / 怎么验 / 不许改什么**。不要求长，要求**开工前存在**。

## 三、可抄点 ②：ADR（决策记录）——「为什么这么定」

`DECISIONS.md` 里 18 条，格式极简，每条就四行：

```markdown
## ADR-0016：P2 Today/Parser/历史与本地双宿主写入边界

- 日期：2026-08-28
- 状态：已接受；实现核对中
- 决策：<做了什么>
- 原因：<为什么>
- 结果：<限制了我不做什么>
```

**⭐ 最有价值的是「结果」那一栏** —— 他写的全是**限制**，不是成就：

> - **ADR-0002**：「P0-01 **不**引入 NuGet 依赖」
> - **ADR-0007**：「这是 P0 的**静态模块边界，不**建立运行时插件发现或通用模块框架」
> - **ADR-0010**：「默认语言为简体中文，**本 Slice 不加入**语言切换框架」
> - **ADR-0017**：「**除非用户另行明确授权**，任何检查点都**不自动 push、tag、release**」

**还有状态会变**：ADR-0002 写着「**已被 P0-02 局部更新**」——
**他保留旧决策并标注被谁取代，而不是偷偷改掉。**

### 💡 能抄什么

**这条几乎可以原样搬过来。**

本仓库 AGENTS.md 里有一大堆"踩过的坑"，但**只记了"别这么做"，没记"当时为什么决定这么做"**。
结果就是：**过几个月（或另一个 AI）会重新踩一遍**，因为它不知道背后的原因。

**建议动作**：在 `notes/` 建 `决策记录.md`，把 AGENTS.md 里的坑**升级成 ADR 格式**。
优先补三条最有价值的：

| 要补的 ADR | 对应的现有坑 |
|---|---|
| 「为什么养域名四个目录、不许根目录堆文件」 | 目录约定（现在只有规则没有原因） |
| 「为什么笔记要写 `-wb` 后缀」 | 多 AI 并行协作 |
| 「为什么不要批量杀进程」 | 踩坑第 9 条（**这条最有故事，也最该记原因**） |

`second-review/` 6 篇，文件名本身就是故事：

```
review-2026-08-28-p2-second-review.md

现有素材可以直接补两篇：

## 五、可抄点 ④：fail-closed（失败就锁死）—— 数据安全的思路

这是他做得最狠的一块。`ADR-0018` 里，数据库迁移流程是**固定 8 步**：

```
解析 → 上锁 → 备份 → 建候选 → 迁移 → 验证 → 原子切换 → 启动
```

**铁律三条**（原文提炼）：

1. **所有 migration 只改"候选库"**，绝不动正在用的那个
2. **验证全过才允许原子切换**（schema / integrity / foreign key / 关键旧数据，一项不过就停）
3. **⛔ 禁止 EF `Down`、禁止删库重建、禁止原地修复**

状态机写着 8 个失败态（`BACKUP_FAILED` / `VERIFY_FAILED` / `PROMOTION_UNKNOWN` …），
并且明确规定：**任何非 `READY` 状态都不允许普通业务写入。**

> 翻译成大白话：**宁可启动不了让你看见，也不许它自己乱动你的数据。**

### 💡 能抄什么

**思路能抄，别抄实现**（那是 .NET 数据库层的东西，本仓库用不上）。

本仓库对应的场景是 **「改线上站点 / Worker / 部署」**，
2026-10-10 的`部署验证铁律`已经踩过一次惨的（一篇文章折腾 2 小时）。

**他的做法可以给铁律加一条**：

> **改任何线上东西之前，先确认"改坏了怎么退回去"**（记住旧版本号 / 旧文件在哪）。
> **说不出来退路的，先别改。**

## 六、可抄点 ⑤：他对用户诚实

`README.md` 里主动列「Alpha 已知限制」（**不是别人问才说**）：

> - Toast/Tray/Widget 的跨进程通知宿主桥接**尚未启用**
> - Windows 睡眠/唤醒、真实桌面通知效果和用户 sign-off **尚未完成人工验收**
> - 本包用于会议前试用，**不建议承载唯一生产数据**

**`PRODUCT_RULES.md` 里反复出现同一句话**（我数了下至少 4 次）：

> 「**不能把独立测试当作该步骤的验收证据**」

### 💡 能抄什么

这条**本仓库已经做对了一半**：AGENTS.md 里有「**"命令成功了"≠"线上变了"**」，就是这个精神。

**差的一半是「交付时主动说限制」**。
本仓库做完页面的交付话术，可以补一句固定格式，比如：

> 「这个页面 X 能用，**Y 还没做**（我知道，别当它坏了）。」

**加上"我知道"，用户就不会以为是 bug 而反复来问。**

## 八、🔴 对照：本仓库刚发生的实例（2026-10-10）

就在写这篇之前，**主人的斗地主 mod 联机卡死了**，日志特征：

```

**这两句话刷了 200+ 遍，无限重试、不放弃、不提示。**

**如果按 ReminNote 的规范，这一段应该有：**

| 他的原则 | 本仓库该补的 |
|---|---|
| fail-closed（失败锁死并暴露状态） | 重试 N 次后**停止**，弹「与主机失联」，而不是静默刷屏 |

| `verify-*.ps1` 门禁 | 联机断线属于**可自动测**的场景，`projects/dou-spire` 有 `tools/` 可加 |

**具体 bug 位置**：`projects/dou-spire` 里处理"连接或握手还没就绪"的那段重试逻辑。
**日志文件**：`%APPDATA%\SlayTheSpire2\logs\godot.log`（当时已 2958 行 / 819 行是斗地主）。

## 九、❌ 哪些**不要**抄

调研要能分辨"好但用不上"。以下**明确不建议搬**：

| 他的做法 | 为什么不抄 |
|---|---|
| 6 个项目分层（Core/Infra/Windows/Agent/Bootstrap/Widget） | 本仓库是**单人 + 多 AI 的作品集**，不是要长期维护的商业产品；分层会拖慢出活 |
| `Directory.Packages.props` 中央版本管理 | .NET 专属；本仓库的 `projects/` 以 mod 和前端为主 |
| 18 条 ADR 的**完整**体量 | 抄**格式**，不抄数量。本仓库先补 3 条最痛的 |
| `CODE_OF_CONDUCT.md` / `CONTRIBUTING.md` | **单人项目，没有协作者**，写这个纯属装饰（他有是因为开源标准流程） |
| `MASTER_DEVELOPMENT_PLAN.md`（58.6 KB） | 他的项目有明确终点（一个桌面应用）；本仓库是**持续产出作品的仓库**，计划会立即过期 |

**判据**：他做的是**一个要交付的软件**，本仓库是**一堆作品 + 求职材料**。
**凡是"为了长期维护"的规范都要打折，凡是"为了不返工"的规范都值得抄。**
