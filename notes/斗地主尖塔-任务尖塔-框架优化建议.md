## 术语小抄（先说人话）

| 词 | 人话 |
|---|---|
| **框架** | 别人写好的一层地基。我们不用自己从零写，直接用它的现成零件 |

## 二、A 类：确定该改

### A1 ⚠️ 三个真 bug，都是"元数据说了假话"

> **2026-10-08 下午更新**：拆完 `ModTemplate-StS2` 后**多找到一条、并推翻了一条**。
> 权威依据见 `notes/杀戮尖塔2-拆解-ModTemplate工程模板.md` §四（游戏 v0.111.0 的反编译源码）。
> 现在 A1 是**三条**。

#### A1-1 ★ 依赖版本字段名写错 → **版本约束完全失效**（新发现，最严重）

**问题**：我们的依赖条目写的是
```jsonc
{ "id": "STS2-RitsuLib", "version": "0.6.6" }
```
但游戏只认 **`min_version`**：

```csharp
// MegaCrit.Sts2.Core.Modding/ModDependency.cs（v0.111.0）
public class ModDependency {
    [JsonPropertyName("id")]          public string  id;
    [JsonPropertyName("min_version")] public string? minVersion;   // ← 只有这一个版本字段
}
```

`version` **不是合法字段**，`System.Text.Json` 直接忽略 → `minVersion = null`，
而 `ModManager` 的校验是 `else if (declaredDependency.minVersion != null) { ...比对版本... }`
→ **null 就把整段版本校验跳过**。

**不是猜的，是数出来的**（本机 121 个工坊 manifest + 本地 4 份，共 65 个依赖条目）：

| 依赖条目里用的键 | 次数 |
|---|---|
| `id` | 65 |
| **`min_version`** | **48** |
| `version` | **10** ← **这 10 条全是我们自己的 mod** |
| `min` | 1 |

**全生态只有我们在用 `version`。**

**后果**（要说准确，别夸大）：
- 依赖的**存在性**检查仍然有效（`id` 是读得到的）→ 玩家没装 RitsuLib，照样报 `MISSING_DEPENDENCY`；
- **版本**检查彻底失效 → 假如某个玩家装着**能加载、但比我们要求的旧**的 RitsuLib，
  游戏会放我们进去，然后在运行时炸（`MissingMethodException` 之类），而不是给一句人话。
- 而且 `ModManifest.ReadFromStream` 里已经写了**老格式迁移告警**，
  明说这套"不写 min_version"的写法 **"will be removed in a future release"** → 早晚会硬性要求。

**改法**：3 个 mod 的 **6 条**依赖（DouSpire 2 条、QuestSpire 2 条、FrostSpire 3 条）+ BloomlessSpire 1 条：
```jsonc
{ "id": "STS2-RitsuLib", "min_version": "0.6.6" }
{ "id": "BaseLib",       "min_version": "v3.4.7" }   // 开头的 v 合法（SemanticVersion.cs:66 显式跳过）
{ "id": "MinionLib",     "min_version": "0.6.3" }
```

> ✅ **改这个键名是安全的**：`v3.4.7` 这种带 `v` 的写法游戏解析得了（`SemanticVersion.cs:66`）；
> 且被依赖三方自己声明的 `version` 分别是 RitsuLib `0.6.6` / BaseLib `v3.4.7` / MinionLib `0.6.3`，
> **都 ≥ 我们要求的值**，不会把谁挡住。
> ⚠️ 但**改完是一条"收紧"**：以前是"完全不检查"，现在是"真的检查" —— 属于预期行为，不是回归。

#### A1-2 ⚠️ `min_game_version`：**原结论的前提是错的，已改口**（原 A1-1）

原文写的是："三个 mod 声明 0.106.0 起，但 RitsuLib 0.6.6 自己要求 0.111.0 起"。**前半句对，后半句错。**

**真实情况**：RitsuLib 0.6.6 **支持四个游戏版本** `0.107.1 / 0.109.0 / 0.110.0 / 0.111.0`。

| 证据 | 内容 |
|---|---|
| 工坊 `3747602295/ritsulib-variants.manifest`（1956 B） | `variants: compatTarget = 0.107.1 / 0.109.0 / 0.110.0 / 0.111.0` |
| 工坊 `3747602295/compat/` | 四个目录：`0.107.1 0.109.0 0.110.0 0.111.0` |
| 工坊 `3747602295/mod_manifest.json` | `"min_game_version": "0.107.1"`（= 最低那个 compatTarget） |
| RitsuLib 构建规则 `build/RitsuLib.ModManifest.targets:84` | `min_game_version = $(Sts2ApiCompat)`；发行版取 `lowest_compat_target(...)` |
| **本地 `mods/STS2-RitsuLib/`** | `compat/` **只剩 `0.111.0`**，`variants.manifest` 只有 **629 B**，`mod_manifest.json` 里 `min_game_version` 被改写成 **`0.111.0`** |

**我当初看的是最后那一行 —— 本地那份"按当前游戏版本裁剪过的安装副本"，
把"它当前选中的变体"当成了"它的最低要求"。**

**已执行的改动（要保持现状还是回退，需要你拍板）**：
已把三个 mod 的 `min_game_version` 从 `0.106.0` 改成 **`0.111.0`**。
按游戏判定（`GAME_VERSION_UNSUPPORTED`），**游戏在 0.107.1~0.110 的玩家现在会被直接拦住**，
而他们的 RitsuLib 其实是能跑的。

**⚠️ 但不能顺手改回 `0.107.1`** —— 我们的 dll 是拿 **0.111.0** 的 `sts2.dll` 编的，
"我们的代码在 0.107 上能不能跑"**没有任何证据**。
`min_game_version` 的准确定义是"低于它就不给加载"，
**要调低它，前提是先验证我们的代码没用 ≤0.107 之后新增的 API**。这是另一件事，
详见 `notes/杀戮尖塔2-拆解-ModTemplate工程模板.md` §7.1 和 §九.1。

**已知的、能立刻确定的**：这一项**我们四个工程里没有任何机制在管**。
（但生态里**有** —— RitsuLib 自己的 `GenerateRitsuLibModManifest`、模板的 `UpdateDependencyVersions`
都在构建前重写 manifest。**我们缺的是"接入"，不是"世上没有"。** 原文那句"没有任何自动机制"口径不准。）

#### A1-3 "构建时自动同步依赖版本"这个安全网，实测**没有生效**（原 A1-2）

四个 csproj 里都有一个 `SyncManifestDependencies` 目标，意图是"构建时把 manifest 里
`dependencies[STS2-RitsuLib].version` 自动改成实际用的版本"（`QuestSpire.csproj:72-98`、`DouSpire.csproj:108+`）。

但**部署出来的清单里，这个值还是旧的**：

| mod | 部署清单里写的 RitsuLib | 实际装的 | 部署 dll 时间 |
|---|---|---|---|
| `DouSpire` | 0.6.6 | 0.6.6 | 2026-10-08 02:29 |
| `QuestSpire` | **0.6.2** ❌ | 0.6.6 | 2026-10-08 01:03 |
| `FrostSpire` | **0.6.5** ❌ | 0.6.6 | 2026-10-07 00:18 |

**坐实"目标没跑"的证据**（不是猜的）：

1. 部署那份和源码那份**逐字节相同**（`diff` 无输出）→ `CopyMod` 拷的就是源码原文，中间没被改写；
2. 这个目标会**回写源码文件**。QuestSpire 的 `QuestSpire.json` mtime 是 **2026-10-04 14:54**，
   而最后一次构建是 **2026-10-08 01:03** —— 如果目标真的跑过且需要更新，源码 mtime 会被刷到 10-08 01:03。
   它没有 → **目标被跳过了**。FrostSpire 同理（json 10-06 20:34 / 最后构建 10-07 00:18）。
   （DouSpire 的 json 也是 10-07 01:52 没动过，但它的值**本来就等于** 0.6.6，
   所以"没写"是正常的 —— 正因为如此，**光看 DouSpire 判断不出这个目标到底行不行**。）

**为什么它必然不生效 —— 现在是"三重失效"叠加**（拆完模板后才看全）：

| # | 失效点 | 说明 |
|---|---|---|
| 1 | **守卫条件为空** | `Condition="'$(PkgSTS2_RitsuLib)' != ''"` 为假 → **整个目标被跳过，一声不响** |
| 2 | **改的键名是错的** | 正则里写的是 `"version"` —— 就算跑通了，改的也是游戏不认的字段（见 A1-1） |
| 3 | **没有任何输出** | 没有 `Message`/`Warning`，所以「跳过」和「跑完了」在日志里长得一样 |

**★ 正解（从模板抄，`ModTemplate-StS2/content/ModTemplate/ModTemplate.csproj:70-92`）**：
> ⚠️ **这段下面立刻就是协作者的「A1-3 更正」——先读那段再读这段。**
> ① 我把失效原因归到"守卫条件为空"是**错的**（已被实验证伪）；
> ② 模板这个 `project.assets.json` 方案**版本号来源不能照抄**（它给的是 NuGet 解析到的最新版，
> 我们这里是 0.6.7，而游戏/工坊装的是 0.6.6 → 照抄会把 0.6.6 的玩家拦下来）。
> **能抄的是"时机 / 正则安全 / 必须有日志"这三条；版本号来源要改成"游戏目录优先"。**
不要去猜 `$(PkgXxx)` 属性，**直接读 NuGet 的解析结果文件** `project.assets.json`：

```xml
<Target Name="UpdateDependencyVersions" BeforeTargets="BeforeBuild"
        Condition="Exists('.godot/mono/temp/obj/project.assets.json')">
  <PropertyGroup>
    <NuGetData>$([System.IO.File]::ReadAllText(".godot/mono/temp/obj/project.assets.json"))</NuGetData>
    <!-- 抠出真实解析到的版本号（模板是 BaseLib，我们换成 STS2.RitsuLib 的包名） -->
    <ActiveVersion>$([System.Text.RegularExpressions.Regex]::Match(
        $(NuGetData), '"Alchyr.Sts2.BaseLib\/([^"]*)').Result('$1'))</ActiveVersion>
    <OldContent>$([System.IO.File]::ReadAllText($(ManifestPath)))</OldContent>
    <NewContent>$([System.Text.RegularExpressions.Regex]::Replace($(OldContent),
        '("id":\s*"BaseLib",\s*"min_version":\s*")[^"]*', '${1}$(ActiveVersion)'))</NewContent>
  </PropertyGroup>
  <WriteLinesToFile Condition="'$(OldContent)' != '$(NewContent)'" File="$(ManifestPath)"
                    Lines="$(NewContent)" Overwrite="true" Encoding="UTF-8" />
  <Message Condition="'$(OldContent)' != '$(NewContent)'"
           Text="Updated BaseLib dependency version in mod manifest json to version $(ActiveVersion)"
           Importance="high" />
</Target>
```

**它为什么就一定行**：`project.assets.json` 是 NuGet 每次还原都会写的**解析结果**，
"实际用了哪个版本"白纸黑字在里面，不存在"属性没生成所以为空"这种可能。

**顺带一条规矩（今天两次栽在这）**：构建脚本里**"必须成立"的前提要么 `<Error>`、要么至少 `<Warning>`，
绝不允许静默跳过**。模板的 `CheckDependencyPaths` 就是硬 `<Error>` 的正确示范。

> 另外这个目标会**回写被 git 跟踪的源码文件**，就算修好了也会造成"每次构建都有 diff"的噪音，
> 更稳的写法是只改写**部署副本**、不碰源码。

#### 🔧 A1-3 更正（国际 WB 补，2026-10-08 下午）——**结论方向对，"为什么"错了**

上面 §A1-3 的**观察**全部成立（部署那份 = 源码原文、源码 mtime 没被刷、值对不上）。
但归因的**第 1 条「守卫条件为空 → 整个目标被跳过」是错的**。已用实验证伪：

**证伪实验**：把 `DouSpire.json` 里的 RitsuLib 版本**故意写成 `0.6.1`** → 构建 → 源码 json
**变回了 `0.6.7`**。目标**跑了**。（另：`.godot/mono/temp/obj/DouSpire.csproj.nuget.g.props:104`
里 `PkgSTS2_RitsuLib` 有真实路径，守卫条件本来就不为假。）

> 所以「跳过」和「跑了但没效果」在观察上证不出来 —— 这正是上面第 3 条
> 「没有任何输出」造成的误判。那条是**真问题**，保留。

**真正的原因是两个独立的 bug，叠在一起：**

| # | 真因 | 说明 |
|---|---|---|
| ① | **声明顺序抢跑** | 原写法 `AfterTargets="Build" BeforeTargets="CopyMod"`。**两个 target 都挂 `AfterTargets="Build"` 时，MSBuild 按声明顺序跑**；而这个 target 声明在 `CopyMod` **之后** → 实际顺序是 `Build → CopyMod（拷旧 json）→ 才改源码 json`。改完没人再拷一遍 → **部署那份永远是旧的**。<br>**修法**：`CopyMod` 加 `DependsOnTargets="SyncManifestDependencies"`，顺序 100% 确定。 |
| ② | **版本号来源取错** | csproj 引用写 `Version="*"` → NuGet 缓存里躺 0.6.2/0.6.5/0.6.6/0.6.7 好几个，`$(PkgSTS2_RitsuLib)` 指向**最新**（0.6.7），**不是游戏里装的那个**（0.6.6）。<br>**修法**：优先读**游戏目录** `mods/STS2-RitsuLib/mod_manifest.json` 的真实版本，读不到才退回 NuGet。 |

**另外三个坑（原版 `_Replacement` 会踩，DouSpire 2026-10-08 真的写坏过一次文件）**：

| # | 坑 | 说明 |
|---|---|---|
| ③ | **`${1}` / `$1` 反向引用** | MSBuild 会先把 `${1}` 当**自己的属性语法**展开成空串，再交给正则引擎；配合 `(?s)` 让 `.*?` 跨行 → **把整个 `mod_manifest.json` 吞进 `version` 字段**，文件写坏。**修法**：改用唯一占位符 `@@RITSULIB_DEP@@` 替换 → 数出现次数 → **必须恰好 1 个**才落盘。 |
| ④ | **`WriteLinesToFile` + `Regex::Split`** | 拆成行数组再写，会毁掉 JSON 字符串值里的 `\n` 转义 → `Invalid control character at: line 15 column 20`。**修法**：整个 JSON 作为**单行**一次写出（`Lines="$(_Updated)"`，不拆行）。 |
| ⑤ | **静默失败** | 加 `Message`（成功时报"同步为 X，来源 Y"）+ `Warning`（拿不到版本 / 匹配数 ≠ 1 时报警）。**这条是照上面的规誫做的**。 |

**已落地的范围**：`DouSpire.csproj`、`QuestSpire.csproj`、`FrostSpire.csproj` 三个
`SyncManifestDependencies` 已按上述五条重写，三个都编译 `0 警告 0 错误`，
部署清单里的依赖版本 = 游戏里实装的 `0.6.6`（md5 源↔部署一致）。
`BloomlessSpire` 待办。

### A2 设置项的文字：20 次"按节点路径改标签" → 走 BaseLib 自己的本地化键

**现状**：两个 mod 都是"先让 BaseLib 画好设置页，再按 `<属性名>/Label` 这个节点路径
钻进去把文字换掉"。

- `dou-spire/DouSpireCode/DouSpireConfig.cs:154-191` —— `SetupConfigUI` 里 20 次 `SetLabel`
- `quest-spire/QuestSpireCode/QuestSpireConfig.cs:74-99` —— 7 次，同样写法
- 两处注释都写着同一句话：「BaseLib 生成的每一行结构是 `<属性名>/Label`；直接改文字比去凑它的本地化表省事。」

**这句话在当时的条件下是对的**（没 pck、没本地化表）。但其实 **BaseLib 留了正门**，而且规则很简单。

**规则**（已在上游源码里逐字核对）：

```csharp
// BaseLib-StS2-master/Config/ModConfig.cs:499-504
protected string GetLabelText(string labelName, bool slugify)
{
    var key = slugify ? StringHelper.Slugify(labelName) : labelName;
    var loc = LocString.GetIfExists("settings_ui", $"{ModPrefix}{key}.title");
    return loc != null ? loc.GetFormattedText() : labelName;
}
```

- 表名：`settings_ui`
- 键：`{ModPrefix}{大写下划线的属性名}.title`
- `ModPrefix` = **根命名空间转大写 + `-`**（`Extensions/TypePrefix.cs:5-13`，`PrefixSplitChar = '-'`）

所以：
- `DouSpireConfig`（命名空间 `DouSpire`）→ 键是 **`DOUSPIRE-UI_SCALE.title`**
- `QuestSpireConfig`（命名空间 `QuestSpire`）→ 键是 **`QUESTSPIRE-UI_SCALE.title`**

**真样例**（BaseLib 自己带的 `BaseLib/localization/zhs/settings_ui.json`）：
```
"BASELIB-RESTORE_DEFAULTS_BUTTON.title" = "重置为默认"
"BASELIB-SFX_PLAYER_LIMIT.title"        = "音效数量上限"
```
格式完全吻合。

**改法**：在调 `base.SetupConfigUI()` 的**之前**，往 `settings_ui` 表里合并键值 ——
**和 DouSpire 已经对 `rest_site_ui` 做的事一模一样**（`DouSpireRestSite.cs:120-141`，
`LocManager.Instance.GetTable("settings_ui").MergeWith(...)`），仓库里已有现成招法，不用发明。

```csharp
public override void SetupConfigUI(Control optionContainer)
{
    EnsureLabels();                  // ★ 必须在 base 之前：base 读表的时候要能读到
    base.SetupConfigUI(optionContainer);
}

private static void EnsureLabels()
{
    if (_labelsReady) return;
    try
    {
        var table = LocManager.Instance?.GetTable("settings_ui");
        if (table is null) return;
        var en = GameIsEnglish();
        table.MergeWith(new Dictionary<string, string>
        {
            ["DOUSPIRE-UI_SCALE.title"]   = en ? "Table UI scale"   : "桌面界面缩放",
            ["DOUSPIRE-AI_DELAY.title"]   = en ? "AI thinking delay": "电脑出牌停顿",
            // ……其余照抄现在的 SetLabel 那份对照表
        });
        _labelsReady = true;
    }
    catch (System.Exception e) { Entry.Logger.Warn($"注入设置页文案失败: {e.Message}"); }
}
```

**收益**：
1. 去掉对 BaseLib **内部节点结构**的硬依赖 —— BaseLib 哪天改布局，`GetNode<…>("…/Label")`
   全部 `catch` 掉、静默变回属性名；而本地化键这条路是 BaseLib 承诺的公开行为。
2. 中英双语从"20 次三元表达式"变成"两张字典"。
3. 和仓库里已有的做法统一（少一种写法）。

**注意**：时序 —— 必须先注入再 `base`。可选键还有 `.hover.title`（悬停提示）和 `.description`。

### B1 `UiKit.GameFont()`：遍历整棵场景树借字体 → 用 Shell 主题令牌

**现状**：`quest-spire/QuestSpireCode/UI/UiKit.cs:18-30`

```csharp
{
    var root = Root;

    foreach (var node in Descendants(root))          // ← 递归遍历整个场景树

        if (node is not Label label) continue;

```

注释自己写着「拿不到游戏 UI 的主题，于是从场景里已存在的一个 Label 上'借'它正在用的字体」。

**但 RitsuLib 有现成的主题对象**：

```csharp

public static RitsuShellTheme Current => RitsuShellThemeRuntime.Current;   // :59
public FontTokens Font { get; }                                           // :101

// src/Ui/Shell/Theme/Tokens/FontTokens.cs

```

**改法**：
```csharp
public static Font? GameFont()
{
    try
    {
        var f = RitsuShellTheme.Current.Font.Body;   // O(1)，且就是游戏当前主题的正文字体
        if (f != null) return f;
    }
    catch (System.Exception) { /* 主题还没初始化 → 走老路 */ }
```

- 从"遍历整棵树"变成一次属性读取；
- 拿到的是**当前 Shell 主题**的字体（跟玩家的主题切换联动），而"第一个 Label"是谁取决于

- `Button` / `BodyBold` 两种字重白送，以后想做强调文字不用再想办法。

**风险**：低。留兜底就行（主题没起来时回退老路）。

> 对比：DouSpire 也有一份同样的 `GameFont()`（`DouSpireUi.cs:119-131`），
> 但它是**保底**（先去自己的字体档 `DouSpireAssets.FirstFont(...)`，找不到才借场景的），
> 而且它自己的字体是**主路径**。所以 DouSpire 这处优先级低。

```csharp
...
```

**框架能力**：`[RegisterNodeAttachment(typeof(父节点类型), "本地id")]` ——
声明"当某个类型的节点进入 `_Ready` 时，把子节点挂上去"。RitsuLib 会去补那个父类型的 `_Ready`：

**风险**：**中**。两个前提要保留：
1. 按钮必须**克隆**游戏原生的 `NMainMenuTextButton`，不能 `new` —— 它的 `_Ready` 会
   `GetChild<MegaLabel>(0)` 取那个文字子节点，新对象没有子节点直接抛（现有注释已记录）；
2. 克隆体要从**可见的**模板来（现有注释记录了"挑中了隐藏的『继续游戏』→ 按钮在树上但看不见"这个坑）。

也就是说，克隆逻辑要包成一个 `INodeAttachmentFactory`（工厂能拿到父节点，够用了）。

**建议**：**先开实验分支验证**，别在已上架的 DouSpire 上直接改。收益是"代码更干净"，不是"修 bug"。

> ⚠️ 已知限制，别白找：RitsuLib 的 `Ui/MainMenu/NMainMenuScroller` 是 **`internal`**，
> **没有公开的"往主菜单加按钮"API**（全 src 搜 `MainMenuEntry` / `AddMainMenu` 为空）。
> 所以我们"手动找容器"这个方向本身没错，只是**挂载时机**可以声明式化。

### C2 联机层：41KB 手写二进制编解码 → 框架的类型化消息

**现状**：`dou-spire/DouSpireCode/Table/DouSpireNet.cs`（**41,976 字节**）——
用 `System.Buffers.Binary.BinaryPrimitives` / `Encoding` 手写"结构体 ↔ 字节"，
再 `RitsuLibSidecarBus.RegisterHandler(ulong opcode, Action<ctx> handler)` 手工分发。

**框架能力**（`src/Networking/Sidecar/Core/Messaging/`）：

```csharp
public sealed record RitsuLibSidecarMessageDescriptor<T>(
    string ModuleId, string MessageKey,
    Func<T, byte[]> Serialize, Func<ReadOnlySpan<byte>, T> Deserialize,
    RitsuLibSidecarDeliverySemantics Delivery = RitsuLibSidecarDeliverySemantics.StableSync,
    bool Required = false);

RitsuLibSidecarTypedMessageRegistry.Register<T>(descriptor);              // → 稳定 opcode
RitsuLibSidecarTypedMessageRegistry.Subscribe<T>(descriptor, handler);
public sealed class RitsuLibSidecarJsonSerializer<T> { ... }              // 现成的 JSON 编解码
RitsuLibSidecarMessageBinding.RegisterForGodotMainLoop<T>(...);           // 自动回主线程
RitsuLibSidecarRequestReply.SendCorrelatedRequestToHostAsync<TReq,TResp>(...);  // 自带关联号+超时
```

**对比现状的优点**：
- 默认投递语义就是 `StableSync` —— 和 DouSpire 现在手工指定的**完全一致**，所以是等价替换；
- 编解码从"手写字节序"变成"给个序列化委托"，或者直接用 `RitsuLibSidecarJsonSerializer<T>`；
- 请求/应答不用自己搓关联号（现有代码里客机→主机是全手工的）。

**收益**：41KB 里可能有一大半能省掉。

**建议**：**现在不要动**。等下次要**加新频道**的时候，新频道直接用 `descriptor<T>` 写，
老的三个 opcode 原样留着。这样风险为零，还能逐步试出这条路靠不靠谱。
