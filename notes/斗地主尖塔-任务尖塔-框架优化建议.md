## 术语小抄（先说人话）

| 词 | 人话 |
|---|---|
| **框架** | 别人写好的一层地基。我们不用自己从零写，直接用它的现成零件 |
| **RitsuLib** | 地基的"管道层"：注册东西、什么时机被叫、界面风格、存档 |
| **BaseLib** | 地基的"零件层"：一堆 `CustomXxx` 父类，继承它就等于"我已经是个 Xxx" |
| **钩子 / hook** | 游戏自己留下的"在这儿叫我一下"的接口 |
| **补丁 / patch** | 游戏没留接口，我们硬撬开它的代码插一句（Harmony 干的活） |
| **本地化表** | 游戏里"key → 显示文字"的对照表。找不到 key 就显示一串内部代号 |
| **令牌 / token** | 框架把"字体、颜色、间距"抽成一个个有名字的值，用名字取，别硬编码 |

## 二、A 类：确定该改

### A1 ⚠️ 两个真 bug，都是"元数据说了假话"

#### A1-1 游戏版本声明比依赖要求还低

**问题**：三个 mod 声明"支持游戏 0.106.0 起"，但依赖的 RitsuLib 0.6.6 自己声明"要 0.111.0 起"。

| 事实 | 值 | 出处 |
|---|---|---|
| 本机已装游戏版本 | **v0.111.0** | `D:/software/steam/steamapps/common/Slay the Spire 2/release_info.json` |
| 已装 RitsuLib 版本 | **0.6.6** | `mods/STS2-RitsuLib/mod_manifest.json` |
| RitsuLib 0.6.6 自己声明的最低游戏版本 | **0.111.0** | 同上，`min_game_version` |
| `DouSpire` / `QuestSpire` / `FrostSpire` 声明的 | 都是 `"0.106.0"` | 各自 `<Mod>.json` |

**后果**：一个还在 0.106–0.110 的玩家会看到"这个 mod 支持我的版本"，
装了之后 RitsuLib 装不上 → mod 整个不工作，**而且看起来像是我们的 bug**。

**改法**（3 个文件各改一行）：
```jsonc
// DouSpire.json / QuestSpire.json / FrostSpire.json
"min_game_version": "0.111.0",   // 原来 "0.106.0"
```

> 这一项**没有任何自动机制**在管 —— csproj 里的同步目标只碰依赖版本，不碰 `min_game_version`。
> 所以必须手改，改完记得重新构建部署（部署目录那份也要跟着变）。

#### A1-2 "构建时自动同步依赖版本"这个安全网，实测**没有生效**

四个 csproj 里都有一个 `SyncManifestDependencies` 目标，意图是"构建时把 manifest 里
`dependencies[STS2-RitsuLib].version` 自动改成实际用的版本"（`QuestSpire.csproj:72-98`、`DouSpire.csproj:108+`）。

但**部署出来的清单里，这个值还是旧的**：

| mod | 部署清单里写的 RitsuLib | 实际装的 | 部署 dll 时间 |
|---|---|---|---|
| `DouSpire` | 0.6.6 | 0.6.6 | 2026-10-08 02:29 |
| `QuestSpire` | **0.6.2** ❌ | 0.6.6 | 2026-10-08 01:03 |
| `FrostSpire` | **0.6.5** ❌ | 0.6.6 | 2026-10-07 00:18 |

**坐实"目标没跑"的证据**（不是猜的）：

1. 部署那份和源码那份**逐字节相同**（`diff` 无输出）→ `CopyMod` 拷的就是源码原文，中间没被改写；
2. 这个目标会**回写源码文件**。QuestSpire 的 `QuestSpire.json` mtime 是 **2026-10-04 14:54**，
   而最后一次构建是 **2026-10-08 01:03** —— 如果目标真的跑过且需要更新，源码 mtime 会被刷到 10-08 01:03。
   它没有 → **目标被跳过了**。FrostSpire 同理（json 10-06 20:34 / 最后构建 10-07 00:18）。
   （DouSpire 的 json 也是 10-07 01:52 没动过，但它的值**本来就等于** 0.6.6，
   所以"没写"是正常的 —— 正因为如此，**光看 DouSpire 判断不出这个目标到底行不行**。）

最可能的原因：目标的守卫条件 `'$(PkgSTS2_RitsuLib)' != ''` 为假
（`PkgSTS2_RitsuLib` 由 `GeneratePathProperty="true"` 产生，依赖 NuGet 还原时把它生成出来；
用 Godot 编辑器构建 / 沙箱脚本构建时这条链不一定走通）→ **整个目标被跳过**，一声不响。

**建议**：
- **短期（就现在）**：别指望这个目标，**手工把三个 manifest 改成 `"0.6.6"`** —— 一行的事，立刻可控；
- **长期（可选）**：想修目标的话，把守卫条件从 `'$(PkgSTS2_RitsuLib)' != ''`
  换成"读不到就报 `Warning`"，至少让它**失败得可见**，而不是静默跳过。
  另外这个目标会**回写被 git 跟踪的源码文件**，就算修好了也会造成"每次构建都有 diff"的噪音，
  更稳的写法是只改写**部署副本**、不碰源码。

### A2 设置项的文字：20 次"按节点路径改标签" → 走 BaseLib 自己的本地化键

**现状**：两个 mod 都是"先让 BaseLib 画好设置页，再按 `<属性名>/Label` 这个节点路径
钻进去把文字换掉"。

- `dou-spire/DouSpireCode/DouSpireConfig.cs:154-191` —— `SetupConfigUI` 里 20 次 `SetLabel`
- `quest-spire/QuestSpireCode/QuestSpireConfig.cs:74-99` —— 7 次，同样写法
- 两处注释都写着同一句话：「BaseLib 生成的每一行结构是 `<属性名>/Label`；直接改文字比去凑它的本地化表省事。」

**这句话在当时的条件下是对的**（没 pck、没本地化表）。但其实 **BaseLib 留了正门**，而且规则很简单。

**规则**（已在上游源码里逐字核对）：

```csharp
// BaseLib-StS2-master/Config/ModConfig.cs:499-504
protected string GetLabelText(string labelName, bool slugify)
{
    var key = slugify ? StringHelper.Slugify(labelName) : labelName;
    var loc = LocString.GetIfExists("settings_ui", $"{ModPrefix}{key}.title");
    return loc != null ? loc.GetFormattedText() : labelName;
}
```

- 表名：`settings_ui`
- 键：`{ModPrefix}{大写下划线的属性名}.title`
- `ModPrefix` = **根命名空间转大写 + `-`**（`Extensions/TypePrefix.cs:5-13`，`PrefixSplitChar = '-'`）

所以：
- `DouSpireConfig`（命名空间 `DouSpire`）→ 键是 **`DOUSPIRE-UI_SCALE.title`**
- `QuestSpireConfig`（命名空间 `QuestSpire`）→ 键是 **`QUESTSPIRE-UI_SCALE.title`**

**真样例**（BaseLib 自己带的 `BaseLib/localization/zhs/settings_ui.json`）：
```
"BASELIB-RESTORE_DEFAULTS_BUTTON.title" = "重置为默认"
"BASELIB-SFX_PLAYER_LIMIT.title"        = "音效数量上限"
```
格式完全吻合。

**改法**：在调 `base.SetupConfigUI()` 的**之前**，往 `settings_ui` 表里合并键值 ——
**和 DouSpire 已经对 `rest_site_ui` 做的事一模一样**（`DouSpireRestSite.cs:120-141`，
`LocManager.Instance.GetTable("settings_ui").MergeWith(...)`），仓库里已有现成招法，不用发明。

```csharp
public override void SetupConfigUI(Control optionContainer)
{
    EnsureLabels();                  // ★ 必须在 base 之前：base 读表的时候要能读到
    base.SetupConfigUI(optionContainer);
}

private static void EnsureLabels()
{
    if (_labelsReady) return;
    try
    {
        var table = LocManager.Instance?.GetTable("settings_ui");
        if (table is null) return;
        var en = GameIsEnglish();
        table.MergeWith(new Dictionary<string, string>
        {
            ["DOUSPIRE-UI_SCALE.title"]   = en ? "Table UI scale"   : "桌面界面缩放",
            ["DOUSPIRE-AI_DELAY.title"]   = en ? "AI thinking delay": "电脑出牌停顿",
            // ……其余照抄现在的 SetLabel 那份对照表
        });
        _labelsReady = true;
    }
    catch (System.Exception e) { Entry.Logger.Warn($"注入设置页文案失败: {e.Message}"); }
}
```

**收益**：
1. 去掉对 BaseLib **内部节点结构**的硬依赖 —— BaseLib 哪天改布局，`GetNode<…>("…/Label")`
   全部 `catch` 掉、静默变回属性名；而本地化键这条路是 BaseLib 承诺的公开行为。
2. 中英双语从"20 次三元表达式"变成"两张字典"。
3. 和仓库里已有的做法统一（少一种写法）。

**注意**：时序 —— 必须先注入再 `base`。可选键还有 `.hover.title`（悬停提示）和 `.description`。

## 三、B 类：QuestSpire 的两处"手写了框架已有的东西"

### B1 `UiKit.GameFont()`：遍历整棵场景树借字体 → 用 Shell 主题令牌

**现状**：`quest-spire/QuestSpireCode/UI/UiKit.cs:18-30`

```csharp
public static Font? GameFont()
{
    var root = Root;
    if (root == null) return null;
    foreach (var node in Descendants(root))          // ← 递归遍历整个场景树
    {
        if (node is not Label label) continue;
        if (label.HasMeta(MetaTag)) continue;
        var f = label.GetThemeFont("font");
        if (f != null) return f;                     // ← 撞到第一个 Label 就拿它的字体
    }
    return null;
}
```

注释自己写着「拿不到游戏 UI 的主题，于是从场景里已存在的一个 Label 上'借'它正在用的字体」。

**但 RitsuLib 有现成的主题对象**：

```csharp
// src/Ui/Shell/Theme/RitsuShellTheme.cs
public static RitsuShellTheme Current => RitsuShellThemeRuntime.Current;   // :59
public FontTokens Font { get; }                                           // :101

// src/Ui/Shell/Theme/Tokens/FontTokens.cs
public sealed record FontTokens(Font Body, Font BodyBold, Font Button);   // :21
```

**改法**：
```csharp
public static Font? GameFont()
{
    try
    {
        var f = RitsuShellTheme.Current.Font.Body;   // O(1)，且就是游戏当前主题的正文字体
        if (f != null) return f;
    }
    catch (System.Exception) { /* 主题还没初始化 → 走老路 */ }
    return BorrowFontFromScene();                    // 现在的实现原样留作兜底
}
```

**收益**：
- 从"遍历整棵树"变成一次属性读取；
- 拿到的是**当前 Shell 主题**的字体（跟玩家的主题切换联动），而"第一个 Label"是谁取决于
  场景里谁先建出来 —— 这个不确定性会直接反映到观感上；
- `Button` / `BodyBold` 两种字重白送，以后想做强调文字不用再想办法。

**风险**：低。留兜底就行（主题没起来时回退老路）。

> 对比：DouSpire 也有一份同样的 `GameFont()`（`DouSpireUi.cs:119-131`），
> 但它是**保底**（先去自己的字体档 `DouSpireAssets.FirstFont(...)`，找不到才借场景的），
> 而且它自己的字体是**主路径**。所以 DouSpire 这处优先级低。

### B2 手打的 Harmony 补丁 → RitsuLib 的补丁框架

**现状**：`quest-spire/QuestSpireCode/Entry.cs:43-59`

```csharp
var harmony = new HarmonyLib.Harmony("local.questspire");
foreach (var patchType in new[] { typeof(Patches.CardAddedToDeckPatch),
                                  typeof(Patches.CardRemovedFromDeckPatch) })
{
    try { harmony.CreateClassProcessor(patchType).Patch(); ... }
    catch (System.Exception e) { Logger.Warn(...); }
}
```

注释解释得挺好：「**逐个补丁类分开打**：`PatchAll` 是"一个失败整批失败"——
万一某个补丁的目标方法对不上…另一个本来好的补丁也会被连累。」

**但这个担心在 RitsuLib 的 `ModPatcher` 上不成立** —— 我读了它的实现：

```csharp
// src/Patching/Core/ModPatcher.cs:266-302
public bool PatchAll()
{
    var results = new ModPatchResult[_registeredPatches.Count];
    for (var i = 0; i < _registeredPatches.Count; i++)
        results[i] = ApplyPatch(_registeredPatches[i]);     // ← 逐个记录结果
    var success = ProcessPatchResults(results);
    ...
    else { logger.ErrorNoTrace($"...Critical patch(es) failed, rolling back all patches...");
           UnpatchAll(); IsApplied = false; }
    return success;
}
```

**它是逐补丁记录成败的**，只有 `IsCritical == true` 的补丁失败才 `UnpatchAll()` 回滚。
把两个补丁都标 `IsCritical => false`，就得到和现在**完全一样的隔离**，外加拿到了别的东西。

**框架给的架子**（`Patching/Models/IPatchMethod.cs:11-36`）：
```csharp
static abstract string PatchId { get; }
static virtual bool IsCritical => true;          // 默认 true；我们要设 false
static virtual string Description => "Patch";
static abstract ModPatchTarget[] GetTargets();
```

**改法**：
```csharp
// 补丁类改成实现 IPatchMethod
internal sealed class CardAddedToDeckPatch : IPatchMethod
{
    public static string PatchId => "questspire_card_added_to_deck";
    public static string Description => "牌加进整局卡组 → 通知任务册";
    public static bool IsCritical => false;                    // ★ 失败不连累另一个

    public static ModPatchTarget[] GetTargets() => [
        new(typeof(CardPileCmd), nameof(CardPileCmd.Add),
            [typeof(CardModel), typeof(PileType), typeof(CardPilePosition),
             typeof(AbstractModel), typeof(bool)])
    ];

    public static void Postfix(CardModel card, PileType newPileType) { /* 原样 */ }
}

// Entry.Initialize() 里换成：
var patcher = RitsuLibFramework.CreatePatcher(ModId, "quest-spire", "QuestSpire 补丁");
patcher.RegisterPatch<Patches.CardAddedToDeckPatch>();
patcher.RegisterPatch<Patches.CardRemovedFromDeckPatch>();
patcher.PatchAll();
```
（`CreatePatcher` 在 `RitsuLibFramework.cs:1697`；`RegisterPatch<T> where T : IPatchMethod`
在 `Patching/Core/ModPatcherExtensions.cs:38`）

**收益**：
- 补丁**进入 RitsuLib 的补丁诊断**（统一报告里能看到我们的补丁有没有生效），
  现在只有我们自己的日志；
- 日志自动带 `PatchId`，将来游戏更新改了签名，一眼看出是哪一个坏了；
- 和 DouSpire 的写法风格统一（DouSpire 目前没自己打补丁，全靠声明式）。

**风险**：低-中。要重写两个补丁类（`[HarmonyPatch]` 特性不能用了，改成 `GetTargets()`）。
**建议先只改这两个文件、编译通过、跑一局验证"加牌任务还在计数"**。

### ⚠️ B3 但这两条补丁**本身必须留着** —— 我核实过，不是优化对象

差点以为是"框架有钩子我们却写了补丁"，所以专门去查了游戏 API。

**事实**（来源：`projects/dou-spire/.godot/mono/temp/bin/Debug/sts2.xml`，游戏官方 XML 文档）：

- `MegaCrit.Sts2.Core.Hooks.Hook` 一共 **147 个成员**；
- 名字里带 `Deck` 的只有**两个**：
  - `Hook.ShouldAddToDeck` → `<summary>See `AbstractModel.ShouldAddToDeck(CardModel)`.`
  - `Hook.ModifyCardBeingAddedToDeck` → `<summary>See `AbstractModel.TryModifyCardBeingAddedToDeck(CardModel, ref CardModel)`.`
- 这两个都是**"加之前的闸门 / 改写"**，**没有"加完之后通知我一下"**。
- `Hook.AfterCardChangedPiles` 对应的就是 `AbstractModel.AfterCardChangedPiles` ——
  也就是 `QuestBookRelic.cs:509` 已经覆盖的那个，签名里带 `CombatState`，是**战斗牌堆之间**的搬运。

**RitsuLib 的 `CardMovedBetweenPilesEvent` 也盖不到这个场景** —— 它是挂在这个钩子上的：

```csharp
// src/Lifecycle/Patches/CombatHookLifecyclePatches.cs:209-241
internal sealed class AfterCardChangedPilesLifecyclePatch : IPatchMethod
{
    public static ModPatchTarget[] GetTargets() => [
        new(typeof(Hook), nameof(Hook.AfterCardChangedPiles),
            [typeof(IRunState), typeof(CombatStateCompat), typeof(CardModel),
             typeof(PileType), typeof(AbstractModel)]),
    ];
    ...RitsuLibFramework.PublishLifecycleEvent(new CardMovedBetweenPilesEvent(...))
}
```

（顺手核过：RitsuLib 和 BaseLib 都**没有**包装 `ShouldAddToDeck` /
`ModifyCardBeingAddedToDeck` 这两个钩子。）

**结论**：`CardAddedToDeckPatch` / `CardRemovedFromDeckPatch` 是**必要的**，
只值换个架子（§B2）。这两刀的签名记得照反编译逐字核对 —— 现有注释已经强调了，继续保持。

### C1 主菜单按钮：`[RegisterNodeAttachment]` 能不能替掉"装三次 + 手找容器"？

**现状**：`dou-spire/DouSpireCode/Entry.cs:36-38` + `Table/DouSpireMenuButton.cs:41-89`

```csharp
RitsuLibFramework.SubscribeLifecycle<MainMenuReadyEvent>(_ => EnsureEntryPoints());
RitsuLibFramework.SubscribeLifecycle<RunLoadedEvent>(_ => EnsureEntryPoints());
```
```csharp
// DouSpireMenuButton.Install()：每次自己下去找
var menu = FindDescendant<NMainMenu>(root);
var container = menu.GetNodeOrNull<Control>("MainMenuTextButtons");
...

```

**框架能力**：`[RegisterNodeAttachment(typeof(父节点类型), "本地id")]` ——
声明"当某个类型的节点进入 `_Ready` 时，把子节点挂上去"。RitsuLib 会去补那个父类型的 `_Ready`：

```csharp
// src/Scaffolding/Godot/NodeAttachments/ModNodeAttachmentRegistry.cs:266
NodeAttachmentPatchInstaller.EnsureReadyPatched(parentType);
```
可选参数很全：`DuplicatePolicy`、`AddMode`、`SetupTiming`、`ChildIndex`、
`InsertBeforeName` / `InsertAfterName`、`IncludeDerivedParentTypes`。
（`Interop/AutoRegistration/RegistrationAttributes.NodeAttachments.cs`）

**收益**：删掉"要装三次"这个补丁式设计；挂载点变成声明式、只跑一次。

**风险**：**中**。两个前提要保留：
1. 按钮必须**克隆**游戏原生的 `NMainMenuTextButton`，不能 `new` —— 它的 `_Ready` 会
   `GetChild<MegaLabel>(0)` 取那个文字子节点，新对象没有子节点直接抛（现有注释已记录）；
2. 克隆体要从**可见的**模板来（现有注释记录了"挑中了隐藏的『继续游戏』→ 按钮在树上但看不见"这个坑）。

也就是说，克隆逻辑要包成一个 `INodeAttachmentFactory`（工厂能拿到父节点，够用了）。

**建议**：**先开实验分支验证**，别在已上架的 DouSpire 上直接改。收益是"代码更干净"，不是"修 bug"。

> ⚠️ 已知限制，别白找：RitsuLib 的 `Ui/MainMenu/NMainMenuScroller` 是 **`internal`**，
> **没有公开的"往主菜单加按钮"API**（全 src 搜 `MainMenuEntry` / `AddMainMenu` 为空）。
> 所以我们"手动找容器"这个方向本身没错，只是**挂载时机**可以声明式化。

### C2 联机层：41KB 手写二进制编解码 → 框架的类型化消息

**现状**：`dou-spire/DouSpireCode/Table/DouSpireNet.cs`（**41,976 字节**）——
用 `System.Buffers.Binary.BinaryPrimitives` / `Encoding` 手写"结构体 ↔ 字节"，
再 `RitsuLibSidecarBus.RegisterHandler(ulong opcode, Action<ctx> handler)` 手工分发。

**框架能力**（`src/Networking/Sidecar/Core/Messaging/`）：

```csharp
public sealed record RitsuLibSidecarMessageDescriptor<T>(
    string ModuleId, string MessageKey,
    Func<T, byte[]> Serialize, Func<ReadOnlySpan<byte>, T> Deserialize,
    RitsuLibSidecarDeliverySemantics Delivery = RitsuLibSidecarDeliverySemantics.StableSync,
    bool Required = false);

RitsuLibSidecarTypedMessageRegistry.Register<T>(descriptor);              // → 稳定 opcode
RitsuLibSidecarTypedMessageRegistry.Subscribe<T>(descriptor, handler);
public sealed class RitsuLibSidecarJsonSerializer<T> { ... }              // 现成的 JSON 编解码
RitsuLibSidecarMessageBinding.RegisterForGodotMainLoop<T>(...);           // 自动回主线程
RitsuLibSidecarRequestReply.SendCorrelatedRequestToHostAsync<TReq,TResp>(...);  // 自带关联号+超时
```

**对比现状的优点**：
- 默认投递语义就是 `StableSync` —— 和 DouSpire 现在手工指定的**完全一致**，所以是等价替换；
- 编解码从"手写字节序"变成"给个序列化委托"，或者直接用 `RitsuLibSidecarJsonSerializer<T>`；
- 请求/应答不用自己搓关联号（现有代码里客机→主机是全手工的）。

**收益**：41KB 里可能有一大半能省掉。

**风险**：**高**。这是**已经跑通的联机**（用户实测过的），重写等于把验证过的路径换成没验证的。

**建议**：**现在不要动**。等下次要**加新频道**的时候，新频道直接用 `descriptor<T>` 写，
老的三个 opcode 原样留着。这样风险为零，还能逐步试出这条路靠不靠谱。
