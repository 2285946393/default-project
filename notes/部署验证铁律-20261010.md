## 二、六条铁律

### 铁律 1 · 部署后必须验证"线上内容真的变了"

**只看命令退出码 = 没验证。** 传错目标时，`wrangler deploy` / `vercel deploy` / `git push`
全都会打印成功。

```bash
# ✅ 必须做：比对线上字节数 / 内容哈希
curl -s -o /dev/null -w "code=%{http_code} size=%{size_download}\n" \
  "https://<域名>/<新路径>?v=$RANDOM"     # ?v= 绕过边缘缓存
```

**判据**：
- 线上字节数 == 本地构建产物的字节数 → 传对了
- 线上 500 / 404，而本地 `wrangler dev --local` 是 200 → **100% 是"传错了目标"，不是代码问题**

> 部署命令的输出**不是证据**，HTTP 响应才是。

---

### 铁律 2 · 指代不明的目标，先问，别自己认

用户说 **"那个站" / "小站" / "我的博客" / "上次那个"** 时：

- ❌ 不要从记忆或历史里挑一个最像的当成目标
- ✅ 花 10 秒问一句："是 `<具体域名>` 吗？"
- ✅ 或者**从环境里直接查**：DNS → 响应头 `Server:` → 平台 API 列出真实资源

**2026-10-10 就是在这里亏掉 40 分钟。** 猜错目标的代价，远大于问一句的尴尬。

---

### 铁律 3 · 先本地复现，再怀疑远端

远端排查受网络、缓存、平台限制干扰，**极慢且不可靠**。
本地能跑就跑本地 —— 结论干净、快、可重复。

```bash
# Cloudflare Worker 本地跑（不碰网络，直接出栈）
node_modules/.bin/wrangler dev --port 8799 --local
curl -s -o /dev/null -w "%{http_code} %{size_download}\n" http://127.0.0.1:8799/<路径>
```

**本地 200 + 远端 500 ⇒ 代码没问题，问题在"部署到哪了"。** 一步定位，别绕。

---

### 铁律 4 · 先跑网络基准，区分"我慢"和"对面坏"

本机网络代理会限速、会超时、会并发失败。**这类噪声极容易被误判成"站点挂了"。**

```bash
# 基准：一个肯定快的站
curl -s -o /dev/null -w "%{http_code} %{time_total}\n" -m 10 https://www.baidu.com/
```

**判据**：
- 基准 0.5s，目标 25s / `code=000` → **可能是对面真的慢，也可能只是这个请求被限速**，
  必须**重试 3 次**再下结论
- 基准本身就慢 → **你这边的问题，停止分析对面**
- ⚠️ **不要并发压代理**：`xargs -P 5` 会让所有请求一起 `000`，制造"全站挂了"的假象

---

### 铁律 5 · 同名/近名资源，必须逐个核对

平台里常有**名字极像的多个资源**（`a` / `aa`、`prod` / `production`、`v1` / `v1-new`）。
**配置文件里写的不一定是线上正在用的那个。**

```bash
# Cloudflare：列出账号里所有 Worker 及各自绑定的域名（别猜，直接查）
curl -s -H "Authorization: Bearer <token>" \
  "https://api.cloudflare.com/client/v4/accounts/<account_id>/workers/domains"

# Cloudflare：列出所有 Worker 服务
curl -s -H "Authorization: Bearer <token>" \
  "https://api.cloudflare.com/client/v4/accounts/<account_id>/workers/services"

# Vercel：列出项目绑定的域名
curl -s -H "Authorization: Bearer <token>" \
  "https://api.vercel.com/v9/projects/<project_id>/domains?teamId=<team_id>"
```

**核对三件事**：① 线上域名绑的是哪个资源 ② 我要传的是哪个 ③ 两者是同一个吗。

---

### 铁律 6 · 沉没成本熔断：同一方向失败 3 次就停

**在错误的前提上深挖，挖得越深亏得越多。**
一旦出现下面任一信号，**立刻停止当前方向，回到"我是不是搞错了目标"**：

- 修好了一个 bug，但现象**完全没变**
- 同一个现象连续 3 次尝试都不动
- 你开始说"可能是缓存""再等等就好"
- 你修的东西**和最初的目标没有直接因果关系**

> 2026-10-10 我在"Vercel 那条错分支"上顺手修了 `fs.cpSync` 沙箱强杀、定位了 opennext 的
> `execSync` 撞沙箱 —— **修得都对，但目标错了，修好的东西一次都没用上。**

## 三、部署前 / 部署后 检查清单（照抄）

### 部署前

- [ ] 线上域名是哪个？谁在服务它？（DNS + 响应头 `Server:`）
- [ ] 线上绑定的资源名 / ID，和我即将部署的**完全一致**吗？
- [ ] 本地能跑起来吗？（`wrangler dev --local` / `npm run dev`）
- [ ] 本地产物字节数记下来了吗？（用来和线上比对）
- [ ] 网络基准跑了吗？

### 部署后（**不许跳过**）

- [ ] 线上访问新内容，`code=200` 且**字节数与本地一致**（带 `?v=$RANDOM` 绕缓存）
- [ ] 旧内容**没有**被弄坏（随便抽 1~2 个老页面）
- [ ] 首页/列表页**收录了**新内容
- [ ] 把"线上真身"的名字 / ID / 域名**写进文档**，别留给下一个人猜

## 四、本机特有环境（2026-10-10 实测）

### 4.1 博客小站 —— ⚠️ 有两个名字只差一个字母的 Worker

| Worker 名 | 状态 | 说明 |
|---|---|---|
| `xinghuisama**b**logs`（**多一个 a**） | ✅ **线上真身** | `ephemeralbloom.dpdns.org` 绑在它上面 |
| `xinghuisanblogs` | ❌ 废弃 | 没绑任何域名，但 `wrangler.jsonc` 里写的是它 |

- **真站**：`https://ephemeralbloom.dpdns.org`（Cloudflare Worker，`Server: cloudflare` + `x-opennext: 1`）
- **`wrangler.jsonc` 的 `name` 必须是 `xinghuisamablogs`**
- **主路径是 `git push`** → GitHub 触发 Cloudflare 自动构建（约 100~150 秒）
- ⚠️ **本机没有 GitHub 凭据，`git push` 会 401** —— 推完必须 `git log origin/main -1` 核对远端 SHA
- 备用路径：`cd D:\work\git\XinghuisamaBlogs\XHBlogs && node_modules/.bin/wrangler deploy`
- 工作目录：`D:\work\git\XinghuisamaBlogs\XHBlogs`（**仓库根是上一层**，不是 XHBlogs）

### 4.2 本机沙箱会强杀递归 `fs.cpSync`

任何**递归** `fs.cpSync` 会让 node 进程被直接 kill（**RC=127，无异常、`exit` 钩子都不触发**）。
`opennextjs-cloudflare build` 内部用了它 ⇒ 构建中断。

**补丁**：`D:\work\AI产出\小站部署\cpsync-shim.cjs`
用 `NODE_OPTIONS=--require=<该文件>` 预载，把 `fs.cpSync` 换成手写递归
（`mkdirSync` + `copyFileSync`）。**实测可行。**

### 4.3 Vercel 那边（与真站无关，但别搞混）

- 项目 `youhuawushi-blog`，**没绑任何自定义域名**，账号下 **0 个域名**
- git 集成缺 `rootDirectory: XHBlogs` ⇒ **所有 git 触发的构建全部 Error**
  （仓库根没有 `app/` 目录）。CLI 直传可以绕过
- `www.xinghuisama.top` 仍指向另一个 Vercel 账号的旧部署 —— **历史遗留，不是真站**

### 4.4 本机网络代理

- 会限速、会超时、并发即挂。**先跑 `https://www.baidu.com/` 基准**（约 0.5s）
- 出现 `code=000` 先怀疑它，别先怀疑站点
- **大响应（>100KB）容易被拖断**：加 `curl --compressed`，160KB 的首页会压到 ~82KB，8 秒就能下完
- ⚠️ **`git push` 走的是另一套代理，不受环境变量控制**：
  仓库里写死了 `http.proxy = http://127.0.0.1:7892`（本机代理客户端 Clash 之类），
  **它的优先级高于 `HTTPS_PROXY` 环境变量**。该客户端没开时 push 会报：
  `Failed to connect to github.com:443 over proxy 127.0.0.1 after 2111 ms`。
  临时绕过（**不改仓库配置**）：

  ```bash
  git -c http.proxy=http://127.0.0.1:56978 -c https.proxy=http://127.0.0.1:56978 push origin main
  ```

  判断哪个端口活着：`netstat -ano | grep "127.0.0.1:<端口>"` —— 有 `LISTENING` 才通，
  只有 `FIN_WAIT_2` / `CLOSE_WAIT` 说明对面已经关了。

### 4.5 `next build` 会"静默卡死" —— 两个已知根因（2026-10-10 实测）

**正常基准：`next build` 在本机只要 12~18 秒。**
（可查 `.next/trace-build` 里 `id=1` 那条 `next-build` 的 `duration`，单位微秒）

一旦超过 2 分钟、且 `.next` 无新文件写入，**就是卡死，不要再等**。

#### 根因 A：`next.config.ts` 里的 `initOpenNextCloudflareForDev()` 在构建期也执行

它本该只在 `next dev` 时跑。构建期执行会在 `127.0.0.1` 上起一个 miniflare 代理并**永久等待**。

识别特征（四条全中基本可确诊）：
- 日志停在 `Using secrets defined in .dev.vars` 之后不再动
- `netstat -ano | grep <构建PID>` 能看到它 **LISTENING**
- CPU 占用接近 0（`cat /proc/<msysPID>/stat` 看 utime/stime 几乎不涨）
- 多出一个 `node_modules/wrangler/node_modules/@esbuild/win32-x64/esbuild.exe` 子进程

修法 —— 加环境守卫：

```ts
// next.config.ts 末尾
if (process.env.NODE_ENV === "development") {
  import("@opennextjs/cloudflare").then((m) => m.initOpenNextCloudflareForDev());
}
```

#### 根因 B：`.next/cache/turbopack` 被"中途杀掉的构建"污染

Turbopack 持久缓存约 128MB。构建被 kill 后缓存处于不一致状态，
下一次 `next build` 会在读缓存时卡住 —— **CPU 有 10~15% 占用但零文件写入**，最容易被误判成"只是慢"。

修法：`rm -rf .next` 后重建。**冷缓存也只要约 12 秒**，比等它"恢复"快得多。

#### 怎么 30 秒内判定卡死 vs 慢

```bash
# 1) 正常耗时基准（上一次成功构建）
python -c "import json;d=json.load(open('.next/trace-build'));print([e for e in d if e.get('id')==1])"

# 2) 近 2 分钟有没有写文件 —— 0 就是卡死
find .next -newermt "$(date -d '-2 minutes' '+%Y-%m-%d %H:%M')" -type f | wc -l
```

#### ⚠️ 连带教训：`--skipNextBuild` 不能随便用

`output: 'standalone'` 是 **OpenNext 在跑 `next build` 时通过环境变量注入**的。
如果你自己手跑 `next build`、再 `opennextjs-cloudflare build --skipNextBuild`，
会因为缺 `.next/standalone/.next/server/pages-manifest.json` 报 `ENOENT` 而失败。

**正确姿势**：既然构建只要 12 秒，就直接让 OpenNext 完整跑（不加 `--skipNextBuild`）：

```bash
NODE_OPTIONS="--require=D:/work/AI产出/小站部署/cpsync-shim.cjs" \
  node_modules/.bin/opennextjs-cloudflare build
node_modules/.bin/wrangler deploy
```

## 五、反模式清单（做过一次，不许再做）

| ❌ 反模式 | ✅ 正确做法 |
|---|---|
| 部署命令打印 Success 就宣布完成 | 必须 curl 线上比对字节数 |
| "小站"是哪个自己猜 | 问一句，或从 DNS/响应头查 |
| 远端 500 就一头扎进代码 | 先本地 `wrangler dev --local` |

## 六、正确顺序（背下来）

```
① 确认线上域名 + 谁在服务它        （DNS + 响应头 Server:）
② 确认要改的东西 == 线上那一个      （名字 / ID 逐个核对）
③ 本地跑一遍，确认产物正常          （wrangler dev --local）
④ 部署
⑤ 验证线上内容真的变了              （curl 比对字节数 + 抽检旧页面）
⑥ 把"线上真身"写进文档
```

**任何一步没做就往下走，后面都要用小时来还。**
