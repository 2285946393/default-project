## 0. 一句话结论

**这是「给游戏本体加玩法选项」的标准答案，而且它和我们的 DouSpire 是同一个域。**

它把休息处的 2 个选项（休息 / 锻造）扩到 **14 个**，还顺手解决了两个我们一定会撞上的问题：
- **选项超过 5 个，一行放不下怎么办** → 自己劫持容器 + 加滚动 + 重排（§5）
- **多人联机时两端选项不一致会串位** → 官方同步是**按下标**的，必须确定性排序（§3）

我们的 `projects/dou-spire/DouSpireCode/Table/DouSpireRestSite.cs` 开头就写着
「照着 RestSiteExpansion / Miyabists2 两个现成 mod 抄的」—— 这次是把那个"抄"补成"懂"。

## 2. ★★★ 官方口子：`TryModifyRestSiteOptions`

**不用 Harmony 打补丁**。游戏本体就给了钩子，由 `Hook` 统一派发：

```csharp
// MegaCrit.Sts2.Core.Hooks.Hook.cs:2402
public static IEnumerable<AbstractModel> ModifyRestSiteOptions(IRunState runState, Player player,
                                                              ICollection<RestSiteOption> options)
{
    List<AbstractModel> list = new List<AbstractModel>();
    foreach (AbstractModel item in runState.IterateHookListeners(null))
        if (item.TryModifyRestSiteOptions(player, options)) list.Add(item);
    return list;
}

// MegaCrit.Sts2.Core.Models.AbstractModel.cs:2105
public virtual bool TryModifyRestSiteOptions(Player player, ICollection<RestSiteOption> options) => false;
```

**触发点**（`RestSiteOption.Generate`，`:53`）：

```csharp
int num = 2;
span[0] = new HealRestSiteOption(player);      // 休息
span[1] = new SmithRestSiteOption(player);     // 锻造
if (player.RunState.Players.Count > 1) list2.Add(new MendRestSiteOption(player));  // 多人加「修补」
Hook.ModifyRestSiteOptions(player.RunState, player, list2);   // ← 所有 mod / 遗物在这里插
return list2;
```

**原版就是这么干的**（`Shovel` 铲子 → `DigRestSiteOption`）：

```csharp
public sealed class Shovel : RelicModel
{
    public override bool TryModifyRestSiteOptions(Player player, ICollection<RestSiteOption> options)
    {
        if (player != base.Owner) return false;      // ← 只给自己加
        options.Add(new DigRestSiteOption(player));
        return true;
    }
}
```

原版自带 7 个这种"额外选项"：`Clone` / `Cook` / `Dig` / `Hatch` / `Kindle` / `Lift` / `Mend`。
**想学"一个遗物怎么给篝火加选项"，直接读这 7 个。**

### `RestSiteOption` 基类全貌（`:19`）

| 成员 | 说明 |
|---|---|
| `abstract string OptionId` | 稳定 id。**本地化键和图标文件名都由它拼** |
| `LocString Title` | **非 virtual** → `rest_site_ui` / `OPTION_<OptionId>.name` |
| `virtual LocString Description` | `rest_site_ui` / `OPTION_<OptionId>.description` |
| `string IconPath` | `ui/rest_site/option_<optionid 小写>.png` |
| `virtual IEnumerable<string> AssetPaths` | 打包/预加载清单 |
| `virtual bool IsEnabled` | 默认 `true`；置灰时**仍可悬停看说明** |
| `abstract Task<bool> OnSelect()` | 返回是否"成功"（false 时选项**不消耗**） |
| `virtual Task DoLocalPostSelectVfx(ct)` / `DoRemotePostSelectVfx()` | 自己 / 别人的表现层 |

> ⚠️ **`Title` 和 `Icon` 是非 virtual 的** —— 所以 RitsuLib 只能**运行时补丁它们的 getter**
> 才能让你换标题/图标。这正是我们记忆里那条「图标/标题按 OptionId 自动拼」的来源。

### RitsuLib 的 `ModRestSiteOptionTemplate`

`STS2RitsuLib.Scaffolding.Content.ModRestSiteOptionTemplate : RestSiteOption(owner)`，
实现 `IModRestSiteOptionAssetOverrides`（`AssetProfile` / `CustomIconPath`）
和 `IModRestSiteOptionCustomTitle`（`CustomTitle`）。
RitsuLib 在运行时补丁 `Title`/`Icon` 的 getter 来尊重它们。
官方注释还写明：**请从 `TryModifyRestSiteOptions` 重写里 Add 这个选项**。

## 3. ★★★ 联机同步是**按下标**的 —— 最危险的坑

```csharp
// RestSiteSynchronizer.cs:164
public Task<bool> ChooseLocalOption(int index)
{
    OptionIndexChosenMessage message = default;
    message.type = OptionIndexType.RestSite;
    message.optionIndex = (uint)index;                 // ← 只发下标！
    message.location = _messageBuffer.CurrentLocation;
    _netService.SendMessage(message);
    return ChooseOption(LocalPlayer, index);
}

// :90 BeginRestSite() —— 每个玩家的选项表是**各自本地生成**的
foreach (Player player in _playerCollection.Players)
    _restSites.Add(new PlayerRestSite { options = RestSiteOption.Generate(player) });

// :175 ChooseOption —— 唯一的校验只有越界
if (optionIndex >= restSite.options.Count) throw ...;
RestSiteOption option = restSite.options[optionIndex];   // 下标 → 选项
```

> **⚠️ 结论：网络上传的是 `uint` 下标，不是 `OptionId`。**
> **两端 `options` 列表只要有一个元素的差异（顺序不同 / 数量不同），
> 同一个下标就指向不同的选项 → 双方看到/执行的是不同的东西。**
> 而且游戏**只校验越界**，不做任何一致性校验 —— 错了也**不会报错，只会静默错**。

**这条直接解释了这个 mod 为什么要做下面这些事**：

1. **确定性排序**：`RestSiteExpansionSingleton.DesiredOrder`（22 个 id 的固定数组）
   + `RankOf(optionId)` → `RestSiteSubmenuFilter.Apply` 里
   `orderby RestSiteExpansionSingleton.RankOf(OptionIdOf(button))`。
   **顺序不能依赖字典/反射的枚举顺序。**
2. **启动自检**：`RestMenuState.ValidateOrWarn(DesiredOrder)` ——
   检查排序表有没有漏掉子菜单入口/成员、有没有一个选项同时属于两个组，
   有问题就打 WARN。**排序表缺项 → 该选项会被排到最后 → 可能就是两端不一致。**
3. **配置必须两端一致**：见 §6（房主权威）。

### 另外两个钩子

```csharp
// AbstractModel.cs:2273 —— 选完一个之后，要不要把剩下的都禁掉？默认 true
public virtual bool ShouldDisableRemainingRestSiteOptions(Player player) => true;
```
→ 「迷你帐篷」这类遗物**返回 false**，所以能在一个篝火连选多项。
→ RestSiteExpansion 的「帐篷平衡」是**反过来**：即使帐篷允许，它也把子菜单内部锁成单选。

`AfterAllRestSitesCompleted()` —— 房间退出前必须等所有人选完（否则校验和会不一致）。
`BeforeLocalRestSiteExited()` —— 本地还有剩余选项时清空并广播 `RestSiteSkippedMessage`。
`OnPeerDisconnected()` —— **有人掉线时要把他的休息处标记完成**，否则房间退出会**永远卡住**。

还有 `RestSiteOptionHoveredMessage`（悬停同步，**50ms 节流**）——
联机时队友能看到你在看哪个选项。

## 4. ★★★ 子菜单机制（选项太多怎么组织）

`RestSubmenu` 是 `[Flags]` 枚举：`None=0 / Rest=1 / Forge=2 / Gold=4 / Fun=8`。

```csharp
private sealed record SubmenuDef(RestSubmenu Menu, string EntryOptionId, string EntryIconResPath,
                                 string[] MemberOptionIds, string HintLocKey);

// 4 条定义 = 4 个子菜单；入口选项复用了原版图标
new SubmenuDef(RestSubmenu.Rest,  "REST_MENU",  "res://images/ui/rest_site/option_heal.png",
               new[]{"NAP","HEAL","DEEP_SLEEP","MEDITATE","STAY_UP_LATE"}, "…_REST_MENU_HINT"),
new SubmenuDef(RestSubmenu.Forge, "FORGE_MENU", "res://images/ui/rest_site/option_smith.png", …),
new SubmenuDef(RestSubmenu.Gold,  "GOLD_MENU",  "res://art/images/rest_site/gold_menu.png",  …),
new SubmenuDef(RestSubmenu.Fun,   "FUN_MENU",   "res://art/images/rest_site/fun_menu.png",   …);
```

**核心思路：用一个"假的"选项当子菜单入口。**

- `SubmenuEntryRestSiteOption`（继承 `ModRestSiteOptionTemplate`）：
  - `_menu == None` → 它是「返回」按钮 → `RestMenuState.CloseSubmenu(owner)`
  - 否则 → `RestMenuState.OpenSubmenu(owner, _menu)`
  - `OnSelect()` 返回 **`false`** → **选项不消耗、不结束休息处**，纯粹是"切页面"
  - `IsEnabled` = 这个子菜单是否有任何成员可用
- **开合状态存在 Godot 节点的 meta 上**，不是自己维护一个字典：
  ```csharp
  room.SetMeta("rse_submenu_" + player.NetId, (int)menu);        // 每个玩家一份
  holder.SetMeta("rse_choices_submenus", (int)activeMask);       // 哪些子菜单是开的
  ```
  → **好处：场景一销毁状态自动没了，不用手动清理。**
- **可见性判定**（`RestMenuState.IsVisible(optionId, open, mask)`）：
  - 没有子菜单 → 全显示
  - 有开着的子菜单 → 只显示「返回」+ 该子菜单成员
  - 没开子菜单 → 显示所有"不属于任何子菜单"的 + 子菜单入口
- **重排**：`MoveVisibleToFront()` 用 `MoveChild` 把可见的挪到前面，
  再把「返回」放到最后 —— 这样隐藏的按钮**不会留下空位**。
- **新增按钮**：连 `ChildEnteredTree` 信号 → 新按钮进场时立刻算一次可见性 + 重排。
- 顺带：`RestSiteOptionAccess` 用反射读 `RestSiteOption.Owner`（`protected`），
  拿不到就**从兄弟节点里找一个能拿到的** —— 兜底很到位。

## 5. ★★★ 布局适配（`RestSiteChoicesLayout`，465 行）

原版一行放 5 个（`ButtonWidth 251` + `GapX 40` = 步进 291）。超过就溢出。

**做法**：Harmony **Prefix** 挂 `NRestSiteRoom._Ready` → `TryInstall(room)`：

1. 拿 `%ChoicesContainer`（Godot 唯一名节点）和它的父 Control
2. 早退条件：没子菜单 && 布局开关关 && 选项数 ≤ 5 → **完全不碰原版**
3. 把 `%Header` 上移 0、`%Description` 上移 **223**，给选项块腾地方
4. 新建 `ScrollContainer`（`VerticalScrollMode=3`、`FollowFocus=true`），复制原容器的 anchors
5. 新建提示 Label `RestSiteScrollHint`：
   **字体直接从 `%Description` 取 `GetThemeFont("normal_font")`**（跟着游戏语言/字体走），
   字号 18、颜色 `(1,0.96,0.89,0.65)`、描边 8
6. **新建一个叫 `ChoicesContainer` 的 Control，并设 `UniqueNameInOwner = true`**，
   把原容器改名成 `ChoicesContainerVanilla`
   → 这样 `%ChoicesContainer` 就指向**新的**容器，游戏后续 `AddChild` 按钮都进新容器
7. **★ 校验 + 回滚**：
   ```csharp
   if (room.GetNodeOrNull<Control>("%ChoicesContainer") != holder)
   {
       // 唯一名没抢到 → 把新节点全删掉、原容器改回名字
       MainFile.Logger.Warn("[Layout] 唯一名校验未通过，已回滚为原版布局。");
       return;
   }
   ```
   **抢唯一名失败就整块回滚，不留半成品** —— 这是很值得抄的防御姿态。
8. 给新容器打 meta `rse_choices_layout`，连 `ChildEnteredTree` / `ChildExitingTree`
9. `RelayoutDeferred()` → `CallDeferred`（**等这一帧结束再算**）

**`Relayout()`**：
- 先 `RestSiteSubmenuFilter.Apply()` 过滤 + 排序
- 行数 = `ceil(count/5)`，最多 5 列
- **`MeasureTextBottom()` 真的去量字高**：
  `label.GetThemeFont("font")` + `GetThemeFontSize("font_size")` + `font.GetHeight(size)`
  → 布局跟着字体/行高走，不写死。量不到就回退 205。
- 摆位：`(16 + (contentW - rowW)/2 + col*291, 10 + row*stride)`
- **重算每个按钮的 `FocusNeighborTop/Bottom/Left/Right`**（手柄导航），带跨行环绕
- 设 `holder.CustomMinimumSize = (blockW, contentH)`
- **日志去重**：把布局签名存进 meta，只有变了才打日志（`"[Layout] 选项摆位："`）

**可调常量**（想改观感直接照这个调）：
`251/164`（按钮宽高）、`40/14`（横竖间距）、`291`（步进）、`16/10/10`（内边距）、
`223`（描述上移）、`164/190`（提示条位置）、`-300`（块顶）、`490`（可用高度）。

## 6. ★★ 联机配置：房主权威（RitsuLib `RunSavedData`）

README 那句「**单击改动即生效，联机时以房主配置为主**」是这么实现的：

private static bool TryGetMultiplayerSnapshot(Player player, out RestSiteExpansionSnapshot? snapshot)
{

## 9. ★ 帐篷平衡：给**原版选项**打补丁

「帐篷平衡」要求子菜单内部单选。但原版「休息」「锻造」不归它管，所以：

```csharp
[HarmonyPatch(typeof(HealRestSiteOption), "OnSelect")]
internal static class HealRestSiteOptionTentBalanceOnSelectPatch
{
    private static bool Prefix(HealRestSiteOption __instance, ref Task<bool> __result)
    {
        Player owner = RestSiteOptionAccess.GetOwner(__instance);
        if (owner == null || !TentBalanceGate.IsBlockedFor(owner, owner_optionId)) return true;
        __result = Task.FromResult(false);      // ← 拦下：选项不消耗
        return false;
    }
}
```
同款还有一个 `…TentBalanceDescriptionPatch`（改说明文字）+ `SmithRestSiteOption` 的两份。

**判定依据**是游戏自己的 run 历史：
```csharp
val.CurrentMapPointHistoryEntry.GetEntry(player.NetId).RestSiteChoices   // List<string> of OptionId
```
→ **不要自己存"这个篝火选过什么"，游戏已经记了。**（§3 里 `ChooseOption` 就在写它。）

## 10. 它踩过 / 避过的坑（我们该注意的）

1. **选项顺序必须确定性** → 否则联机下标错位（§3）。**有固定排序表 + 启动自检。**
2. **配置必须两端一致** → 房主快照；缺失就禁用，**不回落本地**（§6）。
3. **`%ChoicesContainer` 唯一名劫持后必须校验**，失败整块回滚（§5 第 7 步）。
4. **`OnSelect()` 返回 `false` = 不消耗选项** —— 子菜单入口/返回就是靠这个实现的。
5. **`Hook.ModifyRestSiteOptions` 会被每个 `TryModifyRestSiteOptions` 调用一次** ——
   必须像 `Shovel` 那样 `if (player != base.Owner) return false;`，否则**多人时给所有人加选项**。
6. **`_slot` 为 null 的兜底**：RitsuLib 注册失败时不能崩，回落到本地配置 / 持久存储。
7. **重入保护**：写大厅快照会再次触发 staging 事件。
8. **所有 `Info` 日志都带 `player=NetId`** —— 联机排查时能分清是谁的。
9. **掉线要把对方的休息处标记完成**（`OnPeerDisconnected`），否则房间退出死等。
10. **每个补丁单独 `try/catch`**（`MainFile.Initialize` 里 `PatchAll` 整体包了 try）：
    `"Harmony 补丁应用失败（选项布局适配将不可用）"` —— 布局挂了，mod 主体照常。

## 11. 对 DouSpire 的具体可复用清单

| # | 结论 | 落点 |
|---|---|---|
| 1 | **官方口子就是 `AbstractModel.TryModifyRestSiteOptions`**（我们已经在用） | 已验证 ✓ |
| 2 | **必须 `if (player != base.Owner) return false;`** —— 否则多人给所有人加 | 检查 `DouSpireRestSiteSingleton` |
| 3 | **联机是按下标同步的**：我们的选项列表必须**确定性排序**，且两端数量/顺序一致 | 我们的斗地主选项 + 赌注相关选项 |
| 4 | 我们的篝火选项如果要加**开关/数值**（赌注大小等），联机要**房主权威**，用 `RunSavedData` + `SyncLobbyOnChange` | 新增 |
| 5 | 选项超过 5 个就要做**布局适配**（`%ChoicesContainer` 劫持 + 滚动 + FocusNeighbor 重算） | 我们选项还少，暂不需要；**但要做就照抄 §5** |
| 6 | 「跨战斗状态」用 `RunSavedData`（局内）+ `ModDataStore`（持久）两层，`LocalContext.IsMe` 才写盘 | 斗地主的"钱"如果要跨局保留 |
| 7 | 「下一场战斗生效」用 `HookedSingletonModel : base(HookType.Combat)` 覆写 `BeforeCombatStart` / `ModifyHandDraw` / `ModifyMaxEnergy` / `AfterEnergyReset` | 如果我们加"下一场战斗"类效果 |
| 8 | **选项 id 是稳定契约**：本地化键 + 图标文件名都由 `OptionId` 拼，改了要同步改注入 | 我们的 `DOU_SPIRE` |
| 9 | `ShouldDisableRemainingRestSiteOptions` 默认 `true`（选一个就结束）；想连选要自己返回 false | 我们的"不限次数"需求相关 ⚠️ |
| 10 | 加设置页照抄 RitsuLib `ModSettingsValueBinding` + `Settings` 命名空间 | 我们的配置页 |

> ⚠️ **第 9 条要特别注意**：用户原话是「**不限次数**」。
> 而游戏默认选完一个就把剩下的禁掉。**我们"不限次数"到底是"一个篝火能连打多局"还是"整局不限次数"，
> 实现路径完全不同** —— 前者要 `ShouldDisableRemainingRestSiteOptions` 返回 false，
> 后者只要每次 OnSelect 都返回 true 并且不消耗。**动手前先跟用户确认。**
