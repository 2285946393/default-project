## 一、症状

用户说"皮肤用不了 dsh 插件"——网页里「设置 → 皮肤」看不到 / 皮肤不生效。

## 二、根因（两条，都撞在一起）

### 坑 1：皮肤插件被自动升到新版，与旧 DSH 不兼容 → 整条被跳过

| 项目 | 版本 | 位置 |
|---|---|---|
| **桌面图标真正跑的 DSH** | **0.1.5-rc.2** | `D:\software\dsh\node_modules\@deepseek-ai\dsh` |
| npm 全局另一份（不是你在用的） | 0.1.7-rc.2 | `%APPDATA%\npm\node_modules\@deepseek-ai\dsh` |
| 皮肤插件（10-16 自动更新后） | 0.1.8 / 0.1.7 | `profiles\web\node_modules\@smalltailqwq\` |

- 皮肤 0.1.4 起 peer 要求 `@deepseek-ai/dsh >=0.1.7-rc.1`，本机是 0.1.5-rc.2 → **启动时整条 bundle 被跳过**
- **唯一不挑 DSH 版本的皮肤版本是 0.1.3**（peer 只有 `@deepseek-ai/cordis ^4.0.1`，没有 dsh）
- 同类历史：桌宠 `dsh-pet` 也是这个原因被停用的（补丁里有注释记录）

### 坑 2：补丁文件末尾的"自动生成"块把两套皮肤都关了

`D:\software\dsh-home\profiles\web\cordis.patch.yml`：

- 文件**开头**手写段：女仆 = `disabled: false`、虎鲸 = `disabled: true`（正常，皮肤互斥）
- 文件**末尾** `# --- dsh-skin managed (auto-generated; do not edit) ---` 块：
  两套**都**是 `disabled: true`
- **后面的覆盖前面的** → 结果一个都不显示

> ⚠️ 这个块是某个皮肤管理脚本自动写的，标签写着 "do not edit"。
> **但它是错的**，会覆盖手写配置。以后皮肤"突然全没了"，先查文件末尾这段。

## 三、为什么 DSH 升级失败（9-25 / 9-27 两次，都是同一个错）

日志：`D:\software\dsh-home\dsh-update-checker-ops.log`

```
op: main-update-error
error: update did not reach 0.1.7-rc.2 (installed=0.1.5-rc.2) — restored from backup
code: E_VERSION
```

**不是下载失败，是升级错了地方。** 链路：

1. `deployType(root)` 判断部署类型的逻辑：读根目录 `package.json`，
   **有** name/dependencies → `"local"`；**读不到** → `"global"`
2. `D:\software\dsh\` 目录下**没有 package.json**（只有 `node_modules`、`dsh.cmd` 等）
   → 被判成 `"global"`
3. 于是执行 `npm install -g @deepseek-ai/dsh@0.1.7-rc.2`
   → **装进了 npm 全局那份，桌面图标用的 `D:\software\dsh` 那份纹丝不动**
   （全局那份 0.1.7-rc.2 就是这两次升级的残留，时间戳 9-27 12:58）
4. 装完 `readInstalledVersion()` 一读还是 0.1.5-rc.2 ≠ 目标 → 报 `E_VERSION` → 自动回滚

**另外**：10-13 / 10-16 又各拦了一次升级，日志是 `main-update-prerelease-blocked`。
原因是新版本是 `0.2.1-alpha.x`，当前在 `rc` 通道 —— **升级器默认不允许从 rc 跳到 alpha**，要先切通道。

### 想真升级的话（本次没做，先记着）

- 在 `D:\software\dsh\` 下补一个 `package.json`（含 dependencies），让它被识别成 `local`，才会升对地方
- 或设环境变量 `DSH_DEPLOY_ROOT=D:\software\dsh`（`findDeployRoot()` 会优先读它）
- 再把更新通道从 `rc` 切成 `alpha` 才能拿到 0.2.x
- ⚠️ 升上去后 `dsh-chat-manager` 等老插件可能要连带换版本（见 `DSH插件安装-版本兼容记录-20261003.md`）

## 四、我改了什么（最小改动，未动 DSH 本体）

1. **补丁开关**（`profiles\web\cordis.patch.yml` 末尾）
   `ui-skin-maid-atelier: disabled false`，`ui-skin-orca-link: disabled true`
   —— 与开头手写段一致，保持皮肤互斥（同时开会叠加装饰层、设置按钮消失）
2. **皮肤降级到 0.1.3**（唯一兼容 0.1.5 的版本）
   ```bash
   cd D:/software/dsh-home/profiles/web
   pnpm add "@smalltailqwq/dsh-client-ui-skin-maid-atelier@0.1.3" \
             "@smalltailqwq/dsh-client-ui-skin-orca-link@0.1.3" \
             "@smalltailqwq/dsh-client-ui-skin-deep-whale-manager@0.1.3"
   ```
3. **把 package.json 里的 `^0.1.3` 钉成 `0.1.3`**
   —— `^` 允许升到 0.1.8，会被更新器再次搞坏。钉住才一劳永逸。

## 五、验证方式（本次用的）

另起端口跑，不动正在用的 3080 实例（**不要批量杀进程**）：

```bash
cd /d/software/dsh
nohup node node_modules/@deepseek-ai/dsh/lib/bin.js web --port 3099 --no-open > /tmp/dsh3099.log 2>&1 &
sleep 25
curl -s -o /dev/null -w "%{http_code}\n" "http://127.0.0.1:3099/"   # 401 = 服务活着
grep -i "skin|skipping|incompatible|did not activate" /tmp/dsh3099.log
```

- 本次结果：**启动日志干净，没有任何 `skipping` / `incompatible` / `did not activate`**
  （降级前必然会有，这就是修好的证据）
- ⚠️ 页面是客户端渲染，`curl` 拿到的 body 是 0 字节、API 全 401，**靠 curl 验证不了皮肤有没有真的渲染**
  → 最终确认要**重启 DSH 后在网页里看**（见下）

### 收尾

```bash
PID=$(netstat -ano | grep ":3099" | grep LISTENING | awk '{print $5}' | head -1)
taskkill //PID $PID //F      # 只杀这一个 PID
```
